# Changelog

Notable changes to Trysil, in reverse chronological order.

`## 2.0.0` is the released version. The sections below it, down to
`## JOIN Queries & Raw Select`, are development windows between 1.0.0 and 2.0.0,
in the same order: they were never tagged, so they carry a title and no version
number. From `## Change Tracking & Soft Delete` down, the sections are the ones
the changelog of 1.0.0 already had. **Read the windows newest first and let the
newest win** - `includeDeleted`, for one, was read from the select payload in a
window below and is decided server-side from 2.0.0, and both entries are true of
their moment.

## 2.0.0 - Audit Integrity, Directional JSon Attributes & Fail-Safe Startup

*2026-09-20*

**Major release: upgrading from 1.0.0 requires code changes.** This section carries **twenty-two compilation breaks** and **eighty-four breaks the compiler does not catch**, and a long list of behaviour changes, described inline below. **What is counted, and against what:** a break is counted when code of the host written against 1.0.0, or against the public `master` between 1.0.0 and this release, has to change. Most of those upgrading run the public master, and fourteen of the breaks below do not exist against the tag `v1.0.0` - the compilation breaks on `DoConfigureConnection`, on `TTObjectLazyList<T>` and on the `IncludeDeleted` overload of `TryGet<T>`, and the silent ones on the text of `SColumnNotFilterable`, on an RS256 key that is not RSA, on `CreateUndeleteCommand`, on `Undelete<T>` writing only what it restores, on a `NUMBER(1)` read as a boolean on Oracle, on the 30-byte bound on a join column alias, on `TTHttpLogParameters`, on a list built by `CreateEntityList<T>` owning what the identity map will not hold, on freeing that list before its context, on `RegisterConfig` for a connection already registered and on a detail collection whose child entity maps a `[TJoin]` - so they carry *on the public master, not in 1.0.0* in their title. Most of the silent ones are defects corrected rather than decisions taken - a value cut to the size of its column without a word, a paging dropped because one of its two bounds was missing, a pure date sent as the evening of the day before. They are counted all the same: what is asked is whether code of the host has to change, not whether the behaviour it was written against was worth keeping. What a client of the HTTP server sees change - a request refused where it was answered, a cap on the body, a filter value read differently - is marked **Breaking for a client of the server, not counted** - eleven entries - and the upgrade page lists the ones a client is likely to meet. Four more carry **Breaking, not counted because the code it hits could not work**: a refusal put where an access violation, an empty `FROM`, a cache keyed on a key nobody held, an instance the identity map freed under the caller still holding it on the public master, or a `BaseUri` that made every route answer `404` used to be. Of the eighty-four silent ones, four are about a custom driver living outside this repository - see the `TTGenericConnection`, `TTParam` and `CreateUndeleteCommand` entries under ORM, and `TTMetadataProvider.GetConnectionName`. Of the eighty that remain, **nine are about lifetime and are the ones to read first**: an entity reached through a lazy member is now freed with the entity that carries it, so a reference kept past that entity's life is a use-after-free in code that still compiles; a rolled back transaction **rewinds what Trysil wrote to the entities**, so an entity written inside a transaction and freed with a bare `Free` before it ends makes the rollback write into freed memory - every entity goes through `FreeEntity<T>`; `TTSession<T>.Insert` **adopts** the entity it is given and, unless the identity map holds its type, frees it with the session, where in 1.0.0 the host freed it; a `TTSession<T>` releases its clones and the entities it inserted through the disposal path, and must be freed **before** the context that created it; the list handed to `CreateSession<T>` must **outlive** the session, because `ApplyChanges` reads it; a list built by `CreateEntityList<T>` now owns what the identity map will not hold, so a loop that freed those entities by hand frees them twice and has to go; that same list must be freed before that context, which it never had to be, because it tells the context about every entity it frees and until this release it owned nothing whenever the map was on; a `TTContext` must now be freed **before** the connection it was built on, because it registers an observer there; and a foreign key the **JSON deserializer** writes over an entity already read frees the entity the lazy member had loaded, so on a context without an identity map a reference kept to the old master across the call is a use-after-free, where the old instance stayed and the relation answered with it under a new id. **Thirty-six refuse something that used to go through**, so the code that meets them stops rather than drifts: at mapping time, `[TDeletedBy]` without `[TDeletedAt]`, two change tracking attributes on one column, and four mappings that cannot mean anything; identifiers are quoted now, so a name written in the attribute with the quotes of the engine, `[TTable('"Clienti"')]`, or one that names something other than an identifier, such as a table-valued function, is quoted as a name and reaches nothing, a column whose name cannot become the name of a parameter is refused at the first read where it was read as long as nothing was written, and `.Where(name).IsNull` on a column the entity does not map - with its twin in the expression API, `TTProperty.IsNull` - raises `SColumnNotFound` where it used to emit the name, and so does an `OrderByAsc` or an `OrderByDesc` on anything but a mapped column - an expression, a `NULLS LAST`, a name the entity does not map - which reached the statement as it was, and a detail collection whose child entity maps a `[TJoin]`, which loaded when its column name was not ambiguous; `Save<T>` on a `TTHttpContext`, an `Insert<T>` of an entity whose primary key is zero, a `Refresh<T>` of a row that is no longer there, an `OldEntity` first read after the command, an offset with no limit, and an exception raised inside a `[TValidator]`, which now leaves the validator instead of becoming a validation error; a string longer than the column it is written to raises, where it was cut to size and the cut value written back into the entity, on a filter value as much as on a write, and two columns whose names differ only by a space and an underscore are refused, where one wrote over the other; every `UPDATE` now leaves a soft-deleted row alone, so an `Update<T>` on a row read with `IncludeDeleted` - the only way to bring a deleted row back in 1.0.0 - raises `ETConcurrentUpdateException`, whose text `SRecordChanged` is reworded to say so: use `Undelete<T>`; on the server, a tenant name that cannot be one, a route with a placeholder before a fixed segment, a `Start` with a route that requires authentication and no authentication class registered, a route carrying `[TArea]` on a listener built by hand, which answers `403` instead of opening, and a body that does not parse, which answers `400` where it answered `500`, so a host that caught `EJSONException` or `EConvertError` around its own call to the deserializer catches nothing now - `ETJSonException` is what every deserializing method of `TTJSonContext` raises, and what `TTJSonDeserializer.EntityFromJSon` raises for a value it cannot convert; and SQL Server no longer sends `Encrypt=No`, so Driver 18 against a self-signed certificate does not connect until the connection string says so. Five more of them: a second `Delete<T>` of a row already soft-deleted, which used to pass and stamp the audit again; a sequence value too large for a `TTPrimaryKey`, which came back cut; an element of a JSON array that is not an object, which was dropped from the list in silence; a `RegisterController`, `RegisterAuthentication`, `RegisterLogWriter`, `AllowAnonymous`, `OnCanLog` or `OnRedactContent` after `Start`, which did nothing where it looked as though it had worked; and `RegisterConfig` for a connection already registered, whose pool parameters were stored and never read. Four more: a `RegisterLogWriter` whose writer opens a file or a connection in its constructor, which is built at registration now and can refuse to start a server that used to start and log nothing; every driver error on the first read of an entity, which arrives as `ETException` where a host could catch `EFDDBEngineException` and read its code; and two more start-up refusals on the server, `[TArea]` with no authentication class registered and `[TArea]` on a route marked `[TAuthorizationType(None)]`, neither of which `AllowAnonymous` waives - it waives the check on authentication, not the two on areas. Four more, all on the JSON and HTTP side: an empty HMAC secret, which signed tokens anyone could reproduce; an RS256 key that is not RSA, which verified ECDSA signatures while the token header said otherwise; a detail collection sent as something other than an array, which from Delphi 12 deserialized an entity with no rows at all and said nothing; and `TTHttpContext.Delete<T>(AID, AVersionID)` on a row that is not there, which raises `ETHttpNotFound` where it raised `ETConcurrentUpdateException` - a controller that caught the latter around that call catches nothing now. **The other thirty-five change what a working call writes, reads or returns, and say nothing**: `Update<T>` no longer writes the creation audit columns or the delete audit columns, so an import that corrected `CreatedAt`, or a soft delete done by hand with `Update<T>`, writes nothing now, and no audit column is read from a JSON body any more, whatever the entry point; `OldEntity<T>` returns `nil` where there is no old row, where it used to hand back a copy of the **in-memory** state as the state of the database; `Undelete<T>` writes only the columns it restores, so an edit the entity carries is no longer saved with it; connection pooling is on by default, so a connection closed to release a file - SQLite, Firebird embedded - keeps it until the pool is emptied; the e-mail validator now accepts long top-level domains; on Oracle a `NUMBER(1)` arrives as a boolean; a join column alias longer than 30 bytes is shortened; `OrderByDesc` makes every column it is given descending, where only the last one was, and a limit with no offset pages from the first row, where the paging was dropped and every row came back; a `TDate` or a `TTime` member of an entity goes out as `2026-03-05` or `10:30:00`, where both were converted to UTC and a pure date could arrive as the day before; `MetadataToJSon<T>` renames two keys and stops describing a member it never serializes, and `MaxLevels` bounds detail collections too; `TTHttpResponse.ContentEncoding` writes the charset instead of the `Content-Encoding` header; request and response bodies are no longer captured in the log by default, and the short constructors of `TTHttpLogParameters` changed what they mean without changing their signature; a JSON serializer registered by the host is now one instance shared by every request thread instead of one built per call; a member whose name begins with `F` or `f` not followed by an ASCII capital - `FatturaID`, `FirstName`, `F1Codice`, `fattura` - changes its JSON key in both directions, on every entity that goes out through `EntityToJSon` and comes back through `EntityFromJSon`, described in a section below; and three changes in what `DatasetToJSon` emits - an exact decimal read through `CreateDataset` keeps all its digits instead of the fifteen `FloatToStr` writes, a `DATE` or a `TIME` column goes out as `2026-03-05` or `10:30:00` instead of a timestamp converted to UTC, and strings are no longer HTML-encoded, so `Rossi &amp; Figli` goes out as `Rossi & Figli` - and a client that put such a value into a page as HTML was protected by that encoding, by accident, and is not any more. Eleven more of them, and the first is the one to read: `nil` assigned to a lazy member that has not loaded now clears the foreign key, where the assignment did nothing and the next `Update<T>` wrote the old key back; on PostgreSQL a narrow `NUMERIC` arrives as a `TCurrencyField` rather than a `TBCDField`, so a cast on a dataset from `CreateDataset` fails where it worked and `MetadataToJSon<T>` names another type; `[TJSonIgnore]` on a detail collection is obeyed at last, so that key leaves every response; a commit that fails puts the entities back among the new ones, so the `Save <T>` that follows inserts where it updated; two message texts changed - `SForbidden`, and the text of `SColumnNotFilterable` on the public master - which a translation table keyed on the English text loses without a sound; and `[TRequired]` on a lazy relation tells a key never set from a key pointing at no row, with a message of its own, `SRequiredRelationValidation`, which is new and has to be added to that table; and a detail collection left out of a JSON body deserialized over an entity already read keeps its rows, where it was emptied in memory; and an overload of a controller method with no `[TArea]` no longer takes the areas of a sibling that has them, so it answers every authenticated caller where it was restricted; a header a controller method sets before raising is removed from the error response; and the constructor of a tenant config and its `GetParameters` run outside the write lock, in parallel and twice for the same tenant, where `GetParameters` ran under it once. Twenty-one of the twenty-two compilation breaks carry **Breaking (compilation)** in their title; the twenty-second is inside the entry on the numeric validators, where `IsValidInteger` widened to `Int64` and `TValidationValueType` is gone. Do not go looking only for the entries marked **Breaking**: read the section through, because several changes are observable without being source-incompatible. The development windows further down this file carry **compilation breaks of their own**: `NestedException: Exception` is gone from `ETException`, the `TExceptionHelper` class helper on `Exception` is removed, `TTTransaction.Create` lost its **one-argument** form - `TTTransaction.Create(LConnection)` is the call that breaks, and there has never been an argument-less one: that shape belongs to `TTContext.CreateTransaction()`, deprecated but still there - a JWT **application payload must change ancestor**, from `TTHttpJWTAbstractPayload` to `TTHttpJWTHS256Payload` or `TTHttpJWTRS256Payload`, because the abstract one no longer carries `GetSecret` or `Secret` and no longer lives in `Trysil.Http.JWT`, which is the most expensive break here for anyone using Bearer authentication, and `TTHttpJWTEncoding` changed both its signatures while `TTHttpJWTHeader` was removed outright - the third public type this library drops against 1.0.0, and `TTObjectLazyList<T>`, which only the public master ever carried, is a fourth. They carry one the compiler does not catch as well: an entity assigned to a lazy member without an identity map is stored as a **clone**, where 1.0.0 kept the instance and freed it with the context, so an instance the host handed over and rightly stopped freeing is now lost - free what you assign. Note that `TTHttpListener<C>.Create` has now changed twice, once there and once here. Coming from 1.0.0 means reading every section of this file above `## Change Tracking & Soft Delete`, not just this one: from there down, the sections were already in 1.0.0.

The major bump is what those compilation breaks require. Nothing in this release was made breaking in order to justify it.

### Change tracking and audit

- **Breaking, and the compiler does not catch it: `Update<T>` no longer writes the `[TCreatedAt]` and `[TCreatedBy]` columns.** They are set once, on `Insert`, and a normal update now leaves them alone: `TTUpdateSyntax` skips them in the `SET` list. Until now every mapped column was written on every update, the version column as `Version = Version + 1` and all the others from the entity, so a client that round-tripped an entity through JSON could rewrite who created a record and when. Applications that set a creation timestamp by hand on an existing entity and call `Update<T>` - a data import, a migration tool - no longer see that column written, and must go through raw SQL for that case
- **Breaking, and the compiler does not catch it: change tracking columns are no longer read from JSON.** Every entry point that deserializes - `EntityFromJSon`, `EntityFromJSonObject`, `ListFromJSon`, `ListFromJSonArray` and nested detail objects - skips `[TCreatedAt]`, `[TCreatedBy]`, `[TUpdatedAt]`, `[TUpdatedBy]`, `[TDeletedAt]` and `[TDeletedBy]`: those columns are the framework's to write, not the client's. `{"deletedAt": "..."}` in a `PUT` body no longer soft-deletes a row, and the delete endpoint with its `[TArea]` can no longer be bypassed that way
- **Breaking, and the compiler does not catch it: `Update<T>` no longer writes the `[TDeletedAt]` and `[TDeletedBy]` columns either.** All four of the delete and creation audit columns are now out of the `SET` list, and of the six audit columns only `[TUpdatedAt]` / `[TUpdatedBy]` are written by an update. They had to stay in while `Undelete` was implemented as an `Update<T>` that cleared them - excluding them would have turned it into a silent no-op - but `Undelete` now has a command and a `SET` list of its own, so the exception has nothing left to protect. `Delete<T>` and `Undelete<T>` are the only ways to move a row in or out of the deleted state, which is what the attribute pair meant in the first place. An entity with no `[TVersionColumn]` whose only non-key columns are creation or deletion audit columns now raises on `Update<T>`, as one whose only non-key columns were creation audit already did. With a version column the `SET` list is never empty, because the version is emitted as `V = V + 1` and is neither the key nor an audit column, so the raise is out of reach
- **The primary key and the version column stay readable from JSON**, also deliberately: `EntityFromJSonObject` builds a fresh entity, and `Update<T>` needs both to compose its `WHERE`. Excluding them would break every `PUT` written against the documented controller pattern
- **Breaking, and the compiler does not catch it: `[TDeletedBy]` without `[TDeletedAt]` is refused at mapping time**, with `SDeletedByWithoutDeletedAt`. It was a column that no path could write: `Delete<T>` decides between soft and hard delete on `[TDeletedAt]`, so it took the hard branch and dropped the row; `Update<T>` no longer writes the delete pair; and `Undelete<T>` raises on an entity without `[TDeletedAt]`. Mapped, read back, never written, and silent about it. The check joins the type checks that were already there, so the failure now arrives on the first `Load` of the entity instead of never. The creation and update pairs are unaffected: a lone `[TCreatedBy]` or `[TUpdatedBy]` is written normally
- **Breaking, and the compiler does not catch it: a column carrying two change tracking attributes is refused at mapping time**, with `SDuplicateChangeTrackingColumn`. The three pairs were validated one at a time, each for its own type and its own duplicate, and nothing compared them with one another: a `TTNullable<TDateTime>` field marked both `[TUpdatedAt]` and `[TDeletedAt]` was accepted, and the undelete `SET` list named that column twice - `Stamp = NULL, Stamp = :Stamp`, error 264 on SQL Server - with the two values contradicting each other. `Update<T>` also stopped writing it, silently, because it counts as a delete column. Nobody writes that mapping on purpose, which is exactly why it has to fail loudly at the first `Load` instead of at the first undelete
- **A `Currency` column no longer loses its decimals.** Two independent faults truncated the same value, and both had to go. The first: the metadata probe read a column's type and `Size` from the dataset's `FieldDef` and dropped `Precision`, and `SetParameters` copied that `Size` onto the parameter - but for the BCD family the decimal scale of a `TFDParam` travels on `NumericScale`, not on `Size`. `TTColumnMetadata` now carries `Precision` (a new constructor overload; the existing two are unchanged), the probe fills it, and `SetParameters` sets `Precision` and `NumericScale` for `ftBCD` and `ftFMTBcd` when the driver reports a precision - so a dialect that reports none behaves exactly as before
- **Breaking, and the compiler does not catch it: the second fault was PostgreSQL sending a `Currency` parameter as `money`, and the map rule that fixes it is read as well as written.** `TFDParam.SetAsCurrency` writes `ftCurrency` into the parameter directly, whatever type it was given beforehand, and the FireDAC PostgreSQL driver maps a currency parameter to `SQL_CASH`. `money` keeps the fraction digits of the server's `lc_monetary`, two in the common case, so an amount on its way into a `numeric(19,4)` column was rounded by the type it travelled in: `1234.5678` was stored as `1234.56` and `1000000.0001` as `1000000`, with no error and no warning. `TTPostgreSQLConnection.ConfigureMapRules` now declares `dtBCD` and `dtCurrency` interchangeable on the connection (`FormatOptions.OwnMapRules` with one `MapRules` entry, the same mechanism the Oracle driver already used for integers), so the parameter goes to the server as `numeric`. It covers every `Currency` parameter, a `WHERE` on an amount included, and on the read side it changes nothing for a `numeric(19,4)`, which is wider than what FireDAC classifies as BCD and is fetched as it was before. It does change a narrower one: the rule applies to the columns of a result too, so a `NUMERIC(p,s)` with `p - s` up to 14 and `s` up to 4 arrives as a `TCurrencyField`, whose buffer is a `Double`, and past about 9 * 10^11 its last decimals are lost - through `DatasetToJSon` and through an entity alike. SQL Server returns the same `DECIMAL(18,4)` as an exact BCD. A descendant of `TTPostgreSQLConnection` adds what it needs in `DoConfigureConnection`, and overrides `ConfigureMapRules` calling `inherited` if it has map rules of its own: `ConfigureConnection` is no longer virtual, which is the compilation break described below. Found by running the suite against PostgreSQL for the first time; the other six dialects hid both faults, having no money type on that path and either declaring a smaller precision or reporting a type that `Size` alone describes
- `TTColumnsMap` gained `IsCreatedChangeTracking`, `IsUpdatedChangeTracking`, `IsDeletedChangeTracking` and `IsChangeTracking`, so the question "is this column managed by change tracking?" is asked of the mapping instead of being re-derived

### ORM

- **Breaking, and the compiler does not catch it: `OrderByAsc` and `OrderByDesc` accept only mapped columns.** In 1.0.0 both put the string they were given into the `ORDER BY` as it was, and on the public master so did the `TTProperty` overloads: an expression such as `UPPER(Name)`, a `NULLS LAST`, a name the entity does not map or a name qualified by hand all reached the statement. Each item of the list is now checked against the metadata, a trailing `ASC` or `DESC` kept apart, and one that is not a mapped column raises `SColumnNotFound`. The clause is rebuilt from the resolved column names, so the name that reaches the statement is the one the check approved, which is what the HTTP filter already did, and each item takes the direction the method's own name states unless it carries one. Order by a mapped column - on a `[TJoin]` entity by its output alias `Alias_Column` - or put the expression in a `RawSelect`. No signature changes
- **A server-side filter on a `[TJoin]` entity produces valid SQL.** For an entity with joins the metadata are keyed by the **output alias** - `Customers_Name`, the name the select list gives the column - and the HTTP filter put that name straight into the `WHERE`. No engine resolves a select-list alias in a `WHERE`, so every filter on a join entity was invalid SQL; `ORDER BY` was fine, which is why the defect only showed on filters. `TTColumnMap` now carries a `SqlReference` alongside its alias - `Customers.Name` against `Customers_Name` - filled where the join aliases are resolved, `TTColumnMetadata` carries it through, and the filter emits it. It is the separation the expression API has had all along between the name that resolves the type and the reference that goes into the SQL. An entity without joins has nothing to qualify and its reference is the bare column, exactly as before
- **Breaking, and the compiler does not catch it: identifiers are quoted, on all seven engines.** `TTConnection.GetDatabaseObjectName` was `virtual` and returned its argument unchanged, and none of the seven connections overrode it: the hook existed and was empty, so every table, column, alias and sequence name went into the statement bare. That works only while the schema avoids each engine's reserved words - and they differ, so a column named `Value`, `Level` or `Position` is not uniformly safe. Each connection now quotes: `"` on PostgreSQL, Firebird, InterBase and Oracle, `[ ]` on SQL Server **and SQLite**, backticks on MariaDB, with a closing quote inside a name doubled so it cannot end the identifier early. **The name is folded to the engine's own default case first** - lower on PostgreSQL, upper on Oracle, Firebird and InterBase - because that is what an unquoted name already resolved to: `"customers"` on PostgreSQL names exactly the object `Customers` named before. Quoting without folding would have asked those four engines for objects that do not exist and broken every application on them, which is the reason the hook had stayed empty. **Nothing resolves differently after this change**; what changes is that a reserved word stops being a trap. The four places that emitted identifiers raw while their neighbours went through the hook - the table reference and the output alias in a join select list, the join alias and its source table - now go through it too, and so do the sequence names in the five dialects that name a sequence in SQL. PostgreSQL was the exception there and is covered by a later entry in this section: `nextval('name')` takes a string literal, which the engine already resolves with the same folding. SQLite takes brackets rather than quotes for a reason that only shows on that engine: a double-quoted word that resolves to no identifier is read by SQLite as a **string literal**, a compatibility rule the other six do not have, so a column an entity maps and the table does not have would have come back as that column's own name in every row instead of raising. Brackets are always identifiers there, so the refusal survives the quoting. A **qualified** name is quoted one part at a time, so `[TTable('dbo.Invoices')]` reaches SQL Server as `[dbo].[Invoices]` and keeps working. One host is not covered by *nothing resolves differently*, and it is the one that had the only way of reaching a reserved word before this release: **a name that already carries the quotes of the engine inside the attribute** - `[TColumn('[Order]')]`, `[TTable('"Clienti"')]` - is now quoted again, and the closing quote inside it is doubled, so `[TTable('"Clienti"')]` becomes `"""clienti"""`, which names nothing. On SQLite the bracket form is refused outright instead, because that engine has no escape for a `]`. Take the quotes out of the attribute: the framework puts them in. The same holds for an attribute that names something other than an identifier, such as a table-valued function in `[TTable('dbo.GetClienti(1)')]`: 1.0.0 put it into the statement as written, and it is now quoted as a name that reaches nothing
- **A PostgreSQL sequence whose name is a reserved word is reachable.** `NEXTVAL` takes its argument as a literal, which is right - `regclass` applies the same fold an identifier gets - but the parser behind `regclass` is the identifier parser, so `nextval('order')` is a syntax error where `nextval('"order"')` is not. The name is quoted inside the literal now. It was the one exception left to the sentence above.
- **A join alias longer than thirty bytes folds before it hashes.** `TTIdentifier.JoinAliasName` truncates and appends a hash when the alias does not fit the shortest limit of the seven, and it hashed the name in the case it was written while every lookup that consumes the alias compares without regard to case. Two spellings of one column produced two suffixes, and the one the query named was refused as an unknown column - only above thirty bytes, and never as wrong SQL, because both the fluent and the HTTP filter check the name before it reaches the engine.
- **A key or a `[TDeletedAt]` column is qualified by the table it declares, not by the table of the `FROM`.** Four places qualify a column when the entity has joins, and three of them composed the name of the `[TTable]` with the name of the column, ignoring the table the `[TColumn]` itself names. On an entity whose key is declared `[TColumn('Customers', 'ID')]` while its `[TTable]` is `Orders`, the `WHERE` read `Orders.ID` - a column that exists, so no engine complained: it was **the wrong row, silently**. All four now take the reference the mapping already resolved, which is `Table.Column` with joins and `Column` without, so the two branches collapse into one. The fourth is the `WHERE` that loads an eager detail list, and it is the one that had no qualification at all: it names a column of the **child** table, given as a string by `[TDetailColumn]`, so it looks that column up in the child's mapping and uses the reference it finds. When the child does not map it - which is allowed, and is what the cookbook shows - it falls back to the table of the `FROM`, which is the best guess available and the one it used to make unconditionally.
- **A Firebird or InterBase connection can declare its character set.** `RegisterConnection` built the connection parameters itself and there was no `CharacterSet` among them - the word appeared nowhere in the library - so a database created with `UTF8` or `UNICODE_FSS` was always opened with none, and the server did no transliteration: text travelled as raw bytes in both directions, and anything outside ASCII came back changed. A new overload takes the character set after the database name and FireDAC passes it as `lc_ctype`; `TTFireDACConnectionParameters` gained a `CharacterSet` for the multi-tenant path. It is **optional and defaults to the old behaviour**, because an application that has been writing raw bytes would read different data back the day it declared one
- **Breaking (compilation): `TTColumnsMetadata.Add` takes the SQL reference, and takes it once.** The four overloads of `Add`, and the four constructors of `TTColumnMetadata` behind them, are one of each now. The short forms filled `SqlReference` from `TTColumnMap.SqlReference` - the mapped name, qualified for a join entity and **never quoted**, because quoting is the connection's job and only the long form went through it. So anything that filled the metadata by hand got bare references in the filter builder, the `ORDER BY` and the lazy list, with no signal of any kind, which is the guarantee this release puts in a headline in the entry on quoting. The reference is now an argument you cannot forget. Since the signature was breaking anyway, the three type descriptors that always travel together became `TTColumnType`, so the call is four arguments instead of six: `Add(name, sqlReference, TTColumnType.Create(dataType, size, precision), columnMap)`. Nothing changes for code that **reads** metadata - `DataType`, `DataSize` and `Precision` are still properties of `TTColumnMetadata`. And nothing changes for a driver built on `TTGenericConnection`, which is every driver here and the shape the documentation describes: it inherits `ReadMetadata` and never calls `Add`. What this reaches is a connection derived straight from `TTConnection` that answers `GetMetadata` itself.
- **Breaking, and the compiler does not catch it: a column name that cannot become the name of a parameter is refused, instead of silently not being written.** `TTConnection.GetParameterName` replaced spaces with underscores and left everything else alone, but the parameter scanner of the driver reads only `0-9`, `a-z`, `A-Z`, `#`, `$`, `_` and Unicode letters: a `]`, a `"`, a backtick, a hyphen or a dot **ends the name there**. So `[TColumn('Cli]enti')]` on SQL Server built `INSERT INTO [Clienti] ([Cli]]enti]) VALUES (:Cli]enti)`, the driver read the parameter as `Cli`, the bind looked for `Cli]enti`, found nothing, and the value was never assigned. The `SELECT` worked and the `INSERT` did not - the column was readable and not writable, on all seven engines, and the same holds for the backtick on MariaDB and the double quote on PostgreSQL, Firebird, InterBase and Oracle. Such a name now raises, naming the column and the character. Refused rather than rewritten on purpose: folding every hostile character onto `_` would make `Cli]enti`, `Cli enti` and `Cli-enti` one parameter, and a collision writes one column's value into another column without a word. An accented name was never affected, and a space still becomes an underscore. The check runs where the metadata of the entity are built - see the entry on two columns that name one parameter - so the refusal comes at the first **read** too. Against 1.0.0 that is a change only where such a name used to be readable at all: on PostgreSQL and SQLite, whose unquoted identifiers take every character from U+0080 up, so `N°Fattura` or `Importo€` were read and never written - and MariaDB, which came after 1.0.0, did the same - and on SQL Server, which accepts `@` after the first character. A read-only entity on such a column worked in 1.0.0 and raises at its first `Select` now. Rename the column
- **On Oracle an identifier carrying a double quote is refused, not doubled.** Oracle states that no identifier, quoted or not, may contain a double quotation mark, so there is nothing to escape one with: the shared doubling produced `SELECT "CLI""ENTI"`, which the parser reads as the identifier `CLI` followed by `"ENTI"` - a syntax error, and on another shape of name a different object. `TTOracleConnection.GetDatabaseObjectName` now raises, the way `TTSQLiteConnection` already did for a `]` inside `[ ]`. PostgreSQL, Firebird and InterBase document the doubling as valid and keep it. The message that reports the refusal names the character and the engine now, so it reads correctly for both.
- **Breaking, and the compiler does not catch it: the quoting reaches the filters and the lazy lists too, and `IsNull` checks the name.** `GetDatabaseObjectName` is applied where a statement is built, and three places build one somewhere else: the `WHERE` and the `ORDER BY` a `TTFilterBuilder<T>` composes, the `ORDER BY` of the server-side HTTP filter, and the foreign key condition `TTLazyList<T>` writes into its own filter. All of them emitted the column bare, so on a column named `Level` or `Order` the select list was quoted and the clause beside it was a syntax error. The reference `TTColumnMetadata` carries is now the one the connection has quoted - `ReadMetadata` folds and quotes each column as it reads it, which is the same rule the rest of the driver follows - and those places emit that reference instead of the name. The **parameter** keeps the plain column name: it names the entity's column, not an identifier in the statement. Two consequences worth knowing: on a `[TJoin]` entity the fluent string form now qualifies as well, so `Where('Customers_Name')` reaches the engine as `"Customers"."Name"` instead of an output alias no engine resolves in a `WHERE`; and the expression API is closed for `ORDER BY`, which goes through the metadata now, while its `WHERE` text is still built by `TTProperty` itself and stays unquoted. That last one is the only path left where an identifier reaches the engine bare. **A third consequence, and the compiler does not catch it**: `IsNull` and `IsNotNull` were the only two operators of the builder that did not check the column name. Every other one has raised `SColumnNotFound` since 1.0.0, through the lookup `AppendParameter` does to type the parameter; these two took no parameter and emitted whatever name they were given, straight into the `WHERE`. They go through the same lookup now, so `.Where('DeletedAt').IsNull` on an entity that does **not** map `DeletedAt` raises where it used to build a clause the engine accepted. Map the column, or write that `WHERE` with `TTFilter.Create`. The expression API had the same hole and is closed the same way: `TTProperty.IsNull`, `IsNotNull` and an empty `InValues` built an expression with no parameter, and the builder checked a column only while binding a parameter, so the name was never looked at - and an empty `InValues` does not even emit it. `TTExpression` now carries the names of the columns it refers to, in the new `ColumnNames` property, through `and`, `or` and `not`, and the builder checks every one of them before it adds the condition. The two-argument `TTExpression.Create` is still there; a new overload takes the names as a third argument. An expression built with the two-argument form carries no names and is checked only through its parameters: a host that composes expressions of its own keeps the check by passing the names on, or by propagating `ColumnNames`. **On a `[TJoin]` entity the name checked is the output alias `Alias_Column`**, for the columns of the `FROM` table as well, because that is the key of the metadata. So two forms that used to pass now raise: the one-argument `TTProperty.Create('ShippedAt').IsNull`, even on a mapped column, and `TTProperty.Create('Customers', 'DeletedAt').IsNull` on a column the entity does not map - an anti-join, or the soft delete of the joined table. Name a mapped column with `TTProperty.Create(Alias, Column)`, or write that `WHERE` with `TTFilter.Create`
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): a detail collection whose child entity maps a `[TJoin]` raises on its first read.** On the public master the lazy list loaded with `WHERE <column> = <id>`, the column name as `[TDetailColumn]` wrote it and unqualified: on a join entity that is valid SQL when the name belongs to one of the joined tables only, and the list loaded; it failed only when the name was ambiguous. Now `TTLazyList<T>` raises `SDetailColumnOnJoinEntity` as soon as the child entity maps a `[TJoin]`, ambiguous or not: a join entity keys its metadata on the output alias of each column, so the name the attribute carries cannot be resolved and quoted there. **What changes for an application**: a detail collection on a join entity that used to load now raises - map the detail on an entity without `[TJoin]`, or read the rows with `Select<T>` and a filter
- **A detail column the child entity does not map is quoted from the attribute, not left bare.** `TTLazyList<T>.SqlReference` looks the name up in the metadata of the child entity, and those carry mapped columns only. Nothing obliges a detail entity to map the key `[TDetailColumn]` names - the example in the cookbook does not - and when the lookup missed, the name went into the `WHERE` exactly as written: on a column called `Order`, or one with a space in it, a syntax error on all seven engines. The fallback now quotes the name through the connection, with the same fold a mapped column gets, so the shape the documentation shows keeps working and nothing leaves this path bare. `TTContext` gained `GetDatabaseObjectName` along the way, which is what the lazy list asks and is worth having when you write the SQL of a `RawSelect` by hand.
- **An `ORDER BY` is opened only when there is something to put in it.** `TTSelectSyntax.GetOrderBy` appended `ORDER BY` unconditionally and then filled it from the filter, or from the primary key, or from neither. An entity with no `[TPrimaryKey]` queried without an explicit order would therefore produce `SELECT ... FROM T ORDER BY` with nothing after it, which is a syntax error on all seven engines. It was not reachable through the public API - `TTTableMetadata.Create` refuses an entity with no primary key before any SQL is built, with the message this project has for that case - so this is a guard, not a bug fix: the shape only had to become reachable once, through a caller building a syntax object of its own, to emit an empty clause. The clause is now built first and prefixed only when there is something to prefix
- **SQLite refuses a name it cannot quote instead of naming another object.** The quoting code doubles the closing quote inside a name so it cannot end the identifier early, which is the documented escape on SQL Server and on every engine using `"`. **SQLite has no escape for a `]` inside `[ ]`**: the identifier ends at the first bracket and what follows it is read as SQL, so a doubled one produced a different object silently. The brackets stay - a double-quoted word that resolves to nothing is a string literal on that engine, which is worse - and a name carrying a `]` is now refused with a message that says why. It affects SQLite alone
- **A text LOB is written as a text LOB, and on Oracle it is written at all.** Oracle reports a `CLOB` as `ftOraClob`, and that type was not registered among the string parameters - `ftOraBlob` was registered among the binary ones two lines below, so the asymmetry was invisible. A `CLOB` column therefore did not reach the parameter class at all: it was refused outright with *parameter not registered*, which means **no entity mapping a `CLOB` could be written on Oracle**. No test in the suite declared a text LOB on any engine, so nothing had ever asked. On the six engines that do report a memo type, the second half of the defect applies: `SetParameters` declares every parameter with the type the metadata report - `ftMemo` or `ftWideMemo` for a `CLOB`, a `TEXT`, a `LONGTEXT`, an `nvarchar(max)` or a `BLOB SUB_TYPE TEXT` - and then `TTStringParameter` wrote the value with `AsString`. `TFDParam.SetAsStrings` keeps the declared type only when it is already one of `ftString`, `ftFixedChar`, `ftWideString`, `ftFixedWideChar`, so a memo was rewritten to `ftString` and the value left as an ordinary string. PostgreSQL, MariaDB and SQL Server take a long string bind anyway; **Oracle does not** - a `VARCHAR2` bind stops at 4000 bytes. The type cannot be put back after the write, because `TFDParam.SetDataType` clears the value when the type changes, so the value now goes through `TFDParam.Text`, which assigns without touching the declared type. `TTParam` gained `AsText` for it, `virtual` **with a body that calls `SetAsString`**, so a driver outside this repository that does not override it behaves exactly as it did - unlike the three abstracts listed above. `AllTypes` gained a `Notes` text LOB on all seven dialects and a round trip of 8000 characters through it, which is the first test of this shape in the suite
- **The expression API cuts a long join alias the way the mapping does.** `TTTableMap` shortens an output alias longer than 30 bytes in UTF-8 - the shortest identifier limit of the seven engines, Oracle before 12.2 - and replaces the tail with a hash, so the column the select list produces is the short one. `TTProperty.Create(alias, column)` built the whole name instead, so above that length it named a column the metadata does not have: `CheckColumn` refused it and the expression API stopped working on that entity, on all seven. Both now go through the same function, which moved to `TTIdentifier.JoinAliasName` in `Trysil.Classes` so that `Trysil.Filter.Expression` can reach it without taking a dependency on the mapping
- **Folding a name no longer follows the language of the machine.** `TStringHelper.ToUpper` and `ToLower` without an argument are the **linguistic** case of `SysLocale.DefaultLCID`, not an invariant fold: on a machine set to Turkish or Azeri, `I` lowercases to the dotless `ı` and `i` uppercases to `İ`. Trysil folds a name before quoting it on the four engines that fold - Oracle, Firebird, InterBase, PostgreSQL - so `[TColumn('CodiceID')]` reached Firebird as `"CODİCEİD"`, an object that does not exist, and `ID` reached PostgreSQL as `"ıd"`. Every statement on those four engines, on every entity carrying an `i` in a name. The same reading applied to the comparisons that match a mapped column against the metadata the database returned: `String.Compare(a, b, True)` is locale-aware too, so `ID` and `id` stopped being the same name and the column of the entity was not found. Every fold and every comparison Trysil writes on an **identifier** is now invariant, through a new `TTIdentifier.Same` in `Trysil.Classes`. The sweep went further than the comparisons, because the fold is the other half of the same fault, and because one thing reads as invariant and is not: `TIStringComparer.Ordinal`, which in spite of its name the RTL implements with `AnsiSameText` and a hash over `AnsiLowerCase`. Both dictionaries that used it - the column lookup of `TTColumnsMap` and the header dictionary of `TTHttpHeaders` - are keyed on `TTIdentifier.Comparer` now, which compares the way `Same` does and **hashes what it compares**. Be exact about why, because the obvious story is not the true one and an earlier draft of this entry told it: measured on the Win32 primitives with the Turkish locale passed explicitly, `CompareStringW` with `NORM_IGNORECASE` calls `ID` and `id` equal, and the non-linguistic lower-casing of `ID` is `id`. For an **ASCII** identifier those two dictionaries were therefore not misbehaving on Windows, and no test can show them doing so. What was wrong is the dependency itself - a comparer whose name says ordinal has no business reaching for the locale - and the single RTL primitive that really does fold an ASCII identifier differently under Turkish is `TStringHelper.ToUpper`/`ToLower` with no argument, which is what the rest of this entry is about. And every remaining `ToLower` on an identifier is invariant: the name of a tenant, which decides which database is opened and which was folded and then validated against ASCII, so a tenant called `Italia` could not be created at all on a Turkish machine; the uri of a route, on both the side that registers it and the side that receives it, where the two folds had to agree or a registered route answered `404`; the areas of `[TArea]`, where they had to agree or an authorized user got `403`; the names in the driver and connection registries; the host in the log; and the scheme of an `Authorization` header, where `BASIC` is legal by RFC and stopped being accepted. The parameter lookup on a SQL Server connection string went the same way, because `TStrings.IndexOfName` compares with the locale unless told otherwise. The same fault reached three more places that turn a token into text: JSON property names and the `type` of `MetadataToJSon<T>` (`ID` went out as `ıd`, `ftInteger` as `ınteger`), the type-name test that decides whether a value is a `TDateTime` (`tdatetıme` matches nothing, so **every date went out as a plain string** under that locale), the Sqids alphabet, the HTTP method name derived from the command type (`OPTİONS`), and the keys of a Digest `Authorization` header (`urı`). The registries that lower-case a name to key a dictionary are left alone: they fold both sides in the same process, so they were never inconsistent with themselves
- **Six more comparisons that decide an identity are invariant now.** The sweep above closed every fold and every comparison on a **column** name, and left the ones that decide an identity of another kind: the key of the SQLite sequence cache, where two spellings of one table became two counters; the keyword test on a SQL Server connection string, and `TrustServerCertificate` carries an `i`; the two type-name tests in `TTRtti.IsSameType`, which decide dispatch when the library is loaded as packages, and `TDateTime` carries one too; the charset test on a request; and the `LIKE` and `NOT LIKE` tokens of the server-side filter, where a client sending `like` in lower case was answered `400` on a Turkish machine and on no other. All of them ask `TTIdentifier.Same` now.
- **The translation table finds what its own comparer calls equal.** `TTLanguageValueEqualityComparer` compares the language and the key without regard to case, and hashed them in the case it was given: `it` and `IT` were equal and never landed in the same bucket, so a client sending `Accept-Language: IT` fell through to the untranslated key. The hash folds the pair the way the comparison does.

- **The check that refuses a string longer than its column is a ceiling, and the documentation now says so.** It reads the width the driver reports, and what that width counts is the engine's business: characters on most of them, bytes on InterBase and Firebird with a Unicode character set, where a `VARCHAR(100)` is 400 bytes and the engine enforces the bytes. So on those a 150-character value is accepted, by the engine and by the check alike. It is never a false positive, since a character is never smaller than a byte, and it is not a substitute for `[TMaxLength]` - which is what states, in characters and on every engine, the length the application accepts. Written up in `docs/guide/validation.md`
- **Breaking, and the compiler does not catch it: `Save<T>` and `SaveAll<T>` are refused on a `TTHttpContext`.** `Save` decides between an insert and an update from what the context created and has not written yet, and a context the listener builds and destroys inside one request has no such history: the entity was filled from the body, key included. Whether a request creates or updates is in the request, and the controller is what says so - which is why the REST example has always used `Insert<T>` and `Update<T>` and never `Save<T>`. The refusal is a virtual `CheckSave` on `TTContext` overridden in `TTHttpContext`, so it holds however the object is reached, including through a `TTContext` reference. `TTJSonContext` is unaffected: it is an ordinary context with JSON attached, and its lifetime is the host's business
- **Breaking, not counted because the code it hits could not work: `TTNewEntityCache` identifies entities by instance.** It keyed them by `(TypeInfo, primary key)`, read at the moment of the call, which broke in two ways. A key that changed after `Add` left the cache pointing at a value nobody holds. And in the JSON path `CreateEntity<T>` runs while loading, so the key is not assigned and stays zero: **every** deserialized entity of a type registered under the same key `0`, and removing one cleared the flag for all of them. The cache is now a set of object references, and `CreateEntity<T>` registers only when it is **not** loading - an entity whose state came from outside is not one the context gave an identity to. Entities leave the set when they are disposed, through the `FreeEntity<T>` and `TTObjectList<T>.OnDisposeItem` path the transaction rewind already used
- **Breaking (compilation): `TTNewEntityCache` has a different constructor and three methods that are no longer generic.** It is a public class in `Trysil.Provider`: `Create(AProvider)` is now `Create`, and `Add<T>`, `Contains<T>` and `Remove<T>` take the entity as a `TObject`. Neither `TTContext` nor `TTProvider` handed one out in 1.0.0, so this reaches only code that built a cache of its own
- **Breaking, and the compiler does not catch it: `Insert<T>` refuses an entity whose primary key is zero.** Nothing assigns a key on the way in - `CreateEntity<T>` takes one from the sequence, and that is the only place - so an entity that reached `Insert` with zero had never been given an identity, and the row went in with `ID = 0`, silently, ready to collide with the next one. It is unreachable from the direct application; it is the JSON path, where the body may carry no key and the controller has to call `SetSequenceID<T>`, as the REST example does. The message says exactly that
- **Breaking, and the compiler does not catch it: a foreign key written by the JSON deserializer drops the entity the lazy member had loaded.** `TTJSonDeserializer` writes the key of a `TTLazy<T>` through `TTRttiLazy`, which set the **field** `FID` by RTTI and so walked past the property setter - the one that clears the cached entity and hands it to the context. The key moved and the instance stayed, so on an entity deserialized **over** one already read - through `TTJSonDeserializer.EntityFromJSon`, public since 1.0.0, or the `EntityFromJSon<T>` and `EntityFromJSonObject<T>` overloads that take an entity, new in this release - the relation went on answering with the old master while its id said another, and a key pointing at a row that is not there passed `[TRequired]` because the validation asks the loaded instance. `TTRttiLazy` writes through the property now, like `TTRttiMember.SetID` and `CloneLazyID` already did: the cached entity is released through `FreeEntity<T>` and the relation reloads on the next read. **What changes for an application**: a reference kept to the previous master across a deserialization is freed, on a context without an identity map - which a JSON or HTTP context never has - exactly as it is when you assign the id yourself. The defect is as old as 1.0.0. On a fresh entity nothing changes: the lazy member has loaded nothing when its key is written
- **Breaking, and the compiler does not catch it: `[TRequired]` on a lazy relation accepts a master that was soft-deleted.** In 1.0.0 `TTLazy<T>.GetEntity` loaded with `Get<T>(FID)`, which carries `DeletedAt IS NULL`, so a key pointing at an archived row failed validation and the row could not be saved at all - which also meant that archiving a master froze every record that pointed at it: no `Update<T>` on those passed again until it came back. A lazy member loads with `Get<T>(FID, True)` since this release, deliberately, so the relation validates and those records go on being saved. If your domain wants the refusal, write it in a `[TValidator]`, where you can tell a key just assigned from one that has been there for years - the attribute cannot.
- **Breaking, and the compiler does not catch it: `[TRequired]` on a lazy relation says which of the two things is wrong.** It reached `TTRttiLazy.ObjectValue`, which is `TTLazy<T>.Entity`, which is a `SELECT`, and built one predicate out of two questions: a key that was never set and a key pointing at a row that is not there both failed with *cannot be empty*, true of the first and misleading for the second. The two are told apart now. An unset key keeps `SRequiredValidation`; a key whose row does not load fails with the new `SRequiredRelationValidation`, *refers to a row that does not exist* - and a row that is **soft-deleted is not** one of those, and the difference is worth reading: a lazy member loads with `Get<T>(ID, True)`, so unlike every other `SELECT` it returns an archived master, on purpose - an order has to be able to show the name of a customer that was archived - and the validation accepts what the lazy member hands it. In 1.0.0 the same attribute refused it, because there `GetEntity` loaded without the deleted ones: that is the one behaviour this entry does **not** restore, and it is counted below. Whether a row that was archived may be pointed at is a question about your data, not about the mapping: `[TValidator]` is where it belongs, with the entity and the context in hand. **The rest of the check is unchanged**: the attribute asks the database, as it did in 1.0.0, and costs the one `SELECT` it always cost, only for a relation that carries the attribute and only when the key is set. A language unit of your own needs one more line for the new resourcestring; the two in `Demos/Languages` have it
- **Breaking, and the compiler does not catch it: `Refresh<T>` raises when the row is no longer there.** It ran the select and then `if not LReader.IsEmpty then MapEntity(...)`, so a row deleted under the caller left the entity exactly as it was, with nothing said: the caller went on working on a record that does not exist, believing it had just re-read it. It now raises `ETConcurrentUpdateException` with `SRecordChanged`, whose text already reads "modified by another user, or no longer available". The new `TryRefresh<T>` on `TTContext` and `TTProvider` is the same question asked without an exception, next to `TryGet<T>`. **What changes without a compiler error:** a `Refresh` on a deleted row now stops the operation instead of passing
- **Breaking, and the compiler does not catch it: `OldEntity<T>` returns `nil` when there is no old row.** It is a clone plus a refresh, so with the refresh silent it handed back a copy of the **in-memory** state as the state of the database - and in an insert event it was not `nil` but a clone of the entity being inserted. It goes through `TryRefresh` now and frees the clone when the row is not there, so `nil` means what it says. Event code that dereferences it must check
- **Breaking, and the compiler does not catch it: `OldEntity` read for the first time after the command is refused.** It is memoized on first access, and `DoBefore` and `DoAfter` run on the two sides of the write: an event that first touched it in `DoAfter` was handed the row the command had just written, under the name of the old one. `TTEvent` gained `CommandExecuted`, called by the command between the SQL and `DoAfter`, and a first read after that point raises `SOldEntityAfterCommand` instead of answering with the new row. Reading it in `DoBefore` and using it in `DoAfter` works as before, because the value is kept
- **Breaking, and the compiler does not catch it: four mappings that cannot mean anything are now refused.** The mapper rejected duplicates early and let contradictions through. A column marked both `[TPrimaryKey]` and `[TVersionColumn]` is refused (`SPrimaryKeyIsVersionColumn`): the update it produces reads `SET ID = ID + 1 WHERE ID = :ID`, moving the key of the row it is identifying by. A primary key or version column that also carries a change tracking attribute is refused (`SKeyColumnWithChangeTracking`): the duplicate check compared the six tracking slots with one another and never with those two, so a key the framework then overwrote on every insert was accepted. A member carrying both `[TColumn]` and `[TDetailColumn]` is refused (`SColumnAndDetailColumn`): one maps a value of this row and the other a collection of another table, and which of the two won depended on the order the attributes were written in. `TTColumnsMap.ChangeTrackingColumns` is the list the two tracking checks now share
- **Breaking, not counted because the code it hits could not work: an entity that cannot be queried is refused when its metadata is built.** `TTTableMetadata.Create` read `ATableMap.PrimaryKey.Name` with no test, so an entity without `[TPrimaryKey]` reached `Select` or `Get` as an access violation - while `TTProvider.GetPrimaryKey` had a clean message for the same case. It now raises that same `SNotDefinedPrimaryKey`, and checks two more things while it is there: an entity with no `[TTable]` (`SNotValidTableName`, which would have produced `FROM ` and a driver error) and an entity mapping no column at all (`SNoMappedColumns` - `TTColumnsMap.Empty` existed and nothing ever asked it). **DTOs are unaffected**: `RawSelect<T>` loads the table map but never builds table metadata, so a class with only `[TColumn]` attributes stays valid, which is what the documentation promises
- **A filter on an empty list of values is "nothing", not a syntax error.** `TTProperty.InValues` with an empty array emitted `IN ()`, which no dialect accepts, and an application filter that resolves to zero ids produces exactly that. It now emits `(1 = 0)` and binds no parameter, which is what "in the empty set" means
- **Breaking, and the compiler does not catch it: `OrderByDesc` makes every column of the list descending.** It appended the suffix to the whole string, so `OrderByDesc('Code, Quantity')` produced `Code, Quantity DESC` - the first column came back ascending, with nothing to say so. Each column now carries its own `DESC`. `OrderByAsc` is unaffected, having no suffix to place
- **A filter built with `TTFilterBuilder<T>` no longer loses the `TGuid` and `Currency` conversions.** `AppendParameter` created the parameter through the four-argument overload, which forces `IsGuid` and `IsCurrency` to `False`, and `Build` copied it through the four-argument one again. The same condition therefore bound an amount as a plain number when it came from the builder and as money when it came from the HTTP filter, which reads both flags off the column metadata. Both now carry them, so the fluent API and the expression API - which goes through the same method - behave like the HTTP path
- **The "column not found" message reaches the caller with the column name in it.** `TTFilterBuilder<T>.CheckColumn` raised `STableMapNotFound` through `Create` after translating it, so the `%0:s` inside was shown verbatim, and raised `SColumnNotFound` through `CreateFmt` **without** translating it, so that one was never localized. Both go through translate-then-format now, and the first names the entity class
- **A failed event resolution is no longer remembered.** `TTEventFactory.SearchMethod` cached the result of the constructor search even when nothing matched, and the search depends on the runtime types of the context and the entity: an event class whose constructor takes a `TTJSonContext`, first reached from a plain `TTContext`, was written into the cache as unresolvable and stayed that way for the life of the process. Only a resolved method is cached now; a failed search costs a second search, on a path that raises anyway
- **A transaction that cannot close during destruction says so in the log.** `TTTransaction.Stop` swallowed the exception whole - correctly, since a destructor is not a place to raise from, but silently, so a commit that failed on the `CommitOnDestroy` path left no trace anywhere. It is now logged as an error with the exception class and message, through the new `TTLogger.LogError(AConnectionID, AMessage)`, which also makes the `TTLoggerEvent.Error` entry reachable from outside the logger for the first time. `ConnectionID` moved up to `TTConnection` as a virtual getter returning an empty string, overridden by `TTGenericConnection` to return the id it already had, so the log line carries the correlation id for every driver in this repository and a driver deriving straight from `TTConnection` keeps compiling
- **Breaking at runtime, not at compile time: a custom `TTGenericConnection` driver must implement three new methods.** The transaction methods were restructured so that the observer is notified around the physical operation instead of before it, and the physical part moved into `InternalStartTransaction`, `InternalCommitTransaction` and `InternalRollbackTransaction`, three `strict protected virtual abstract` methods. A driver living outside this repository - the base class is documented for exactly that - **still compiles**: an unimplemented abstract is `W1020` where the driver is constructed and `EAbstractError` at the first transaction, in production. Worse and quieter: a driver that overrode `CommitTransaction` (which is what the FireDAC driver did until this release) keeps compiling and keeps being called, never reaches the new `Internal*`, and therefore never notifies the observer, so the new-entity cache is never reconciled and nothing warns you. Migration: move the body of your `StartTransaction` / `CommitTransaction` / `RollbackTransaction` override into the matching `Internal*` method and drop the override
- **Breaking, and the compiler does not catch it: an `UPDATE` no longer reaches a soft-deleted row.** `TTUpdateSyntax` now adds `DeletedAt IS NULL` to the `WHERE` clause, so a row that was soft deleted cannot be modified through that entity: not resurrected, and not edited while deleted. The guard comes from the mapping, not from the table, so a second class mapped on the same table without `[TDeletedAt]` still reaches the row - it cannot resurrect it, since the column is not in its `SET` list either, but it can edit it. A lightweight entity on the same table for lists and lookups is a normal pattern, and using it to write walks past the guard. The hole was reachable from any `PUT` written against the documented controller pattern - the deserializer builds a fresh entity, whose `DeletedAt` is null because a body is not allowed to carry it, and the `SET` list wrote that null back over the row. Optimistic locking hid the common case, since a soft delete increments the version and a client holding the pre-delete version was already refused; what got through was a client that read the row **after** the delete, with `IncludeDeleted`: it then carried the post-delete version, the `WHERE` matched, and the version is deserialized from the body like any other non-audit column. The test added with this change uses an entity that does have a `[TVersionColumn]`. **Against 1.0.0** this breaks a host that read a deleted row with `IncludeDeleted` and wrote it back with `Update<T>` - the only way to bring a row back before `Undelete<T>` existed: the `UPDATE` matches nothing and raises `ETConcurrentUpdateException`. Use `Undelete<T>`. `SRecordChanged` is reworded to "modified by another user, or no longer available": zero rows affected now means a version that moved **or** a row that is gone, and the old text was only true of the first. That resourcestring is also the key `TTLanguage.Add` looks up, so a translation table keyed on the old English text loses the entry and falls back to English, silently: the two tables under `Demos/Languages` are updated here, one kept outside this repository needs the same edit
- **Breaking at runtime for a driver of your own (on the public master, not in 1.0.0): `Undelete` goes through `TTConnection.CreateUndeleteCommand`.** `Undelete` is the one operation that must reach a deleted row, so it no longer goes through `Update<T>`: `TTSyntaxClasses.Undelete` returns a `TTUpdateSyntax` descendant without the guard, `TTConnection.CreateUndeleteCommand` builds the matching command, and `TTResolver.Undelete<T>` uses it. **Breaking at runtime, not at compile time:** that method is `virtual` with a body that raises, not `abstract`, so a driver living outside this repository keeps compiling - but one deriving straight from `TTConnection` had a working `Undelete` before, because it went through `CreateUpdateCommand`, and now raises on the first `Undelete<T>`.
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): `Undelete<T>` writes only what it restores.** `Undelete` stopped rewriting the whole row on its way back: its `SET` list is now the version increment, `DeletedAt = NULL`, `DeletedBy = ''` and the `[TUpdatedAt]` / `[TUpdatedBy]` pair, nothing else. Every other `UPDATE` in Trysil writes every column, so an entity carrying an unrelated edit - a name changed in the form, a stale field - used to have that edit written to the database as a side effect of undeleting. Code that relied on it - a screen that loads a deleted row, corrects it and restores it with one call - now brings the row back without the correction, and nothing says so: call `Update<T>` after `Undelete<T>` when the entity carries changes
- **Breaking, and the compiler does not catch it: a second `Delete<T>` no longer overwrites the audit of the first.** `TTSoftDeleteSyntax` builds its `WHERE` from the key and the version only, so an entity loaded with `IncludeDeleted` - which carries the post-delete version, hence a `WHERE` that matches - could be soft deleted again, and the second delete rewrote `DeletedAt` and `DeletedBy` with the current time and user. Who deleted the row, and when, was lost, in the release that made audit its subject. The guard that the `UPDATE` gained moved up to `TTCommandSyntax` and the soft delete now carries it too, so the second delete matches nothing and raises `SRecordChanged`, which the HTTP layer answers as `409`. **What changes for an application:** a `Delete<T>` or a `DeleteAll<T>` over a list that already contains a deleted row used to pass silently and now raises. It was never reachable through `TTHttpContext.Delete<T>(AID, AVersionID)`, whose `Get<T>` excludes deleted rows
- **`TrustServerCertificate` no longer throws away the host's `ODBCAdvanced`.** That keyword has no connection def parameter of its own - it appears in no FireDAC source file, on 22.0 or on 37.0 - so the only channel to the driver is `ODBCAdvanced`, and Trysil writes it there whenever the tri-state is not `DriverDefault`. But FireDAC reads the driver-wide `ODBCAdvanced` **only when the per-connection one is empty**: it is a replacement, not a merge. So writing ours silently discarded whatever the host had put in `TTSqlServerConnection.Driver.ODBCAdvanced` - the very property the entry above offers as the way out of the `Encrypt` break. The value is now merged rather than replaced: when there is no per-connection parameter, the driver-wide one seeds it. Three more faults in the same place went with it. The keyword is now matched **as a keyword** - split on `;`, compared before the `=`, case-insensitively - instead of as a substring, so a host value spelled `trustservercertificate=yes` is recognised as the same setting and no longer earns a second copy. When the keyword is already there, from the host parameters or from the driver-wide value, Trysil leaves it alone: an explicit choice by the host wins, which is what `Encrypt` already did and what `TrustServerCertificate` did the opposite of, appending and leaving the winner to the ODBC driver. And a trailing `;` in the host value no longer produces an empty element in the connection string. `TTSqlServerParams.AddExtraParameters` keeps its signature; the tests are in `Trysil.Tests.SqlServer.Params` and assert on the parameter list, so they need no server
- **Breaking, not counted because the code it hits could not work: the identity map no longer frees an entity it has handed out.** `TTEntityIdentityMap.Add` on the public master used to `Remove` the previous instance before adding the new one, and the dictionary owns its values: the object it destroyed was one the caller could still be holding. In 1.0.0 the second instance was ignored instead, so nothing was freed and the map kept the first - wrong in the other direction, and just as silent. The read path never reached it - `TTProvider.InternalCreateEntity` looks the key up first and reuses the instance it finds - so the only way in was two **new** entities landing on the same key, and the map picked the loser without being able to know which one the caller had. `TTIdentityMap.AddEntity<T>` now raises `SDuplicateEntityIdentity`, naming the class and the key, and `TTEntityIdentityMap.Add` can no longer destroy anything: it adds when the key is free and leaves it alone otherwise. Two instances claiming one identity in one context is an error, and the map is not the place to resolve it silently
- **Breaking, and the compiler does not catch it: a string longer than its column raises instead of being cut.** `TTStringParameter` trimmed the value to the size of the column and then **wrote the trimmed value back into the entity**, so an application that handed Trysil a 120-character name for a `VARCHAR(100)` got 100 characters in the database *and* in its own object, with no exception, no log line and no way to find out afterwards what it had asked for. On a filter the same cut was applied to the search value, which quietly turned an equality into a match on a prefix. It now raises, naming the column, the size it holds and the length it was given. The message uses `[TDisplayName]` when the column has one and falls back to the column name otherwise, exactly as validation messages do - so what a client can learn from it is what it could already learn from a `422`. **What changes for an application:** a value that used to be silently shortened now stops the write. `[TMaxLength]` is the way to catch it earlier and more kindly, as a validation error listing every offending field at once rather than an exception on the first one
- **An `Int64` on a decimal column is written as a whole number, not through a `Double`.** The class that binds a parameter is picked from the **column** type, so a member declared `Int64` mapped onto `DECIMAL` or `NUMERIC` - `NUMERIC(18,0)` on InterBase, `NUMBER(19)` on Oracle - landed in `TTDoubleParameter`, which did `AsType<Double>` and bound `AsDouble`. Above 2^53 a `Double` cannot tell two consecutive integers apart, so the value written was not the value given, with no error and no log line to say so. The read side never had the problem: `TTColumnFactory.CreateColumn` consults the **mapping** first - `IsInteger`, `IsInt64`, `IsCurrency` - and only then the field type, so the same column came back through `TTLargeIntegerColumn`. Writing is now symmetrical: when the mapping says `Int64`, `TTDoubleParameter` binds `AsLargeInt`, nullable included, and a filter value that arrives as `Int64` does the same. Nothing else moves - the class chosen by the factory is unchanged, deliberately, because that is the mechanism the `Currency`-as-`money` defect came through
- **SQLite reads its next key from the primary key column, and does not hand out the same one twice.** `GetSequenceSyntax` was `SELECT IFNULL(MAX(ROWID), 0) + 1`, which is wrong twice over. First, `ROWID` is not the key: a column is an alias for it only when declared exactly `INTEGER PRIMARY KEY` on its own line, and a table written as `ID INT NOT NULL, ... PRIMARY KEY(ID)` - the form the documentation and the test fixtures use - keeps two separate counters. They march together on a table that is only ever appended to, which is why nobody noticed; delete the last row, and SQLite reuses that `ROWID` while `MAX(ID)` does not move. The statement now reads `MAX(<primary key>)`. Second, it is not a sequence: it looks at the rows that are there, so it returns the same number until you insert, and `CreateEntity` called twice before an `Insert` produced two entities sharing a key - which is what the entry above now refuses. `TTSQLiteConnection` therefore keeps, per database and per table, the last key it handed out: it still asks the database every time and takes that answer when it is ahead, and falls back to its own counter when it is not. Keys never go backwards, so a `DELETE FROM` does not make them repeat. The counter lives in the process: two **processes** writing the same file can still collide, exactly as they could before, because the read has never been inside the insert's transaction - SQLite allows one writer at a time and is not the tool for that shape
- **The connection pool cannot be resurrected during shutdown.** `TTFireDACConnectionPool.Instance` is the one singleton in the library with a getter that builds on demand under a lock, and the class destructor now clears the field: between that and the moment it frees the lock, a thread still running would have found `nil`, built a second pool, and opened a `TFDManager` that nothing would ever free - and a moment later `Instance` would have been `TMonitor.Enter(nil)`. The concrete path is a server that was never stopped with an Indy thread registering a tenant while the units finalize. The class remembers that it has been destroyed and raises `SInstanceDestroyed`, naming itself, before touching the lock
- **Breaking, and the compiler does not catch it: a rolled back transaction rewinds the entities, not only the rows, so an entity is freed with `FreeEntity<T>`.** Trysil writes to the entity as it writes to the database: `Insert` resets the version and stamps the creation audit, `Update` and `Undelete` stamp the update audit and increment the version, `Undelete` also clears the delete audit, a soft `Delete` stamps the delete audit and increments the version. All of it happened around the command and none of it was reversible, so a unit of work that failed left the objects describing a state the database never reached. The batch case is the one that bites: `ApplyAll` calls `Update<T>` one entity at a time inside a single transaction, so when the fifth raises, the four that succeeded are already at `VersionID + 1` in memory while the rollback puts their rows back at `VersionID`. From then on **every** `Update` on those four answers `409` for ever, silently, until someone calls `Refresh<T>`. The single-write case is quieter but has the same shape: the update audit is stamped on the entity **before** the command runs, so a failed `Update` left an `UpdatedAt` that no row carries, and a caller retrying without a `Refresh` then persisted it. Every one of those writes now records its previous value for the duration of the transaction and is put back on rollback, through a `TTTransactionObserver` alongside the one `TTNewEntityCache` already uses - so it also covers the commit that fails after the command succeeded, which is a rollback as far as the observers are concerned. `Insert`, `Update`, `Delete` and `Undelete` open a transaction of their own when none is active, as the command layer underneath them already did, so a single write outside an explicit transaction is rewound too; validation still runs before the transaction opens, so a body the entity refuses costs no round trip. **The rewind holds a reference to each entity it has written to until the transaction ends**: an entity passed to a write must not be destroyed before the transaction is over. Every list the framework builds is safe, and so is `FreeEntity<T>`, which tells the rewind to forget the entity before freeing it: an owning list now reports what it is about to destroy through the new `TTObjectList<T>.OnDisposeItem` hook, which fires on `Destroy`, `Clear`, `Remove` and `Delete` alike, and `TTContext.CreateEntityList<T>` installs it. That covers the list inside a `TTLazyList<T>` too, which is where a `Clear` frees detail rows mid-transaction. What remains outside is a list the application builds itself with `TTObjectList<T>.Create(True)`, or a bare `LEntity.Free`, and that is the rule this release adds: **an entity is freed with `FreeEntity<T>`, and a list of entities is built with `CreateEntityList<T>`** - never a bare `Free`, never an owning list of your own. The one list that stays yours is the result of a `RawSelect<T>`, as `docs/guide/identity-map.md` explains. A bare `Free` of an entity written inside a transaction that then rolls back makes the rollback write into freed memory, with no exception and no message. It does not take a transaction of your own: an event that writes another entity and frees it runs inside the transaction Trysil opened for the write that fired the event. Code written for 1.0.0 freed entities exactly that way, and `FreeEntity<T>` is not in 1.0.0 - it came after it, and the public master has it. Before upgrading, search every `.Free` on an entity and every `TTObjectList<T>.Create(True)` that holds entities. Written up in `docs/guide/transactions.md`
- **A failed commit leaves the transaction nothing to undo.** `TTGenericConnection.CommitTransaction` already rolls back, notifies the observers and leaves the connection out of the transaction when the commit fails. `TTTransaction.Commit` then tried a silent rollback of its own and raised, but kept believing it owned an open transaction, so its destructor rolled back once more, failed on a connection that was no longer in one, and wrote a `stop transaction` error to the log for a failure that never happened, next to the real one. It now asks the connection whether the transaction is still there
- **A context built while its connection is already in a transaction sees that transaction.** The rewind of the entities and the cache of the new ones are transaction observers, and an observer learnt that a transaction existed only when it started: a context created inside `RunInTransaction` of another context, or after the host opened a transaction on the connection, missed it. Its rollback then rewound nothing, so an update left the entity one version ahead of its row, and an entity inserted there did not go back among the new ones, so `Save<T>` updated a row that did not exist. `TTConnection.AddTransactionObserver` now tells an observer added during a transaction that the transaction has started. An observer of the host added mid-transaction receives `TransactionStarted` too, and if that raises it is taken back out of the list before the exception goes on, so a failed `AddTransactionObserver` leaves the list of observers as it found it. An observer must not remove itself, or free a context on the same connection, from inside a notification: the connection walks the list while it notifies, and the next observer would be skipped
- **Breaking, and the compiler does not catch it: connection pooling is on by default.** `TTFireDACConfigConnectionPool` started with `Enabled := False`, and `AddConnectionPooling` writes `Pooled=True` into a connection definition only when the pool is on, so an application that never touched `Config` got no pool at all. In the shape this library is written for that is the most expensive default it had: the HTTP listener builds a context per request, the documented pattern opens a connection there, and without a pool that is a TCP connection plus an authentication handshake **per request** - a cost that multiplies by the traffic rather than by the data. It is now `True`. **What changes without a compiler error:** an application that never set `Config.Enabled` now gets pooled connections, and a pooled connection is not closed when it is freed - it goes back to the pool and the physical connection stays open until the pool expires it or the pool is closed. For a desktop application on a file database, where the single connection lives as long as the program, that is a file held open a little longer and no gain to offset it: those set `Config.Enabled := False` at start-up, before the first `RegisterConnection`, as the demos already do. Nothing in this repository moves, because every test fixture and every demo already states its choice. The other road - refusing to start an HTTP server with pooling off - was left alone deliberately: `Trysil.Http` has no dependency on the FireDAC pool and should not gain one, since the context and its connection belong to the host and need not be FireDAC at all
- **The connection pool's guard no longer has a window of its own.** The class destructor set `FDestroyed` and then freed the `TObject` the lock stood on, while `GetInstance` read `FDestroyed` **outside** that lock: a thread that passed the check and lost its slice came back to `TMonitor.Enter` on freed memory, and then on `nil`. The flag was neither volatile nor locked, so the check read as a guard while protecting nothing. The lock is now a `TSpinLock` from `System.SyncObjs` held in a class var. It is a **record**, so it lives in the unit's static memory: there is nothing to allocate, nothing to free, and therefore nothing to use after freeing. Both the class destructor and `GetInstance` do their work inside it, with the flag read under the lock, so a thread arriving late gets `SInstanceDestroyed` - which is what the previous release meant to give it. The section it protects is a test and an assignment, plus the construction of the pool on the first call of the process, so spinning costs nothing in practice
- **The per-transaction undo registry no longer survives into the next transaction.** `TTNewEntityCache.TransactionStarted` created the registry only when it did not already have one, which assumed every transaction ends through Trysil. It does not: a pooled connection recycled, a `TFDConnection.Close`, a FireDAC reconnect, or an Oracle logoff that commits all end the physical transaction without notifying the observer, leaving the registry behind. The next transaction adopted it, and if **that** one rolled back it put back among the new entities an id whose row had already been written, so the following `Save` issued a second `INSERT` on the same primary key. The registry is now discarded and rebuilt at the start of every transaction, so state never crosses two units of work whatever happened to the connection in between
- **Breaking, and the compiler does not catch it: a failed commit now puts the entities back among the new ones, where before it left them marked as committed.** This is observable without breaking any build, so read it even if you skip the entries marked `Breaking`. `CommitTransaction` notified `TransactionCommitted` before the physical commit, so on every path, including a failure. That notification destroys the undo registry `TTNewEntityCache` keeps for the transaction, so an entity inserted inside it stayed marked as already inserted even though the row was never written: the next `Save` issued an `UPDATE` against a row that does not exist and raised `ETConcurrentUpdateException` blaming a concurrent change. Neither branch of the silent rollback recovered it - with the transaction already closed the guard raises and the empty handler swallows it, and with the transaction still open the registry is already gone. The failure path now notifies a rollback and re-raises, and only a commit that actually completed is notified as one. `RollbackTransaction` notifies after the physical rollback too, in a `finally`, which errs in the conservative direction. Note the trade this makes: if the database did commit and the driver raised afterwards, the entities go back to being new and a later `Save` inserts a duplicate - a `Commit` that raises means the commit failed, which is the assumption Trysil already makes elsewhere. The log tells the same story: a failed commit now emits a rollback entry after the commit entry, instead of a commit and nothing. The contract is written up in `docs/guide/transactions.md`
- **Breaking (compilation) (on the public master, not in 1.0.0): `TTObjectLazyList<T>` is gone, and its `IsValid` moved down to `TTObjectList<T>`.** The type existed to carry one Boolean saying whether a lazy list has been loaded, and having it on a class of its own forced everything that wanted to reach the flag to know that class: `TTSession<T>` tested for it by RTTI before invalidating, and `TTLazyList<T>` had to build its own list instead of asking the context for one. With the flag on `TTObjectList<T>` a lazy list is an ordinary owning list from `CreateEntityList<T>`, which is what lets the rewind cover it without a second factory on the context. It sits on the owning list rather than on `TTList<T>` so that the type most code passes around keeps its single method. The flag means nothing on a list nobody loads lazily, and nothing but `TTLazyList<T>` ever reads it. The removed type never appeared in 1.0.0, so it breaks nothing for anyone coming from the tag. It was public on the master between the two, in the `interface` of a core unit, so for anyone following that it is a compilation break with no type left to search for, and it is counted as one
- **Breaking (compilation): `TTTableMap.DetailColums` is now `DetailColumns`.** A typo in a public read-only property, fixed. Anything reading the detail columns off a table map by name needs the extra `n`
- **Breaking (compilation): `TTMetadataCache` is keyed by connection as well as by type.** Its base changed from `TTCache<PTypeInfo, TTTableMetadata>` to `TTCache<TTMetadataKey, TTTableMetadata>`, and `Load` takes the connection name before the type info. This is what stops two connections with different schemas - the multi-tenant case - from sharing one entry, and it is the fix for metadata shared between connections; the signature change comes with it. The cache is public, so code that called `Load` directly must pass the connection name
- **Breaking (compilation): `TTProvider.Get<T>` lost its one-argument overload.** It is now `Get<T>(const AID: TTPrimaryKey; const AIncludeDeleted: Boolean)`, because soft delete gave the question a second answer. `TTContext.Get<T>(AID)` is unchanged and still means "not deleted", so an application that goes through the context - which is the documented way - sees nothing; one that holds a `TTProvider` has to say which it wants
- **Breaking (compilation) (on the public master, not in 1.0.0): the `IncludeDeleted` overload of `TryGet<T>` takes the flag before the output parameter.** It read `TryGet<T>(AID, out AEntity, AIncludeDeleted)`, with the result of the call sitting in the middle of its own argument list, which is a shape nothing else in this library has. It is now `TryGet<T>(AID, AIncludeDeleted, out AEntity)`. The two-argument `TryGet<T>(AID, out AEntity)` is untouched, and it is the only one 1.0.0 had, so this reaches code written against the public master - where the three-argument form appeared - and nothing else. The compiler names every call site
- **Breaking at runtime, not at compile time: `TTMetadataProvider` gained `GetConnectionName`.** It is `virtual abstract`, like the three transaction methods described above, and for the same reason: the metadata cache needs to know which connection a set of metadata belongs to. A metadata provider living outside this repository keeps compiling, warns `W1020` where it is constructed, and raises `EAbstractError` the first time the cache asks. `TTFireDACConnection` implements it by returning the connection definition name
- **The numeric validators compare what the field holds, not what the attribute was written with.** `[TMinValue]`, `[TMaxValue]`, `[TLess]`, `[TGreater]` and `[TRange]` picked the comparison from the **literal**: `Create(const AValue: Integer)` meant "compare as `Integer`", `Create(const AValue: Double)` meant "compare as `Double`". The field was then checked against that choice with `CheckType<T>`, which does not merely refuse - it **adds a validation error**. So the attribute did not fail on bad data, it failed on every save, with a message about an invalid type. `[TMinValue(0)]` on an `Int64` field, on a `TTNullable<Integer>`, or on a `Double` - writing `0` where `0.0` was required - made the entity impossible to save at all. The comparison now reads the value: a nullable is unwrapped as the length and regex validators already did, whole numbers are compared as `Int64` so nothing is lost above 2^53, and anything else numeric goes through `Double`. The type error survives only where it belongs, on a field that holds no number. **Breaking (compilation):** `IsValidInteger` takes `Int64` instead of `Integer`, so a validator derived outside this repository must widen its override; and `TValidationValueType`, the enum that carried that choice, is gone
- **Breaking, and the compiler does not catch it: the `[TEmail]` validator accepts long top-level domains.** The pattern went from `(\.\w{2,3})+$` to `(\.\w{2,})+$`, so an address ending in `.info`, `.name` or `.online` is now valid where it used to be refused. It is a fix - those are perfectly good addresses - but it is also a rule that got looser without a compiler error: data your application used to reject now goes in
- **`TTFilter.IsEmpty` now accounts for the parameters.** It was `Where.IsEmpty and Paging.IsEmpty`, so a filter carrying **only** parameters - exactly what a `[TWhereClause]` entity produces - declared itself empty. That is the root the `[TWhereClauseParameter]` defect grew from, and it would have made the new parametrized `RawSelect` overload wrong from birth. Nothing in the library reads the property any more, so this changes no behaviour inside Trysil; it removes the trap for anyone reading it from outside
- **The metadata probe no longer inherits the entity's `[TWhereClause]`.** `AddWhereClause` is `virtual` and `TTMetadataSyntax` overrides it empty: the probe needs `0 = 1` to read the `FieldDefs`, nothing else. Until now it inherited the clause and accumulated its parameters onto the syntax filter as a side effect of generating the SQL, which is where the ordering trap came from. The metadata SQL changes on all seven dialects, dropping the `(entity clause) AND` prefix
- **The two column-name lookups agree again.** Earlier in this release `TTColumnsMap.Find` moved to a dictionary keyed with `TIStringComparer.Ordinal`, while `TTColumnsMetadata.Find` stayed on `String.Compare(..., True)`. Neither is ordinal, whatever the first one is called, but they fold differently. The same name could therefore be found by one and missed by the other: a column name carrying an accented letter, on a database that changes the case of identifiers - Oracle uppercases them - resolved in the metadata and came back `nil` from the mapping, because ordinal folding leaves accented letters alone. The column was then silently unmapped. The dictionary is still the fast path; on a miss the lookup now falls back to the same invariant comparison the metadata uses, so it only ever matches **more**, never less

- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): on Oracle, a `NUMBER(1)` is read as a boolean.** Oracle has no `BOOLEAN` column type before 23ai, and the driver mapped `NUMBER` with scale zero to `Int32` or `Int64` by precision, so a `Boolean` member had nothing to be read from: the field arrived as a `TIntegerField`, which resolves to the integer column class, and the value could not be assigned. There was no way to map a boolean on the versions in production. The driver now declares `NUMBER(1)` as a boolean to FireDAC, on both `dtBCD` and `dtFmtBCD`, and the integer rules start at precision 2. The Expert emits `NUMBER(1)` for a boolean on Oracle where it emitted `BOOLEAN`, which failed with `ORA-00902` on every version this repository documents as supported. **What changes without a compiler error:** the rule is keyed on precision and scale, not on the member it fills, so an existing `NUMBER(1)` column mapped to an `Integer` member now comes back as a boolean and stops mapping. A status code or a count stored in that width must be widened to `NUMBER(2)`

- **Breaking, and the compiler does not catch it: a lazy member is released with the entity that carries it, not with the context.** `TTProvider` kept every `TTLazy<T>` and `TTLazyList<T>` it built in one owning list that had an `Add` and no `Remove`, so the wrappers were freed only when the context was: freeing the entities freed none of them, and a `TTLazyList<T>` held on to the details it had loaded. It also happens on `CloneEntity`, which maps lazy members too, so `TTSession<T>` - which clones every entity in the list at construction - deposited one wrapper per lazy member per row **on each open**. Harmless in HTTP, where a context lives one request; unbounded in a desktop application, where one context lives as long as the process. The wrappers are now grouped by the entity that owns them and released through the disposal path the entity already went through - `TTObjectList<T>.OnDisposeItem`, `FreeEntity<T>` and the containers of `TTSession<T>`, see below. **What changes without a compiler error:** a related entity read through a lazy member - `LOrder.Customer.Entity` - is owned by that member, so it is now freed when the order is freed, where it used to survive until the context died. Code that keeps such a reference past the life of the entity it came from must copy what it needs or read it again. With the identity map on nothing changes: the map owns those entities and the lazy member never freed them. `TTContext.LazyOwnerCount` reports how many entities currently hold lazy members

- **Breaking at runtime, not at compile time: a custom `TTParam` descendant must implement three new methods.** `TTParam` (`Trysil.Data.pas`) is the parameter contract, and a driver living outside this repository brings its own descendant of it, exactly as it brings its own connection. `GetDataType`, `GetAsCurrency` and `SetAsCurrency` were added to it as `virtual abstract` while `Currency` was made a first-class column type. A descendant that does not implement them **still compiles**: `W1020` where it is constructed, `EAbstractError` in production. Of the three, two are reached at run time: `SetAsCurrency` where you would look for it, and `GetDataType` where you would not. `GetAsCurrency` is read nowhere - `AsCurrency` is a write-only property - so it cannot raise; it stays abstract because removing it would stop a driver that already overrides it from compiling, which is a real break traded for an inert method. `GetDataType` is the one to watch, because it is not read for `Currency` alone. `TTGuidParameter.WriteGuid` reads it on every `TGuid` parameter, and `TTStringParameter` reads it on **every string parameter**, to decide whether the column is a text LOB. A driver with no money column and no Guid anywhere therefore fails on the first write of almost any entity. The entry further down this file that says no driver had to change for `AsCurrency` was true of this repository only, and now says so
- **Breaking (compilation) (on the public master, not in 1.0.0): a driver configures the connection through `DoConfigureConnection`, not by overriding `ConfigureConnection`.** The PostgreSQL and Oracle drivers declare FireDAC map rules on the connection - the one that keeps a `Currency` out of the `money` type, the six that make a `NUMBER(1)` a boolean - and they did it in an override of `ConfigureConnection`. A host deriving from either of them to add an option of its own and omitting `inherited` lost those rules **with no signal at all**: not an error, a different value, which is exactly how the two defects closed earlier in this release were born. `ConfigureConnection` is no longer virtual: it applies the rules of the driver, through the new `ConfigureMapRules`, and then calls `DoConfigureConnection`, which is virtual, empty in every driver here, and yours. An existing `override` of `ConfigureConnection` stops compiling, which is the point - the alternative was to keep losing the rules quietly. Migration: rename the override to `DoConfigureConnection` and drop the `inherited`, which is no longer needed for the rules to survive
- **A failed commit rolls the transaction back for real.** In 1.0.0 and on the public master a commit that failed left the physical transaction open, for whoever called it to roll back. The failure branch first added in this release called `inherited RollbackTransaction`, which is `TTConnection`'s: that method only walks the observers, it never reaches `InternalRollbackTransaction`. So the observers were told a rollback had happened, the log said the same, and the physical transaction stayed open. Nothing broke in practice because `TTTransaction.Commit` catches the re-raised exception and calls `SilentRollback`, which goes through the full `RollbackTransaction` - so anything reaching the database through `RunInTransaction`, `TTTransaction` or `TTSession<T>` did get its rollback, one step later and after a second observer notification for the same rollback. What was left uncovered is a `CommitTransaction` called straight on the connection, where the transaction stayed open and, on a pooled connection, went back to the pool that way. The failure branch now issues the physical rollback itself and notifies once; a rollback that fails in turn is logged and swallowed, so the exception that reaches the caller is still the one from the commit. `TTTransaction.SilentRollback` then finds the connection out of its transaction and does nothing, which is where the second notification went

- **Assigning to a lazy member takes the new entity before it releases the old one.** `TTLazy<T>.SetEntity` freed the entity it held first and cloned the one it was given afterwards, and the one it was given can hang from the one it held: `E.Manager.Entity := E.Manager.Entity.Manager.Entity`, with `Manager` a lazy member of its own class. Freeing the old manager freed its lazy members and the new one with them, and the clone then read freed memory. The new value is taken - kept for the identity map, or cloned - and held by the lazy member before the old one is released, so a destructor that raises while the old one is freed leaves neither a lost clone nor an address the lazy member frees a second time. A value read through the lazy member itself still goes with the old one: after `LNext := E.Manager.Entity.Manager.Entity; E.Manager.Entity := LNext`, `LNext` belonged to the old manager and is freed with it, and `E.Manager.Entity` is what to read. Changing the id of a lazy member lets go of the entity it held before freeing it, for the same destructor

- **Breaking, and the compiler does not catch it: assigning `nil` to a lazy member that has not loaded clears the relation.** `SetEntity` compared the entity it held with the one it was given, and on a member read from the database and never navigated both are `nil`: the assignment did nothing, the id stayed, and the next `Update<T>` wrote the old foreign key back. The same assignment cleared the relation once `.Entity` had been read, so the result depended on a read before it. `nil` now always clears the id. The old behaviour is what 1.0.0 and the public master both do, so an assignment that used to leave the foreign key alone now writes `NULL` on the next `Update<T>` - which is what the code asked for, and what the entry on `TTLazy.SetEntity` in a window below already promised
- **A lazy reference releases the entity it loaded through the disposal path.** `TTLazy<T>` freed it with a bare `Free` in three places - the destructor, `SetEntity`, and the id setter - while `TTLazyList<T>.AddEntity`, thirty lines below, already used `FContext.FreeEntity<T>`. With the wrappers now grouped by the entity that owns them, a bare `Free` leaves that entity's own lazy members behind, keyed on an address nobody holds; and with `TTEntityUndoLog` holding entity references for the length of a transaction, an entity freed outside the path leaves an entry the rollback then writes into. The three calls now go through `FreeEntity<T>`, which already carries the identity-map test, so the surrounding condition is only `Assigned`
- **Breaking, and the compiler does not catch it: `TTSession<T>.Insert` adopts the entity handed to it.** In 1.0.0 the session kept the entities passed to `Insert` in a list that owned nothing and freed only its own clones, so the host freed what it inserted. The session frees it now, when it is destroyed, unless the identity map holds entities of its type, and `Save`, new in this release, does the same for an entity that is not one of the session's clones. A host that inserts through a session without an identity map - which is every host on `TTJSonContext` or `TTHttpContext` - and frees the entity after the session compiles, and frees it twice; one that reads it after the session is destroyed, to write it into the response or to add it to a list, reads freed memory. It is deliberate: a consumer that builds an entity and hands it to the session may have no later moment to free it. Drop the host's own free once the call has returned and do not use the entity after the session; an entity `Insert` refused keeps its owner. Who frees what, in each mode, is the table in `docs/guide/context.md`
- **`TTSession<T>.Save`.** It updates a clone of the session and inserts any other entity, with everything `Insert` implies, adoption included. Calling it again on an entity already inserted raises `EListError` and leaves the entity twice in `Entities`, so an `ApplyChanges` after catching it runs the insert twice with the same key, and on a table with a primary key the whole batch fails, and rolls back unless it joined a transaction of the host: `docs/guide/sessions.md` says so
- **Breaking, and the compiler does not catch it: `TTSession<T>` releases its clones and the entities it inserted through the disposal path too.** It is the case the entries on a lazy member released with the entity that carries it and through the disposal path name as the main one, and it was the one still open: `TTClonedEntities<T>` kept the clones in a `TObjectDictionary` with `doOwnsKeys`, and the session, in the development builds after 1.0.0, kept the entities passed to `Insert` in an owning `TObjectList`. Both free with a bare `Free`, so every clone left its lazy wrappers behind on each open, left its entry in `TTEntityUndoLog` - which a rollback then writes into through RTTI - and left its address in `TTNewEntityCache`, where a later object allocated at the same address is read as a new entity and `Save<T>` inserts instead of updating. Neither container owns anything now: the session releases each entity through `FResolver.DisposedEntity` and `FProvider.DisposedEntity` first, the entities it inserted when the identity map does not hold their type - the rule of `IdentityMapOwns` described below - and the clones always. **What changes without a compiler error:** the session now uses the provider and the resolver *while it is being destroyed*, and both are references it borrowed from the context. Freeing the context first used to be harmless, because the destructor touched neither; it is a read through a destroyed object now. Free the session first - `try..finally LSession.Free` around the block that uses it is always right. Reaching the third register needed no new argument anywhere, because `TTNewEntityCache` was already declared in `Trysil.Provider.pas` and only owned by the context: it now belongs to `TTProvider`, and `TTProvider.DisposedEntity` clears it. `TTContext.DisposedEntity` does the same three things it did before
- **Breaking, and the compiler does not catch it: a list handed to `CreateSession<T>` outlives the session.** The session keeps the list it cloned: `ApplyChanges` marks it as no longer valid, so that a lazy list reloads, and `GetOriginalEntity` answers with its rows. In 1.0.0 the session read the list only while cloning it, so a list freed before `ApplyChanges` did no harm; it is a read of freed memory now, and a write when the list is a `TTObjectList<T>`. Free a list of the host after the session; the list of a lazy member is never freed by the host, and the entity that carries it lives until after the session
- **`TTSession<T>` tells two entities apart by identity, not by what they say about themselves.** Its three dictionaries were keyed on the entity, and the default comparer for a class in Delphi is the **virtual** `Equals` and `GetHashCode` of the object. An application that overrides them by value - legitimate, and not rare on an entity - made two different rows collapse onto one key: the session raised a duplicate key while cloning, and where it did not raise it merged the two silently and `GetOriginalEntity` answered with the wrong row. It is the same trap `TTNewEntityCache` was moved off earlier in this release, one class over. The three now use an explicit identity comparer, `TTEntityComparer<T>.Identity` in `Trysil.Generics.Collections`, which compares addresses and hashes them the way Delphi hashes a pointer. Dictionaries keyed on `TClass` or on `PTypeInfo` never had the problem: those kinds compare by pointer already
- **Three narrower paths through a lifetime.** A clone released on the error branch of `TTClonedEntities<T>` now goes through the resolver as well as the provider, which is what every other disposal does - it was the asymmetry that produced the entry on the session and the new-entity cache, in a method that is one call away from being reachable. The destructor of `TTSession<T>` no longer walks two lists before asking whether they exist, which an exception in the constructor - out of memory, and nothing else - turned into an access violation inside the unwinding. And an entity that `InternalCreateEntity` has just built is protected from that moment rather than from the line after it is registered in the identity map.
- **An event releases the old entity it loaded the same way every other holder of a clone does.** `TTEvent<T>.OldEntity` is a clone, and `CloneEntity` maps the lazy members of the entity it copies, so the clone owns wrappers registered under its own address. The destructor freed it with a bare `Free`: the wrappers stayed alive until the context died, keyed on an address nobody held, and an entity allocated at that address afterwards inherited them. Every `Update<T>` on an entity that declares an event and carries a lazy member left one behind - bounded in a per-request context, unbounded in a desktop one. It was the last bare `Free` on a clone in the library; the session and the clone collection were closed earlier in this section. `TTContext` gained `FreeClone<T>` for it, which releases unconditionally: `FreeEntity<T>` would have been the wrong answer, because with the identity map on it declines to free an ordinary entity and would have turned a partial leak into the whole clone.
- **Breaking (compilation): `TTClonedEntities<T>.Create` takes the resolver as well as the provider.** It is the collection of clones a `TTSession<T>` keeps, and it is a public type in the `interface` of `Trysil.Session.pas`, so the constructor is reachable and the change is a break by the same criterion that counts `TTHttpLogRequest.Create` further down: they are public constructors on public types. In practice nothing outside the unit can use the class - every other member is `strict private` or internal, so all a host can do is construct it and destroy it - but the count at the top of this section is a number readers act on, and a break that is not in it is a break the reader has not been told about. The reason for the argument is in the entry above: releasing a clone goes through the resolver, and the class had no way to reach one.
- **Defence in depth: SQL Server pages a query that declares no order.** `OFFSET` is not accepted without an `ORDER BY` in T-SQL, and the `ORDER BY` is written from the filter or from the primary key. `TTTableMetadata` refuses a mapping with no key long before a select exists, so **no application can reach this**: it is closed against a driver that builds a `TTSelectSyntax` of its own, since the class is public and `TTSyntaxClasses.Select` is `virtual`. It now emits `ORDER BY (SELECT NULL)`, the canonical T-SQL form for a page with no declared order, rather than a statement the parser rejects: the other six accept paging without an order, and refusing on one engine only would be the odd answer.
- **An entity that `TTSession<T>` inserted stops being new, so a later `Save<T>` updates it.** `TTContext.Insert<T>` is the only place in the whole library that calls `TTNewEntityCache.Remove`, and `TTSession<T>.InternalApplyChanges` went straight to `TTResolver.Insert<T>`. So an entity built with `CreateEntity<T>`, handed to a session and written by `ApplyChanges`, was still listed among the new ones, and the next `Save<T>` on it chose `Insert` again and wrote a second row carrying a primary key the table already held. With the identity map off the window closes when the session is freed, because the disposal path takes the entity out of the cache; with it on the session does not release what it inserted, so the window is the rest of the entity's life. The removal now happens where the insert happens, inside the same transaction, so a rollback puts the entity back among the new ones through the undo registry `Remove` already keeps - where before the rollback was right only because nothing had been removed.
- **The five error branches of `TTProvider` release what they built through the disposal path.** `CreateEntity`, `InternalCreateEntity`, `CloneEntity`, the detail loader and `RawSelect` all free the entity with a bare `Free` when something raises after `MapEntity` has run - and `MapEntity` is exactly what registers the lazy wrappers under that entity's address. The entry stayed behind, keyed on a pointer nobody holds, and the wrappers with whatever a `TTLazyList` had already loaded inside them. Not corruption, since the key is a `Pointer` and nothing dereferences it, but if the memory manager hands the same address out again the wrappers of two entities merge. All five now call `DisposedEntity` first
- **`OldEntity<T>` releases its clone the same way.** The clone is built by `CloneEntity<T>`, which maps lazy members and registers them; both exits freed it directly. `FreeEntity<T>` is not the right call here - a clone never enters the identity map, so with the map on it would do nothing and leak - so the two exits notify disposal and free unconditionally, which is what a caller-owned object needs

- **`Get<T>` and `Refresh<T>` on an entity with `[TJoin]` name the key with its table.** The `WHERE` was built by `TTProvider.GetWhere`, which emitted the column name bare - neither qualified nor quoted - while the `ORDER BY` two functions away already qualified it when `HasJoins`. So a `Get<T>` on a join entity produced `WHERE ID = 1` against a statement joining two tables that both have an `ID`, which is an ambiguous column on all seven engines. Writes on a join entity were already refused by `CheckReadWrite`; reads by key were not, and `TTContext.Get<T>` goes straight to the provider. The key is now qualified with the FROM table when the entity has joins, and quoted in both branches, which also closes the quoting for the plain case: a primary key called `Order` or `Level` reached the statement bare
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): a list from `CreateEntityList<T>` owns what the identity map will not hold.** Ownership was decided on `not UseIdentityMap`, but the map registers an entity only when it has a primary key and carries no `[TJoin]` (`TTProvider.InternalCreateEntity`), and `RawSelect<T>` never reaches the map at all. So with the map on - which is what `TTContext.Create(AConnection)` gives you when you do not ask - a `[TJoin]` entity belonged to nobody: one object per row, for the life of the process. `FreeEntity<T>` had the same hole and released nothing. Both now ask what the map will really hold, and so does the branch in `TTLazy<T>` that decides whether to keep the instance it was handed or clone it - it asked whether the map was **on**, which for a join entity is not the same question. `RawSelect<T>` is the one case the question cannot be answered from the type, because a list is built before anyone knows who will fill it: collect a raw select into a `TTObjectList<T>.Create(True)` of your own for a plain DTO, and into a `TTList<T>` freed row by row with `FreeClone<T>` for a class with a lazy member - never into `CreateEntityList<T>`. **This changes what your code must not do**: an application that had noticed the leak and freed those entities by hand, out of a list built by `CreateEntityList<T>`, now frees them twice - if you wrote that loop, delete it. An application that followed the documentation did not write it, because the documentation claimed the list owned them; that sentence is corrected too. The leak is older than this release, but `Get<T>` on a join entity only started working here, which is what made the single-entity path reachable at all.
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): a list built by `CreateEntityList<T>` must be freed before the context that built it.** The list tells the context about every entity it frees - `OnDisposeItem` reaches the undo log of an open transaction, the new-entity cache and the lazy members the entity carries - so the context has to be alive when the list is destroyed. Until this release the order did not matter, because with the identity map on that list owned nothing and freed nothing. It is the order a `TTSession<T>` needs as well, and the same `try..finally` gives it to you: build the list after the context, free it before
- **`TTContext.IdentityMapOwns` is public.** It answers the question the identity map page spends a paragraph describing - whether the map will hold an entity of this shape, which is what decides who frees it - and until now it was private, so an application that had to decide the same thing wrote the rule again by hand. `TTLazy<T>` asks it, and so does the destructor of `TTSession<T>`, which was the last place still asking whether the map was **on** rather than whether it owns: with the map on and an entity carrying `[TJoin]`, the session skipped the release of everything it had inserted. The predicate lives on `TTProvider` now, where the map and the mapping both are, and the context passes it on.
- **Breaking, and the compiler does not catch it: a sequence value that does not fit a primary key raises instead of coming back wrong.** `TTGenericConnection.GetSequenceID` read the value with `Fields[0].AsInteger`, and on every engine but SQLite that field is 64-bit. `TLargeintField.GetAsInteger` is a hard cast, `Integer(L)`, with no range check: the moment a sequence passes 2147483647 it hands back the low 32 bits read as signed, so the next identifier is **-2147483648** and the count walks up from there. Negative identifiers are still unique, so the primary key does not object and the rows go in: the failure is silent for another 2.1 billion rows, then a single insert fails on zero, then every identifier collides with one already used. It is now read as `Int64` and checked against the range of `TTPrimaryKey`, and out of range it raises naming the table and the value. `SelectCount` had the same line, and is dealt with in the entry below. **Declare the ceiling in the sequence as well**, where the engine allows it - `AS int` on SQL Server, `AS integer` on PostgreSQL, `MAXVALUE 2147483647` on Oracle and on MariaDB, where `AS int` arrives only in 11.5 and the supported floor is 10.3 - because there the database refuses the value at the source. Firebird and InterBase generators are 64-bit with no ceiling to declare, and SQLite has no sequence object at all: on those three this guard is the only thing between you and a negative identifier.
- **Breaking (compilation): `SelectCount` returns `Int64`.** The count was read with `Fields[0].AsInteger` from a field the engine hands back 64-bit, so a count above 2147483647 came back truncated to its low 32 bits read as signed - a negative number of rows. The first fix written was the same guard the sequence got, and it was the wrong one: a count is not a primary key, and there is no reason to refuse an answer the database gave correctly. `TTConnection.SelectCount`, `TTGenericConnection.SelectCount`, `TTProvider.SelectCount<T>` and `TTContext.SelectCount<T>` are all `Int64` now. One thing the Delphi widening cannot do on its own: `COUNT(*)` is typed by the **engine**. On SQL Server it is `int`, so past 2147483647 rows the server answered with an arithmetic overflow before any Delphi type came into play - the SQL Server dialect emits `COUNT_BIG(*)` now, through a new virtual `TTSelectCountSyntax.GetCountSyntax`. InterBase types `COUNT` as `INTEGER` and has no wider aggregate, so there the ceiling is the engine's and it fails rather than truncating. The break is narrow and loud: a driver outside this repository that **overrides** `SelectCount` no longer compiles. Calling code does compile, because Delphi assigns an `Int64` to an `Integer` without a word when range checking is off - so a host that keeps `LCount: Integer` truncates in its own variable instead, or raises `ERangeError` under `{$R+}`. `{$Q+}` does not see it: the assignment is not arithmetic. Above two billion rows, declare it `Int64`.

- **A JSON failure that is the server's fault stays a `500`.** The entry on the malformed body below maps `ETJSonException` to `BadRequest`, and that class does not hold only malformed bodies. A serializer or deserializer the host never registered for a member of its own model is a deployment fault; a serialization re-entered by the host's own event is a fault in the host's code; a field type the dataset converter does not know is neither the caller's doing. Mapped with the rest, all three would have told the client its request was wrong - for a few days of this release's history they did. They raise `ETJSonServerException` now - a new class deriving from `ETJSonException`, so nothing that catches the base stops catching them - and the listener answers `500` before it reaches the `400` branch. Against 1.0.0 nothing changes for them: every exception outside `ETHttpException` answered `500` there, and these three still do, while every other `ETJSonException` now answers `400`. It is a fault to look at in the log, not a request to correct. The three are the whole list for a request; a host that converts a `TTJSonValue` of one type to another in its own code still gets an exception, `ETJSonServerException` now and `ETJSonException` in 1.0.0 - a subclass, so a handler for the old class still catches it. Other faults of the host's configuration that surface as JSON errors - a `TTJSonContext` given the identity map it refuses, an event class that is not one, an alphabet Sqids refuses - still raise `ETJSonException` and still answer `400`

- **Breaking (compilation): `TTJSonSerializers.Get` and `TTJSonDeserializers.Get` are gone, and the class registry under them with them.** They returned the serializer **class**, not the instance, so the only way to use what they handed back was `Get(ti).Create` - building an object of your own and owning it. That is exactly the model the entry above retires, where the registries went from one instance per conversion to one shared instance that the framework owns and frees. Nothing in this repository called either method: not the library, not the tests, not the documentation. With the last reader gone the class dictionary beside `FInstances` was write-only, so it went too, and `Register<T>` now records the instance and nothing else. `GetInstance` is the whole public way in

- **Breaking, and the compiler does not catch it: two columns that name the same parameter are refused, where one used to write over the other.** `GetParameterName` folds a space onto an underscore, and that is the one fold left after the entry above stopped folding everything else. The reason that entry gives for refusing the rest applies to this one too: an entity mapping both `Ragione Sociale` and `Ragione_Sociale` puts `:Ragione_Sociale` in the statement twice, and both columns then find the same `TFDParam` - the second writes over the first, on all seven engines, with nothing said. The fold stays, because a column named with a space works today and breaking that at runtime would be the worst kind of break; what is new is that the **collision** raises. The check runs where the metadata for an entity is built, which happens once per type and connection and is cached, so it costs nothing on the path that inserts. It also means the refusal comes at the first **read** of the entity - `Select`, `Get`, `Refresh` - and on entities that never write, join entities included: the check runs where the metadata are built, and they are the same for reading and writing. On a join entity it checks the output aliases, which never become the parameters of a statement Trysil emits, so there it can only refuse, never prevent an overwrite. Besides `Select`, `Get` and `Refresh`, creating a `TTFilterBuilder`, the HTTP filter and `MetadataToJSon` load the metadata too; `SelectCount` does not. The same holds for the characters `GetParameterName` refuses, described in the entry above

- **Breaking (compilation): `SColumnNotFound` existed twice, and the dead one shadowed the live one.** `Trysil.Http.Consts` declared its own `SColumnNotFound` with a `%s` where the one in `Trysil.Consts` has a `%0:s`. In 1.0.0 and on the public master the HTTP filter raised the Http copy, because its interface `uses` names `Trysil.Http.Consts` after `Trysil.Consts`; the filter refuses a column with `SColumnNotFilterable` now, and nothing references the Http copy - the three places that raise the message all live in the base package and see the core one - but almost every unit of `Trysil.Http` puts both `Trysil.Consts` and `Trysil.Http.Consts` in its interface `uses`, with `Trysil.Http.Consts` last, and in Delphi the last one wins. The first line of `Trysil.Http` to write that name would have taken the dead constant without a word. That the ambiguity had already been met is written in the demo language units, which spell the name **qualified** to get past it; the Http copy is gone and they no longer need to. Removing it is a compilation break only for a host that named it, and in this release naming it does nothing, because nothing emits it. In 1.0.0 it did: a host that translated it by name translated the refusal of the HTTP filter, and that refusal is `SColumnNotFilterable` now, which is the one to translate

- **Breaking (compilation): the identity map has no remove.** `TTIdentityMap.RemoveEntity<T>` is gone, and `TTEntityIdentityMap.Remove` under it with it. Nothing in this library called either, and by design nothing should: the map holds what a context loaded and is emptied when that context dies. What settled removing them rather than documenting them is what `Remove` did - the cache is a `TObjectDictionary` with `doOwnsValues`, so taking the key out **freed the entity**, and a caller who read the name and expected the object back was left holding a dangling pointer. A test asserted the freeing by name, so the behaviour was deliberate; it was still an operation this design has no place for, on a class where nothing else offers to take anything out

- **A logger thread destroyed before it ever ran used to drop everything it had been given.** Draining the queue was `Execute`'s job, and `Execute` is not always called: stopping the thread sets `Terminated` first - `SetTerminated` calls `Terminate` before it resumes or waits, and `TThread.ShutdownThread` does the same before it resumes a thread still suspended - and `ThreadProc` skips `Execute` entirely when `Terminated` is already true. Between the constructor returning and the destructor terminating there is a window in which the operating system has not scheduled the thread yet - and everything queued in that window went away without a sound, which for a short-lived logger is everything. The drain is its own method now, and `SetTerminated` calls it **after** `WaitFor`, on the destroying thread, where the logger thread is provably finished and there is nobody on the logger's side to race. A logger that lives for the process was never affected; one created, written to and freed in the same breath was affected completely. With the drain there, `Execute` has no reason left to run on after `Terminate`, so it loops on `Terminated` alone and touches no field once it is set. That also makes the thread safe by construction on a constructor that raises, where it used to be safe only because `ThreadProc` skips `Execute` on a thread already terminated - a limit the first draft of these notes declared, and that no longer holds

- **A logger whose `AfterConstruction` fails before the thread starts no longer hangs the caller.** When `AfterConstruction` raises, the RTL runs `BeforeDestruction` before it destroys the instance, and `TTLoggerThread.BeforeDestruction` stops the thread and waits for it. A host override that raises before `inherited` - opening its file first, say - leaves the thread suspended, and the wait was on a thread that would never run: `RegisterLogger` hung for good, holding the round robin lock - usually the start of the application, and, when an earlier registration had already succeeded, every thread that logged from then on. A thread still suspended is now resumed before the wait, the way `TThread.ShutdownThread` does it: one that never started finds `Terminated` already set and skips `Execute`, one a host suspended by hand wakes up and leaves its loop. One resume undoes one suspension: a thread suspended twice through the deprecated `Suspend` stays asleep and the wait does not return, exactly as it does in `TThread.ShutdownThread`. The exception reaches the caller

- **A logger thread that frees itself on terminate no longer hangs the process at exit.** `TTLoggerThread.BeforeDestruction` stops the thread before `inherited`, and `inherited` is what clears `FreeOnTerminate`. A host logger that set the flag had it still set when the thread left `Execute`, so `ThreadProc` freed the thread from the thread itself, that ran `BeforeDestruction` again and waited on its own handle, and the thread freeing it waited on the same handle: every exit from the process hung. 1.0.0 stopped the thread in `Destroy`, after the flag was cleared. The flag is cleared first thing now, in `TTLoggerThread` and in `TTHttpLogThread`, which has the same order and was safe only because its constructor sets the flag itself

- **Stopping a logger thread no longer waits out its timeout.** `Execute` reset its wake-up event after checking `Terminated`, so a `Terminate` and `SetEvent` that fell between the two were erased, and the thread slept the full five seconds before noticing. With a pool the threads are stopped one after the other, so shutting down could take five seconds per thread; a line queued in the same gap waited as long. The event is reset at the top of the loop now, before the queue is drained, so anything signalled after that point wakes the wait

### JSon

- **Breaking, and the compiler does not catch it: a column an entity maps and the table does not have names the entity, and every other driver error on that first read is an `ETException` too.** Metadata are read with a `SELECT` of the mapped columns against the table, so a column that is not there is refused by the **engine**, and what reached the application was the driver's own error - seven different messages across seven engines, none of which says which class asked for it. The probe now catches that and raises with the entity, the table and the engine's own words inside. What it does **not** do is compare types: the probe records what the server reports and nothing checks it against the member, which is deliberate, because the mapping is meant to be loose - an `Int64` on a `DECIMAL`, a `Currency` on `money`, a `TIME` on a `TDateTime` - and a strict check would refuse mappings that work today on all seven engines. Written up, with the timing that matters in multi-tenant: the cache is lazy and per connection, so a tenant that missed a migration starts normally and fails later, and the way to move that failure to registration is to touch `GetMetadata<T>` there
- **Nine column types that no engine could use are registered, and the read side stops asking for the exact class.** Writing looks a parameter class up by `TFieldType` and reading looks a column class up by the field's class, and both registries had holes: `ftTime`, `ftByte`, `ftShortint`, `ftWord`, `ftLongWord`, `ftBytes`, `ftVarBytes` and `ftGraphic` were in neither, so a `TIME` column on five engines, MariaDB's unsigned integers, `VARBINARY` and `RAW` all failed - readably, but at the first access in production rather than at start-up. `ftLongWord` is registered on the **large** integer, not the integer: an unsigned 32-bit reaches 4294967295, and binding it as an `Int32` would overflow in silence, which is worse than the refusal it replaces. The read side also looked the field up by its **exact** class, so a class descending from a registered one was refused all the same - `TGraphicField` from `TBlobField`, and any field class a driver introduces; the lookup now walks up to the first registered ancestor. `ftTimeStampOffset` is deliberately left out: it carries an offset from UTC that none of the supported member types can hold, so registering it would drop the zone in silence, and the clear refusal is the better answer until there is a type that keeps the value whole
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0), for long names only: a join column alias is bounded at 30 bytes.** A joined column is selected as `Alias_Column`, built with no limit in sight, while Oracle up to 12.1 takes 30 **bytes**, not characters: on an `AL32UTF8` database an alias of 29 characters carrying three accented letters is 32 bytes and comes back `ORA-00972`. Raising the declared minimum does not help, because the Oracle paging syntax already requires 12.1 and 12.1 still counts bytes; only 12.2 stops. So the alias is measured in UTF-8 bytes. Firebird up to 3.0 and InterBase take 31 characters, and the rest 63 or more. `DocumentiRighe_PrezzoUnitarioNetto` is 34: the same mapping worked on SQL Server and PostgreSQL and was refused on three engines, and nothing said so until it ran there. An alias over 30 bytes is now its first 23 bytes, cut between two UTF-16 code units, plus a hash of the whole name - `DocumentiRighe_PrezzoUn_A3F19C` - so the head stays readable in a query and two columns sharing their first 23 bytes, a `Netto` and a `Lordo`, do not collapse into one column selected twice. A character outside the Basic Multilingual Plane can be split there, and the name is then refused at the first read, because half a surrogate pair is not a valid parameter character. The alias is measured before `GetDatabaseObjectName` upper-cases it on Oracle, Firebird and InterBase, and a handful of letters grow in UTF-8 when upper-cased; none of the Italian or Western European ones does. The alias is also the metadata key and the `columnName` a client filters by, so **a client filtering on a joined column whose alias exceeds 30 bytes must use the new name, or the member's JSON name**, which the HTTP filter accepts as well and which the shortening does not touch. An alias within 30 bytes is untouched, which is every mapping in this repository. One within 30 characters but over 30 bytes is not, because an accented letter takes two: `DocumentiRighe_QuantitàResidua` is 30 characters and 31 bytes, and becomes `DocumentiRighe_Quantit_` plus the hash, on every engine. It cannot be decided per engine: `TTMapper` is a global cache and one table map serves every connection, so the shortest limit governs
- **`TTFireDACConnectionFactory` answers to the name of the engine, and reaches MariaDB at all.** Each driver registered itself under `DriverLink.DriverID`, which the base class builds as `Trysil_` plus the **FireDAC** base id, while the lookup builds `Trysil_` plus whatever the caller passes. So the accepted names were `SQLite`, `PG`, `MSSQL`, `FB`, `IB` and `Ora` - internal FireDAC ids, written in no page of the documentation, which shows `Driver := 'SQLite'` and works only because that one engine's base id happens to be its name. MariaDB was worse: its `AfterConstruction` overwrote the id with `MariaDB`, dropping the prefix, so it registered under a key the lookup could never build and every call raised `SNotValidConnectionDriver` - and the factory is what multi-tenant registration and per-connection pooling go through. A driver now declares its names with `GetDriverAliases`, and `RegisterDriver` registers them alongside the base id: `PostgreSQL`, `SqlServer`, `FirebirdSQL`, `Firebird`, `InterBase`, `Oracle`, `MariaDB` and `SQLite` all resolve. MariaDB does not answer to `MySQL`: the driver emits `NEXTVAL` for sequences, which MariaDB has from 10.3 and MySQL does not have at all, so the alias would have handed a MySQL database a driver whose SQL it cannot run. **Purely additive** - the FireDAC base ids keep working, and no `DriverID` changed, so the connection definitions FireDAC holds are untouched
- **Breaking, and the compiler does not catch it: `MetadataToJSon<T>` renames two keys, `columns` to `properties` and `tableName` to `entity`.** The array never held columns: each entry describes a mapped **member** and carries the JSON name the client already sees in ordinary responses, so a `[TColumn('CustomerID')]` on a `TTLazy<TCustomer>` appears there as `customerID` and the column behind it appears nowhere. The old name invited reading the payload as a description of the table, which is the same misunderstanding `tableName` invited, and the two travelled together, so they move together. `entity` carries the class name, without the `T` Delphi puts in front of a type - `TAPIOrder` as `APIOrder` - and only that one letter, only when a capital follows it, so an acronym keeps its shape and a class called `Temp` is untouched. Every other name in that payload is already the JSON name a client sees in ordinary responses - the columns, the primary key, the version column - so the table name was the single line in it that described the **schema** rather than the API. It is of no use to a client that addresses `/api/orders`, it changes when a table is renamed and would break that client for a change that does not concern it, and it is precisely what is worth having to anyone probing an API for the database underneath. The class name identifies the type, survives a schema refactor, and is what a client caching metadata by type needs. Neither key was documented, and nothing in this repository read the table name: a client that walks the payload by key needs the two words; nothing else in it moves
- **`[TJSonIgnoreSerialize]` and `[TJSonIgnoreDeserialize]`** (`Trysil.JSon.Attributes`): asymmetric columns are now expressible. `[TJSonIgnoreSerialize]` goes in but never comes out - a password on creation; `[TJSonIgnoreDeserialize]` comes out but never goes in - a computed total, a server-side status. `[TJSonIgnore]` is unchanged and still means both directions, so no existing annotation changes meaning. All three share one polarity on purpose: every name says *ignore*, and the qualifier says only where
- **Breaking, and the compiler does not catch it: `MaxLevels` now bounds detail collections too.** `DetailColumnsToJSonObject` reset the level counter to zero before every detail column, so the depth budget was reloaded on entering each sub-tree: `Create(1, True)`, `Create(2, True)` and `Create(9, True)` all produced the same output, the entire tree, and detail-of-detail nesting had no bound at all - on a self-referencing table the serializer walked down to the leaves, and with lazy loading every level was a query. The documented contract already described the counter as covering details, with `Create(1, True)` giving `Company + Departments` and `Create(2, True)` adding `Employees`; the code is what disagreed with it. `-1` still means unlimited, so anything on the default is unaffected, and a finite `MaxLevels` with `Details = True` now returns the depth it asked for instead of the whole graph. `Create(0, True)` emits no details, level zero allowing nothing below the current entity. A collection cut off by the budget has no id to degrade to the way a `TTLazy<T>` reference does, so its key is omitted from the object rather than written as an empty array, which would claim the collection has no rows
- **`EntityFromJSon<T>(AJSon, AEntity)` and `EntityFromJSonObject<T>(AJSon, AEntity)`**: deserialize onto an **already loaded** entity instead of a fresh one. This is the safe shape for an update endpoint, and it is what makes `[TJSonIgnoreDeserialize]` usable: with a fresh entity, any column absent from the body is written back as blank, so an ignored column would be wiped on the first `PUT`. The pattern is

  ```delphi
  LEntity := Context.Get<T>(AID);
  try
    Context.EntityFromJSonObject<T>(FRequest.JSonContent, LEntity);
    Context.Update<T>(LEntity);
  finally
    Context.FreeEntity<T>(LEntity);
  end;
  ```

  Two things to know about it. The identity map is forbidden in a
  `TTJSonContext`, so `Get<T>` hands back an entity nobody owns and the
  `try..finally` is not optional. And the semantics are replace-all, not merge:
  a `String` column absent from the body keeps its loaded value, but a
  `TTNullable` column absent from the body is set to NULL, and the `id` in the
  body wins over the one the route resolved - compare them if that matters

- **The loading flag is a counter, so nesting cannot switch it off.** `ListFromJSonArray` raises it and then calls `EntityFromJSonObject`, which lowered it again in its own `finally`. Today nothing regresses from that, because the inner call raises the flag itself before creating anything, so no element ever drew a sequence id; but any future entry point that relies on the flag across a nested call would have been wrong by construction. `BeginLoading` / `EndLoading` make the nesting explicit. No observable change
- **Breaking, and the compiler does not catch it: `[TJSonIgnore]` and the directional attributes now apply to a detail collection field.** Both the serializer and the deserializer read the attributes on mapped columns but not on the collection field itself, so `[TJSonIgnoreDeserialize]` on a `TTLazyList<T>` did nothing. Pre-existing for `[TJSonIgnore]`, more visible now that there are three attributes
- **With Sqids on, a body that does not carry the key no longer answers `500`.** The deserializer sent the primary key to the sqids branch whenever `UseSqids` was true, without looking at whether the member was in the JSON at all: an absent key became `Decode('')`, which raises. Since `EntityToJSon` always emits the primary key a body that comes from a round-trip has it, but one written by hand without that field is perfectly legitimate and it failed. The branch now reads the value first and does nothing when it is absent or null, which is what every other column already did. A value that is present but not a valid sqid raises `ETJSonException` naming the field, rather than the `EConvertError` that came out of the decoder
- **`DatasetToJSon` no longer raises on the types a report is made of.** The `case` over the field type covered eleven of them and sent everything else to `SNotValidType`, so a `CreateDataset` carrying a `BIGINT` answered `500` through `DatasetToJSon`, and so did every `SUM(CAST(x AS DECIMAL(38,0)))` - the form SQL Server requires for a total - because FireDAC reads it back as `ftFMTBcd`. Added: `ftLargeint`, `ftLongWord` and `ftAutoInc`, which get a JSON value type of their own rather than being squeezed through `Integer`; `ftFMTBcd`, `ftSingle` and `ftExtended`; `ftShortint` and `ftByte`; `ftGuid`; and `ftBytes` / `ftVarBytes`, which come out Base64 like the blobs already did
- **Breaking, and the compiler does not catch it: a `TDate` no longer travels as the day before.** `TDate` and `TTime` were registered on the `TDateTime` serializer, which converts to UTC: a pure date of 2026-03-05 on a server at UTC+1 was emitted as `2026-03-04T23:00:00.000Z`, and a browser rendering only the date part showed the previous day. Neither type has a time zone to convert, so they now have serializers of their own - `2026-03-05` and `10:30:00` - and deserializers that accept both the new form and the full ISO 8601 one, so a client still sending the old shape keeps working. It also removes an exception: `ToUniversalTime` raises on a time that does not exist, which is every clock hour skipped by a daylight saving change
- **The serializer survives being called from inside itself.** `TTJSonContext` holds one `TTJSonSerializer` for its whole life, and `EntityToJSon` overwrote the configuration and reset the level on entry. So the case `docs/json/events.md` documents - a `DoAfterSerialized` that calls the context to serialize something else - came back into the same instance: the outer visit carried on with the inner configuration, and since the event fires between the columns and the details, an inner call with `Details = False` silently dropped the detail collections of the entity being serialized. The level went negative for good measure. Both are saved and restored around the call now. It is nesting, not threading: one thread is enough to hit it
- **A column with no member is left out on the way out, and its empty JSON name matches nothing at the filter gate.** `TTColumnMap.Create(AName)` is public and builds a column map with no member, a shape the mapper itself never produces. The serializer computed the JSON name of such a column before asking whether it could serialize it, which is an access violation, and the HTTP filter matched its empty JSON name against a missing `columnName`. The name is computed inside the check now, and an empty JSON name matches nothing. By its column name such a column is still filterable, like any other column the metadata carry

- **The id of a lazy member is read under the key it is written under.** The deserializer applied `GetName` to the member name and then again inside `SetLazyID`. The fold is not idempotent on a name that begins with two `F` and a capital: `FFTPConfig` is written as `fTPConfigID` and was looked up as `tPConfigID`, so the id was never read, without an error. It is folded once, like the serializer and the metadata do

- **Breaking, and the compiler does not catch it: a `DATE` or a `TIME` read through `CreateDataset` leaves `DatasetToJSon` without a time zone.** `TTJSonValue` put `ftDate` and `ftTime` in the branch of `ftDateTime` and `ftTimeStamp` and wrote all four as `DateToISO8601` of the value converted to UTC. A `DATE` read on a server at UTC+1 went out as `2026-03-04T23:00:00.000Z`, the evening of the day before; a `TIME` went out as a day of 1899 moved by the time zone; and a value on the hour a clock skips raised `ELocalTimeInvalid` inside `ToUniversalTime` and failed the whole report with a `500`. The entry above on `TDate` closed the same fault on the entity path, and the two paths disagreed about the same column - the argument of the entry on exact decimals, for dates. A `DATE` goes out as `yyyy-mm-dd` and a `TIME` as `hh:nn:ss`, both invariant, as the entity path writes them. `DATETIME` and `TIMESTAMP` keep the UTC timestamp. **A client that parsed the old string, or that shifted it back by its own offset, has to read the plain date and the plain time** - except on two engines, where FireDAC does not hand the column over as a `DATE`: on Oracle a `DATE` carries a time and arrives as `ftDateTime`, and so does a `DATE` on Firebird or InterBase in dialect 1, so both still go out as a UTC timestamp. And a negative `TIME` on MariaDB goes out without its sign, `-01:30:00` as `01:30:00`, because `FormatDateTime` writes the absolute value; the public master wrote it as a day of 1899, wrong in a way that showed - 1.0.0 had no MariaDB driver

- **Breaking, and the compiler does not catch it: a list item that is not an object is refused, where it used to be dropped.** `ListFromJSon`, `ListFromJSonArray` and a detail array read inside an entity skipped any element that was not a JSON object, so `[{...}, null]` came back as a list of one and nobody was told. It now raises `ETJSonException` naming the position of the item - and the array, for a detail - which through the listener is a `400` where it used to be a `200`. The check runs over the whole array before the list is built or emptied, so a refused array leaves its own list as it was. The check is per array: an item refused inside a nested detail, or in the second element of a list, surfaces after the outer list has been emptied or partly filled. Everything stays owned, and through the listener it is a `400` all the same
- **A cycle in the object graph no longer runs off the stack.** With `MaxLevels` at `-1` - the value the documentation proposes everywhere - the depth gate is always open, and two entities pointing at each other were followed each way in turn until the stack ran out, one query per level. The serializer now remembers which entities it is inside, by class and primary key, and emits only the reference id when one comes round again: the same output `MaxLevels = 0` gives, so the JSON stays finite and valid and nothing raises. An item of a list that comes round again is left out of the array instead, because an array of entities has no place for a bare id. The check is on the key rather than the instance because a JSON context refuses the identity map, so every step loads a fresh object and two instances of one row are the same entity as far as a cycle goes. An entity with no `[TPrimaryKey]`, such as a `RawSelect` DTO, has no identity to compare and behaves as before
- **Breaking, and the compiler does not catch it: a field name is no longer cut when it starts with an F of its own.** `GetName` removed the first letter whenever it was `f` or `F`, without looking at what followed, so a member named `Fax` came out as `ax`, `FirstName` as `irstName` and `FatturaID` as `atturaID`. The round-trip held, because the same function runs in both directions, but the name on the wire was wrong and it carried through to any generated TypeScript. The prefix is now stripped only when the next character is uppercase, which is what the Delphi convention actually says. A real prefix is still removed, so `FFax` is `fax` as it always was; a member whose name simply begins with an `F` keeps its letter, so `Fax` is `fax` instead of `ax`, `FirstName` is `firstName` and `FatturaID` is `fatturaID`. **Every member whose name starts with `F` or `f` followed by anything but an ASCII capital - a lower-case letter, a digit, an underscore, an accented capital - changes key, in both directions**, because `GetName` runs on the way out and on the way in: a client, or a generated TypeScript type, built on `atturaID` now reads empty and writes nothing, with no error anywhere. Search your entities for a member whose name starts with `F` or `f` and does not continue with `A` to `Z` before upgrading. A member named `F` alone used to have an empty key. **A lazy member whose name starts with two `F` - `FFornitore`, `FFattura`, `FFiliale` - changes too, on the way in**: 1.0.0 folded its name twice when it read the id, so it wrote `fornitoreID` and read `ornitoreID`, and the id a client sent back under the key it had received was ignored. It is read as `fornitoreID` now. A client that learned to send `ornitoreID` is ignored instead, and on an entity that is written whole that sends the foreign key to zero
- **Breaking, and the compiler does not catch it: `DatasetToJSon` no longer HTML-encodes the strings it emits.** Every text value went through `TNetEncoding.HTML.Encode` on its way into the JSON, so `Rossi & Figli` came out of a report built on `CreateDataset` as `Rossi &amp; Figli` while the same name from an entity endpoint came out intact. Inside JSON that encoding protects nothing - `TJSonString` already escapes what has to be escaped - except a client that put the value into a page as HTML, which was protected by accident and has to encode it itself now; and it corrupted the value while costing an encode per field per row: fifty thousand of them on a report of five thousand rows by ten columns. The lower-cased field names stay as they are, and the reason is now written in `docs/json/serialization.md`: they come from the database, where the case depends on the dialect, so there is no camelCase to recover
- **Breaking, and the compiler does not catch it: a detail collection left out of the body, or sent as `null`, is left as it was when you deserialize onto an entity you already have.** The deserializer prepared the list before reading the field, so a body without the key emptied the collection in memory. It prepares it now only when the field is an array. On an entity already read - through `TTJSonDeserializer.EntityFromJSon`, public since 1.0.0, or the `EntityFromJSon<T>` and `EntityFromJSonObject<T>` overloads that take an entity, new in this release - a collection the body does not carry keeps the rows the entity had, which is what the serializer means when it leaves a collection out past `MaxLevels` - "not included at this depth", not "no rows". Code that reads the collection after deserializing over an entity saw an empty list and now sees the rows it had. On a fresh entity, which is what `EntityFromJSon<T>(AJSon)` builds, a collection the body does not carry still comes out with no rows: its detail list carries key 0, so reading it runs one query that finds none unless a detail row carries key 0, where it used to come out empty with no query at all. An empty array still empties it
- **Breaking, and the compiler does not catch it: a detail collection that is not an array is refused instead of ignored.** The deserializer read it with the RTL's `GetValue<T>(path, default)`, whose behaviour changed under Trysil's feet: up to Delphi 11 that overload converts without a guard and raises `EJSONException`, which reached the client as a `500`; from Delphi 12 it goes through `TryGetValue` and returns the default, so `{"rows": {}}` silently deserialized an entity with no rows at all. It now raises `ETJSonException` naming the field on every version, which the HTTP listener already answers as a `400`. The reading itself moved to `TTJSonValues` in `Trysil.JSon.Types`, which separates *absent* from *present and unreadable* - the distinction the RTL overload collapses
- **An `Int64` can arrive as a quoted number, on every Delphi version.** JavaScript cannot hold a whole number above 2^53, so a client that has one has no choice but to send it as a string, and whether that string was read depended on the RTL rather than on Trysil: `TJSONString.AsTValue` converts it through `StrToInt64` on Delphi 11 and on Delphi 13, so `"42"` already arrived as 42 there. The deserializer reads the digits itself now and falls back to the numeric path, the same shape `Currency` has on the public master, so the answer no longer depends on the version you compile with. **Not counted as a break**: on Delphi 11 and 13, where the RTL was read, the quoted number was accepted already; 10.3, 10.4 and 12 were not checked. The outgoing direction is unchanged - every number goes out as a JSON number - and `docs/json/serialization.md` now says so plainly instead of claiming that `Currency` is emitted as a string, which it never was
- **`MetadataToJSon<T>` reports `precision`.** Column metadata carried `size`, which for a decimal column is the **scale** and not the length, so a client had no way to know how many integer digits a column accepts: `decimal(19,4)` was `"size": 4` and nothing else. Emitted only when non-zero, like `size`, so an existing payload only gains a key
- **Breaking, and the compiler does not catch it: `MetadataToJSon<T>` no longer describes a member it never serializes.** `TableMetadataToJSon` walked the mapped columns and described every one of them, without the `CanSerializeColumn` test that `ColumnsToJSonObject` applies two methods above. So a member marked `[TJSonIgnore]` - which is what three pages of this documentation suggest for a `PasswordHash` - appeared in no response and appeared in the metadata with its name, its type and its size. What makes it worth a line rather than a note is the field beside them: the payload also carries `"filterable"`, so it handed a client the exact list of columns that are never serialized and are still reachable through a filter, which is the target the `[TNotFilterable]` page describes - `LIKE` plus a row count recovers a value one character at a time. The oracle is a known and accepted cost; publishing its menu was not. The metadata now describe what the entity serializes **or** deserializes, and say which. Only a member that does neither - `[TJSonIgnore]` - is left out. The direction is declared the way `filterable` already was, by writing the exception only: `"readable": false` on a member the body may write and no response returns, `"writable": false` on one that is returned and never read from the body, which includes every change tracking column because the deserializer refuses those. A member that goes both ways gains no key, so a payload of ordinary columns is unchanged. The metadata are a two-way contract because the host reads them as one: a client building a create form from them would otherwise never learn that the password field exists
- **The key and the version column obey the same filter, and an entity without a version column can be described at all.** The `CanSerializeColumn` test above was added to the loop that fills `properties` and not to the two pairs written before it, so an entity that keeps its key or its `[TVersionColumn]` out of the JSon saw them vanish from the list and stay named at the top. Both pairs now pass the same test. Beside it, a fault nothing had reached: `ATableMap.VersionColumn` is `nil` for an entity that has none - which is legal, and is what `TTUpdateMode.KeyOnly` exists for - and it was dereferenced without asking, so `MetadataToJSon<T>` on such an entity was an access violation. Every other place in the framework that touches that field guards it; this one did not, because no test had ever described an entity without a version column.
- **`MetadataToJSon<T>` describes a `[TJoin]` entity, where it used to describe nothing.** The columns of an entity with joins leave the select as `Table.Column AS Alias`, and the metadata are registered under that alias - including the columns of the FROM table, which get one too. The description looked each column up by its bare name, so every lookup missed and `properties` came out as an empty array. The rest of the file already used the lookup name; this line did not. It matters more since this release, because the metadata are now a two-way contract: on a join entity they declared nothing at all.
- **A `CHAR` column serializes instead of raising.** The three lists of textual field types - the one that binds a parameter, the one that decides whether a `LIKE` is allowed, and the one that turns a field into JSON - were not the same list. The third was missing `ftFixedChar` and `ftFixedWideChar`, and it ends with a `raise` rather than a permissive `else`, so `DatasetToJSon` on a dataset holding a `CHAR` or an `NCHAR` did not return a string: it raised. The same column could be written and filtered and not serialized, on the reporting path - `CreateDataset` into `DatasetToJSon` - that the converter exists for.
- **An Oracle `CLOB` is text on the two paths that read it, not only on the one that writes it.** Oracle reports a `CLOB` as its own field type, and the entry above registers it among the string parameters so the column can be written. Two lists that read were left behind: `DatasetToJSon` raised on it instead of returning a string, so a report read with `CreateDataset` that reached a `CLOB` on Oracle failed where it worked on the other six; and the server-side filter did not count it as a string column, so a `LIKE` on the same entity was accepted everywhere and answered `400` on Oracle alone.
- **A serialization re-entered from an event has a ceiling.** `EntityToJSon` starts a depth and a visited set of its own, so that a nested call is not cut short by the state of the one around it. That is right, and it means neither `MaxLevels` nor the cycle guard reaches across a re-entry: two entities whose `DoAfterSerialized` serializes the other recur until the stack gives out. Sixteen re-entries is now the ceiling, and the seventeenth raises naming the count. Nothing that returns before calling again is affected.

- **Breaking, and the compiler does not catch it: a serializer you register yourself is now a single instance shared by every thread.** `TTJSonSerializers` and `TTJSonDeserializers` kept a class per type and built an instance every time a value was converted; they keep one instance per type now, built at registration and destroyed when the unit finalizes. Every serializer in this repository is field-less, so for them the change is invisible and it saves an allocation per value. `Register<T>` is public, though, and `docs/http/server.md` documents it as an extension point: a serializer of your own that keeps state between calls - a buffer, a counter, a cached format - goes from one instance per call to one instance shared by every request thread, with no lock around it, and its destructor now runs at finalization rather than at the end of a conversion. Make it stateless, or move the state to a local

- **Breaking, and the compiler does not catch it: an exact decimal read through `CreateDataset` and written by `DatasetToJSon` keeps its digits.** `TTJSonValue` put `ftCurrency` and `ftBCD` in the same branch as `ftFloat` and read them with `AsFloat`, so a decimal total lost everything past the fifteen significant digits `FloatToStr` writes, with no error and no warning: the number that reached the client was plausible and wrong. `ftFMTBcd` - which is what a `SUM(CAST(x AS DECIMAL(38,0)))` on SQL Server or a `sum(bigint)` on PostgreSQL comes back as - was not in that branch in 1.0.0: it raised, as the entry above on the types a report is made of says, and for a few days of this release's history it joined the branch and rounded like the other two. The same column read into an **entity** member of type `Currency` was exact the whole time, because `TTJSonCurrencySerializer` writes the decimal literal, so the two halves of this library disagreed about the value of the same column depending on which way you read it. The three exact types now go out as their exact literal as well, `ftCurrency` through `CurrToStr` and the two BCD types through `BcdToStr`, both invariant. **It is still a JSON number**: a `TJSonNumber` built from a string validates the digits and then keeps them, and writes them unquoted, which is what the entity path has always done - the type on the wire does not change, only the digits do. One place the fix does not reach, and it is worth knowing: `ftCurrency` is `TCurrencyField`, which descends from `TFloatField` and is already a `Double` in the field layer, so what this corrects there is this library's half of the path and not the field's - and on PostgreSQL that includes every narrow `NUMERIC`, see the entry on `money`. `RawSelect<T>` is not on this path at all: it fills entities, whose members go through the entity serializers, so a `Double` member of a DTO rounds as a `Double` does. Map a total as `Currency`. One edge: a `ftCurrency` value within about 0.02 of the limits of `Currency` rounds past `MaxCurrency` in its `Double` and raises `EInvalidOp` on `AsCurrency`, where `AsFloat` let it through. `TTJSonValue`, the record behind this path, is public, and the exact literal is a value type of its own inside it: its implicit conversions to `Double` and to `String` accept it, the first as the number and the second as the literal, so a host that read a decimal through the record as a `Double` reads it as it did in 1.0.0 - through `CurrToStr` for a `ftCurrency`, so to four decimals - and one that reads it as a `String` gets the literal, where 1.0.0 raised

- **The Sqids alphabet is configurable, once.** `TTJSonSqids.Instance.Alphabet` sets the alphabet the encoder shuffles. The default is the same string 1.0.0 used and the length is still 8, so an application that does not touch it emits exactly the ids it emitted before; the constants it replaces were `strict private`, so nothing that compiled stops compiling. It is **configure-once**: the encoding is built lazily on the first `Encode` or `Decode`, and a write after that raises `SSqidsAlphabetInUse` instead of quietly invalidating every id already handed out - set it at startup, in the same place the `Register*` calls go. It must be at least five characters (`SSqidsAlphabetTooShort`), must not repeat one (`SSqidsAlphabetNotUnique`) and must hold no capital letter and nothing outside ASCII (`SSqidsAlphabetNotLowerCase`), all checked before the lock is taken. The last rule is not a matter of taste: every id is lower-cased on its way out and on its way in, as in 1.0.0, so a client that sends an id in capitals is still read; with a capital in the alphabet that fold turns an id into another string made of the same alphabet, which decodes to another number, and a `DELETE` on the id the server handed out reaches another row. The default alphabet of `TSqidsEncoding` has capitals, which is why the check is here. A character outside ASCII is refused by `TSqidsEncoding` itself, but at the first encode of a request rather than at startup. Like the rest of `TTJSonSqids` the property lives under `{$IF CompilerVersion >= 36}`, because `TSqidsEncoding` is an RTL 12 type: on 10.3, 10.4 and 11 the class compiles without it, as it always has

### HTTP

- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): an RS256 key that is not RSA is refused when it is built.** `PEM_read_bio_PUBKEY` reads any public key - a PEM public key header says `BEGIN PUBLIC KEY` whatever the algorithm underneath - and `EVP_DigestVerify` then verifies with the algorithm the key names. A host that configured an EC key by mistake was verifying ECDSA signatures while the token header said `RS256`, successfully, with nothing anywhere to say the algorithm in use was not the one declared. `TTHttpJWTRSAPublicKey` and `TTHttpJWTRSAPrivateKey` now check the key type in the constructor and raise `ETHttpJWTException`. The check resolves `EVP_PKEY_base_id`, falling back to the OpenSSL 3 name `EVP_PKEY_get_base_id`, so it works against 1.1.1 and 3.x alike
- **Breaking, and the compiler does not catch it: the tenant configuration no longer runs inside the write lock.** `TTMultiTenant<T>.CreateTenant` called `RegisterConnection` - and through it the host's `GetConnectionName` and `GetParameters` - while holding `FLock.BeginWrite`, so a `GetParameters` that reads a file or queries a directory stalled the first access of *every* other tenant, and every reader with it. The documentation of the public master said the opposite, in as many words. The config is now built and the connection registered before the lock is taken, and the lock is held only to publish the tenant. Two threads racing on the same new tenant now both register the connection, which is a no-op the second time: `TTFireDACConnectionPool.RegisterConnection` compares the parameter signature and refuses only a different one. So the constructor of the config, `GetConnectionName` and `GetParameters` can run on two threads at once, and twice for the same tenant. **What changes for an application**: in 1.0.0 the constructor of the config and `GetParameters` ran under the write lock, once per tenant, and on the public master `GetParameters` still did, on the thread that won the race. Now both can run on two threads at once, and twice for the same tenant: make them thread-safe, and have `GetParameters` return the same parameters every time, or the second registration is refused
- **Breaking, and the compiler does not catch it: `GetOrAdd` refuses a tenant name that cannot be one**, with the new `ETTenantNameNotValid`. It took any string and built a connection definition out of it, and a tenant name is almost always request data - a header, a subdomain, a claim - that most applications turn into a database name or a path. A name must now start with a letter or a digit and hold at most 63 of those plus `_`, `-` and `.`, which is a floor and not a substitute for resolving the name against the tenants that exist. The new exception descends from `ETTenantUnavailable`, so a host that already catches that keeps working and can catch the narrower one first to answer `400` instead of `404`; `TTTenantName.IsValid` is the same test, callable before `GetOrAdd`. **What changes without a compiler error:** an application using tenant names outside that alphabet - a space, a colon, a leading dot - now raises
- **Breaking for a client of the server, not counted: a request body is capped at 1 MB by default.** Nothing bounded it before, on any route: Indy read the whole body into memory, `TTHttpRequest.Content` then materialized it as a `String`, and a body of *n* bytes cost several times *n* before any handler saw it, so one client could ask the process for as much memory as it wanted with no token and no route that exists. `TTHttpServer<C>.MaxRequestContentLength` (default `1048576`, `0` for the old unbounded behaviour) is the ceiling: a request that declares more is answered `413` from `OnHeadersAvailable`, before a byte of the body is read. A client can also send a chunked body carrying no length, or lie about the one it sends, so with a ceiling set the server also hands Indy a `TTHttpCappedStream` that refuses to grow past it - a memory bound rather than an exact byte count, since it can overshoot by the allocation slack of `TMemoryStream`, and it ends as a dropped connection rather than a `413`. **What changes without a compiler error:** an application that accepts bodies over 1 MB - a document upload, a large batch insert - must raise the ceiling
- **Breaking for a client of the server, not counted: a `POST` that declares itself another method through a header is refused with a `400`.** Indy replaces the command with what `X-HTTP-Method-Override`, `X-HTTP-Method` or `X-METHOD-OVERRIDE` names, before Trysil sees the request, and nothing in the library asked whether that was wanted. Everything that filters on the request line - a reverse proxy allowing `POST` and blocking `DELETE`, a WAF rule, an alert on deletions - is walked past by one header, and the route Trysil resolves is the one the header asked for. The new `TTHttpServer<C>.AllowMethodOverride` (default `False`) is where an application that needs the override says so; `TTHttpRequest` gained `Method`, `SentMethod` and `IsMethodOverridden`, so the two readings are both available whichever way it is set. **What changes without a compiler error:** a client relying on those headers now gets a `400`
- **Breaking (compilation): the resourcestring `SForbiddenArea` is gone.** It is `SForbiddenAreaLog` now, it reads `Access forbidden: %0:s - missing area: %1:s.`, and it stops the build of one unit that nothing in this repository compiles: the language unit of a host that has translated the framework messages, which names the constant and not its text - the pattern `Demos/Languages/README.md` teaches and the two versioned example units follow. Rename it there. The old string read `Access forbidden: %0:s - Area: %1:s.`, and in 1.0.0 it was the body of the `403` sent to a caller missing an area - which told an unauthorized caller the name of the area it needs. A `403` answers with `SForbidden` now, which names the route and not the area, and the area the caller is missing goes to the **log** through `SForbiddenAreaLog`: a client that read the area out of that message finds the route there instead. Leaving the old constant exported would have meant a translator paying for a string nobody emits, and an invitation to start emitting it again
- **`ETDataIntegrityException` answers `500`, and now a test says so.** It is raised when a command written for one row reports more than one affected, which means the key it filtered on is not unique: the caller asked for nothing wrong and can do nothing about it. Nothing had pinned the contract in either direction, so the behaviour is unchanged and now stated - the status, and that the body stays the constant one carrying only the task id, with what the database said kept for the log
- **A route that answers the request method is no longer hidden by one that does not.** When the address carried a placeholder, the router took the first pattern that matched segment by segment and, if that pattern's controller did not declare the request method, answered `405` without looking at the other patterns. Two controllers sharing a base URI is enough to reach it - `[TGet('/find/?')]` on one and `[TDelete('/?/?')]` on the other, which is what the demo in `Demos/APIRest` writes - and which of the two came first was the iteration order of a hash dictionary, so the same application answered differently depending on how the routes hashed. The search now keeps going until it finds a pattern that carries the method, and falls back to the first match for the `405` when none does. The same hole was open one step earlier: a request whose address matched a route **exactly** was answered `405` when that route did not declare the method, without the parametrized routes ever being tried, so `[TGet('/2024')]` on one controller hid `[TDelete('/?')]` on another. Route resolution is now one question asked in one place - exact address, then patterns, then catch-all, each of them only when it answers the method - and `405` means no route matching the address answers it
- **Breaking, and the compiler does not catch it: a route with a placeholder before a fixed segment is refused at registration**, with `SNotValidParametrizedUri`. `[TGet('/?/detail')]` was accepted and matched `/anything/detail`, but the router has always assumed placeholders sit at the end - it is the assumption that makes "first match wins" defensible - and nothing enforced it. It now fails on `RegisterController`, where the route is written, instead of resolving at random. What the framework still does not refuse is two patterns of the same shape that both answer the same method, `[TGet('/2024/?')]` beside `[TGet('/?/?')]`: a literal segment beside a placeholder is a legitimate special case, so the pair is documented rather than rejected
- **Breaking, and the compiler does not catch it: `TTHttpServer<C>.Start` refuses to start when a route requires authentication and no authentication class is registered.** Both authorization gates in the listener were guarded by `Assigned(FRttiAuthentication)`, so a `RegisterAuthentication` that never ran - one left inside a conditional branch, an initialization order that changed - turned every route, `[TArea]` ones included, into an anonymous one, silently, with the server answering `200` and every functional test still passing. The check runs before the socket is bound, so a refused start leaves nothing listening. **A route without `[TAuthorizationType]` requires authentication by default**, so this affects every server that never registered an authentication class, not only those using `[TArea]`: set the new `AllowAnonymous := True` to declare in one line that the server is meant to serve every route anonymously
- **`OnRedactContent: TFunc<TTHttpRequest, String, String>`** on `TTHttpServer`, next to `OnCanLog`: receives the request and the content, returns what gets logged. Headers were already redacted through a fixed list; bodies were not, so in a JSON API the log held the password of every `POST /login` and the token in every login response. `OnCanLog` was the only lever and it is all-or-nothing per request. The hook is applied to the request body and the response body, and is `nil` by default, so nothing changes for an application that does not set it. It does not reach the query parameters, which go through the redaction list below
- **Breaking, and the compiler does not catch it: an empty HMAC secret is refused when signing, and fails closed when verifying.** `TTHttpJWTHS256Payload` used to hash with whatever `GetSecret` returned, empty string included: every signature it produced could be reproduced by anyone, so a token signed with it proved nothing, and the reading side accepted those tokens as valid. Signing now raises, because there the empty secret is the host's own misconfiguration and no caller is involved. **Verifying does not raise**: it returns `False`. The distinction matters because verifying is the anonymous path and `ETHttpJWTException` descends from `Exception`, not from `ETHttpException` - an exception there would reach the listener's generic branch and answer **500** to a caller who sent no credential at all. An application doing key rotation whose `GetSecretFor(AKeyID)` returns an empty string for a `kid` it does not recognise - the natural reading of "fail closed", and what the RS256 twin already does with a `nil` key - now gets the `403` it deserves
- **Query and route parameters now go through the same redaction list as headers.** They were logged through the overload that forces redaction off, so a parameter named like a redacted header was logged in clear. Note the scope: that list holds header names (`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`), so a parameter called `token` or `password` is **still logged in clear** - keep secrets out of the URL, and use `OnCanLog` to drop the whole entry for routes that carry them
- **Breaking (compilation): the one-argument `TTHttpLogNameValues.Create` is gone.** It built the log copy of headers and parameters **without redaction**, which is the hole closed earlier in this release, and nothing in the library had called it since. Use the two-argument overload, which takes the redaction flag explicitly
- **A logged body that is not JSon no longer vanishes from the log entry.** The request and response items embedded the body with `TJSonObject.ParseJSONValue`, and a `nil` value does not survive `AddPair`, so a body that failed to parse never reached the entry: on Delphi 10.3 to 12 the pair is dropped, leaving neither a `Content` key nor a `ContentOmitted` flag, and on Delphi 13 the RTL substitutes a `TJSonNull`, writing `"Content": null`. The log entry therefore differed by compiler. The obvious use of the new `OnRedactContent` hook - returning `'***'` in place of the body - hit exactly that: the redacted body disappeared instead of being logged as redacted. A content that does not parse is now written as a string
- **A text response body is copied once instead of twice.** `GetContentStream` built a `TBytes` with the whole body and then copied it again into the `TMemoryStream` handed to Indy. It now sizes the stream from `GetByteCount` and encodes straight into it, so a JSON response of any size costs one pass rather than an allocation plus two. The binary branch is unchanged: removing its copy would mean taking ownership of the caller's stream, and `ContentStream` is a public property
- **Breaking (compilation): a free parametrized route can no longer cover a protected sibling, and `TTHttpListener<C>.Create` no longer takes an anonymous-route list.** Whether a request had to be authenticated was decided **before** the route was resolved, by a second matcher of its own: `InternalIsFreeController` walked a list of anonymous routes in registration order, comparing segment by segment, and a `?` there matches anything `Integer.TryParse` accepts. The router then resolved the route by a different rule - exact string first, segments second, `'*'` last. The two disagree whenever a free parametrized route and a protected literal route share a shape: with `[TGet('/?')]` marked `None` and `[TGet('/2024')]` left protected under the same `[TUri('/report')]`, `GET /report/2024` with no credentials was read as anonymous by the first matcher and resolved to the protected method by the second, which then ran - `[TArea]` was the only thing left in its way. Two parametrized routes that both match, `/x/?/2` free and `/x/1/?` protected, disagreed non-deterministically, one side iterating a dictionary and the other a list. The route is now resolved once and the decision reads `AuthorizationType` off the method that will actually run, which is where the attribute had been recorded all along; the second matcher, the list it walked, and the `TTHttpFreeControllerID` record built for it in this same release are gone. A route that does not exist still answers `401` to an anonymous caller rather than `404`: a failed resolution runs authentication before re-raising, so resolving first does not turn the router into an enumeration oracle. `TTHttpControllerID` keeps the public `CommandType` it gained here
- **A column with no mapping behind it is not filterable.** `TTColumnMetadata` decided the flag as "filterable unless the mapping says otherwise", and read the mapping only when it had one, so a column metadata built without a `TTColumnMap` came out filterable. Inside the library it is unreachable - the probe selects the mapped columns and finds every one of them again, so a `TTColumnMap` is always there - but the constructor and `TTColumnsMetadata.Add` are public, and their three-argument overloads take no mapping at all: metadata assembled by hand, in a test double or in a host that builds its own, handed the filter a set of columns it was willing to filter on. The flag now reads `Assigned(AColumnMap) and AColumnMap.IsFilterable`, so the absence of a mapping closes the column instead of opening it. Nothing changes for an entity that goes through the probe
- **Breaking, not counted because the code it hits could not work: `BaseUri` refuses an address.** It is a path prefix: `SetBaseUri` prepends a `/` when one is missing and `RegisterController` glues it in front of every route, so `BaseUri := 'http://localhost'` - which four pages of the documentation showed - registered `/http://localhost/api/persons` and every other route the same way. The server started, reported itself listening, and answered `404` to everything, with nothing anywhere saying why; the address it listens on comes from the port and the bindings and never from here. A value containing `://` now raises `ETHttpServerException` with a message that says what `BaseUri` is for. The pages are fixed too, and the property table says it in words
- **Breaking (compilation): `TTHttpCorsController.Headers` and `.Methods` are `TTHttpCorsValues`, not `String`.** They used to be strings assembled by hand, which is where the duplicated and mis-cased entries came from; they are now the collection type that owns the allowlist. Reading them still tells you what a route allows, but not as a string you can concatenate
- **Breaking, and the compiler does not catch it: `TTHttpResponse.ContentEncoding` writes the charset, not the `Content-Encoding` header.** It used to read and write `TIdHTTPResponseInfo.ContentEncoding`, which on the wire is the transfer coding - `gzip`, `deflate` - while every value Trysil offers for it (`TTHttpContentEncodingTypes`: `utf-8`, `iso-8859-1`, `ascii`, `ansi`) is a **charset**. So the property was putting a charset into the wrong header, and it now reads and writes `CharSet`, which is what those values mean. Nothing breaks at compile time, and a controller setting `utf-8` finally has the effect it always looked like it had - but a controller that had learned to put `gzip` there is now setting a charset called `gzip`, and must set the header itself instead
- **Breaking, and the compiler does not catch it: an error response no longer inherits the content type and headers of the handler that failed.** `MakeResponse` set the status and the body and left everything else alone, so a controller that had already declared `application/pdf` and `Content-Disposition: attachment; filename=invoice.pdf` before failing to find the row sent a `404` whose body was JSON, whose type said PDF and whose headers still told the browser to save it: the client downloaded an `invoice.pdf` containing an error message. The listener now marks how many headers are set **before** it invokes the controller method, and an error response removes only those added after that point, then restores the JSON content type and charset. What the framework itself sets earlier survives, which matters: `WWW-Authenticate` on a `401`, and the CORS headers, without which a browser cannot read the error at all. When the controller method was never reached - an exception anywhere before it runs, from routing to the controller's constructor - there is no mark, and nothing is removed. **What changes for an application**: a header a controller method sets before raising - a `Retry-After`, a `Location`, a `WWW-Authenticate` of its own - no longer reaches the client, whatever the exception. The mark is taken after the controller is constructed, so a header set in its constructor survives; and the mark counts headers, so a header that was already there and that the method overwrites with a value keeps the method's value. To send it, set the status code and the body on the response and return, instead of raising
- **`Accept-Language` is parsed, so translations actually happen.** The header was stored whole and compared against the language a translation was registered under, so `it-IT,it;q=0.9,en;q=0.8` - what a browser sends - never matched `it`, and an application that had called `TTHttpLanguage.Add('it', ...)` got English for ever without a hint as to why. The header is now split, ordered by `q` rather than by the order the tags appear in, and each regional tag is followed by its primary one, so `it-IT` falls back to `it`. Lookup walks that list and takes the first language that has the key, which also means a translation registered for `it-CH` wins over the generic `it` for a Swiss client. A language nobody registered still resolves to the key itself, as before
- **A `405` carries the `Allow` header.** The router refuses a method by looking it up in the dictionary of the methods that route does answer - so it holds the list at the very moment it decides to say no, and threw it away. Without `Allow` a client learns that it got it wrong but not what to use instead, which is the one thing that status exists to tell it. The list now travels on the exception, which is what reaches the listener from the router, and is written as a header on the response
- **`ContentLength` counts bytes, not UTF-16 characters.** It returned `FContent.Length`, while `Content-Length` on the wire is a byte count of the UTF-8 body: for anything outside ASCII - which in Italian is most text - the two differ. Only the log reads the property, so nothing on the wire changes; what changes is that the length written in the log stops disagreeing with the response it describes
- **A percent-encoded path reaches the route it names.** Routing compared `TIdHttpRequestInfo.Uri`, which is the raw request line, so `/api/pe%72sons` did not resolve to `/api/persons` and `/persons/%31` did not resolve to id 1: both came back `404` although they name exactly what the client asked for. The URI is now decoded **per segment, after the split** - not through Indy's `Document`, which decodes first and would therefore let a `%2F` act as a path separator, handing a client the ability to invent a boundary between segments. A segment that decodes to something containing a slash is left encoded, so it simply does not match. `+` is not read as a space: in a path it is an ordinary character, and the decoder is called without `PlusAsSpaces`
- **Breaking for a client of the server, not counted: a malformed request body is refused, where it used to be read as an empty object.** `TTHttpRequest.JSonContent` handed the body to `ParseJSONValue` and, when that returned `nil`, put an empty `TJSonObject` in its place: a body truncated by the network, or one that was never JSON, reached the controller as `{}` and nothing said so. The status code was the smaller half of it. The larger half is the filter: `TTHttpFilter<T>` reads a missing `where` as *no condition* - which is right for a request that carries none - so a **select endpoint answered `200` with the whole table, up to `MaxLimit`, for a request whose body had been cut in half**. A body that is not empty and does not parse now raises `ETHttpBadRequest`, which the listener answers as `400`. **What changes without a compiler error:** a request that carries **no body at all** still reads as an empty object, so a `GET` handler that touches `JSonContent` is unaffected; a handler that relied on a malformed body degrading to `{}` now sees the `400` instead
- **Breaking, and the compiler does not catch it, for a host that calls the deserializer itself: a malformed JSON body answers `400`, not `500`.** `ETJSonException` was not in the listener's chain of handlers, so anything the deserializer refused - unparsable JSON, an array where an object was expected, a value of the wrong type - fell into the generic branch and came back as a server fault. It told the client that the server was broken when the request was, and a client retrying the same body got the same answer for ever. That held for what the deserializer refused on its own, and not yet for what the RTL refused under it: a value the RTL could not convert - `{"age":"abc"}`, a malformed time or date - raised `EJSONException`, `EConvertError` or `EDateTimeException`, and JSON that did not parse, handed to the overloads of `TTJSonContext` that take a string, raised `EJSONParseException`. None of them is an `ETJSonException`, so all of them still answered `500`. They are turned into one now: a conversion that fails raises `SNotValidJSonValue`, naming the field, and JSON that does not parse raises `SNotValidJSon`, carrying the message of the parser. The classes turned into `ETJSonException` are `EJSONException` and its `EJSONParseException`, `EConvertError`, `EDateTimeException`, `EArgumentException`, `ERangeError`, `EIntOverflow`, `EMathError` and `EVariantError`, raised by any deserializer, the host's included; anything else keeps its class and stays a `500`. What counts as a value of the wrong type is still the RTL's call, as in 1.0.0: `true` sent for a number reads as `1`, and a number or a boolean sent for a string reads as its literal, both with a `200`. **A host that calls a deserializing method of `TTJSonContext` - `EntityFromJSon`, `EntityFromJSonObject`, `ListFromJSon`, `ListFromJSonArray` - outside the listener and catches `EJSONException`, `EJSONParseException`, `EConvertError` or `EDateTimeException` around it has to catch `ETJSonException` instead**. `ETDataIntegrityException` stays at `500`, and now by decision rather than by omission: it is raised when a write by primary key affects more than one row, which means the database is not in the state the ORM assumes, and there is nothing the caller can change to make it pass
- **Breaking for a client of the server, not counted: a `Smallint` member refuses a number it cannot hold, where it used to store it cut.** For a host that calls the deserializer itself it is part of the counted entry on `ETJSonException`. `Int16` was registered on the deserializer of `Integer`, which reads a 32-bit value, and `TValue.Cast` copies an integer into a narrower one without a range check: `{"piccolo": 70000}` stored `4464` and answered `200`, on the column type Trysil Expert generates as `Smallint`. It was so in 1.0.0 too. `Int16` has a deserializer of its own now, which raises `ERangeError` outside -32768 to 32767 - one of the classes the entry above turns into `ETJSonException`, so the client gets a `400` naming the field, and a `TTNullable<Int16>` goes through the same deserializer. A body that stored a wrong number with a `200` is refused now
- **A `400` for a value the deserializer could not convert keeps the exception behind it, in the log.** The entry above on the malformed body turns eight classes into `ETJSonException` naming the field, and the class and the message of the failure travelled only in `NestedExceptionClassName` and `NestedExceptionMessage`, which the `400` path never writes, and the listener writes a `400` to the log through `LogAction`, not `LogError`. In the deserializers of the framework that loses nothing, because the eight always come from the value; in one the host registered they can come from a defect - an index out of range, a `StrToInt` on a setting - and nothing anywhere said so. The failure is now attached as the `InnerException` of the `ETJSonException`, through `Exception.RaiseOuterException`, and the log line of the `400` carries its class. Only the class: the message of a conversion of the RTL quotes the value the client sent, and it would reach the log with no cap on its length and without going through `OnRedactContent`, which covers bodies only - on a writer that stores actions in a bounded column, a long value would also lose the line. The body sent to the client does not change. How a deserializer of the host tells the two faults apart is written in `docs/json/deserialization.md`. What the line still carries is the message of the `400` itself, which is the client's too: for JSON that does not parse, handed to `EntityFromJSon` or `ListFromJSon` as a string, that is the parser's message, and it names the path of the keys the client sent
- **Breaking, and the compiler does not catch it: request and response bodies are no longer captured in the log by default.** `MaxContentLength` was 64 KB in the registration overloads that do not take the parameter record, and `LogRequest` runs **before** authentication, so a `POST /logon` was written to the log with the credentials in it and the response with a valid token - which is what the REST demo did. Redaction is and remains the host's job, because Trysil cannot know what is sensitive in a payload: a password may be called `password`, or `pwd`, or `p`, and any list of names would be incomplete. What the default decides is only what happens when the host has decided nothing, and it now decides not to capture. Raise `MaxContentLength` when you want bodies, and assign `OnRedactContent` in the same breath. The REST demo keeps capturing them and now shows the pair: it redacts the body of its logon route
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): the short constructors of `TTHttpLogParameters` mean the same defaults the server means.** `Create(threads, capacity)` filled the two values it was not given with `-1`, which is *no cap*, so `RegisterLogWriter<W>(TTHttpLogParameters.Create(4, 20000))` - the natural way to raise only the pool and the queue - handed back the unlimited body capture the entry above says was closed, `POST /logon` included. The host had decided nothing about the body and got the opposite of what the server decides when nobody says anything. The unsaid values are now the server's own defaults, `0` for the content and `128` for the item count, and the four are public on the record - `TTHttpLogParameters.DefaultThreadPoolSize` and the three beside it - so the server no longer keeps a second copy of them. An explicit `-1` still means no cap: it is a decision, and it is written down. An explicit `0` is not, on the item count: it reads as the default of 128, so an application that wrote `0` to say *no headers and no parameters in the log* gets them back, up to 128. There is no other way to say it, and the two neighbours are deliberately asymmetric: `0` on `MaxContentLength` means no body, because a body of zero bytes is not a thing anyone logs, while `0` items would only ever be a way of writing *off*, and off already has a spelling - do not log at all. If you want the headers out, leave them out with `OnCanLog` or read them out in your writer. At the other end, `Default(TTHttpLogParameters)` gave zero threads and a queue of zero, which writes nothing and says nothing about why; a queue of zero and a pool of zero or less now read as the default, the same shape `TTHttpFilterParameters.GetMaxLimit` already had. A **negative** queue still means an unbounded one, which is what it always meant
- **The response log line can carry the tenant.** Trysil ships per-database multi-tenancy and a structured request log, and the two halves did not meet: no log record had a slot for the tenant, and a host could not add one - every field is `strict private` and filled in the constructor, `TTHttpLog` is `strict private` inside `TTHttpServer<C>`, and a thread variable is no way out because `LogRequest` and `LogResponse` enqueue while the writer runs on the pool. So after an incident on an installation with N databases the log said who, what and when, and not on which: the only correlation was `Host`, which serves whoever separates tenants by subdomain and nobody else, while the two ways the documentation recommends - a header and a JWT claim - left nothing. `TTHttpUser` now carries a writable `Tenant` and `TTHttpLogUser` copies it into `ToJSon` beside `Username` and `Areas`. Nothing fills it automatically, because nothing in the framework resolves a tenant: the host writes it where it already writes the username, in the `Check` of its authentication class
- **The preflight answers the same way for every route, this time including the list of methods.** The change below listed `Authorization` on every route and gave an unknown path the same headers as a known one, which closed half of it: `Access-Control-Allow-Headers` became uniform. `Access-Control-Allow-Methods` did not. A known route was answered with the verbs its controller had registered, an unknown one with the whole of `TTHttpMethodType` - and **no controller can register `OPTIONS`**, because no attribute produces one. So the presence of `OPTIONS` in that header was a clean "this route does not exist", readable without a credential, and the rest of the list said which verbs the route answered. The list is now the whole enumeration on every URI. The test that was supposed to guard this compared two preflights in a fixture that never registered anything with `TTHttpCors`, so both took the unknown-route branch and the comparison was true of nothing; the fixture now registers the way the server does
- **A CORS preflight answers the same way for every route, and says how long the answer is good for.** `OPTIONS` is served before authentication - it has to be, a browser sends it without credentials - and what came back described the route: nothing at all when the path did not exist, and `Authorization` among the allowed headers only when the route required it. Two preflights therefore told an anonymous caller which paths exist and which of them are open, without a token. `Authorization` is now always listed and an unknown path gets the same response as a known one, which costs nothing: the browser sends the preflight and then the real request, and it is there that authentication decides. Added with it: **`Access-Control-Max-Age`**, default 600 seconds and settable through `CorsConfig.MaxAge`. Without it a browser repeats the preflight before every non-simple request, doubling the round trips of the entire application - one header for half the traffic
- **A method the router does not support answers `405`, not `500`.** `GetMethodType` raised `ETHttpServerException`, which is not an `ETHttpException` and therefore fell into the listener's generic branch: `HEAD`, `TRACE` and `PATCH` came back as server faults. Indy routes `hcHEAD` to the GET handler, so a `curl -I` or any health check counted as an error. It now raises `ETHttpMethodNotAllowed`, which the existing handler turns into a `405`. The request also gets a log entry again: `ControllerID.Method` no longer goes through the enum and falls back to the raw command name, so `TTHttpLogRequest` can be built for a method the router refuses
- **The fallback response sets its status before anything that could fail.** The `500` was assembled after the log call, all inside one handler, so an exception from logging left `AResponseInfo` untouched and Indy synthesised its own **`200 OK`** with an HTML body: a client saw a successful response and broke on the JSON. Nothing between those lines raises today, but the guarantee was accidental. The status is now the first statement, the body and headers are best-effort after it, and the log has a handler of its own. The log entry also carries the exception message, which never reaches the HTTP body
- **An exception outside the request handler no longer answers with its own message.** `HandleRequest` has always turned an exception into a generic body carrying only the status, a fixed message and the task id. But `OnHttpServerCommand`, which wraps it, had no handler of its own: anything raised while building the request or the response, while setting the thread language, or while logging, escaped to Indy, which answers `500` with the exception message as the body. The handler is now the whole of `OnHttpServerCommand`, and the fallback writes the same generic body, releasing the response stream if one was already attached and resetting `ContentLength` so Indy recomputes it for the body it actually sends. The fallback cannot fail either: its own body is wrapped, because a host translation of the log message with the wrong format specifier would otherwise raise inside it and hand the request back to Indy, which is the leak this closes. Socket errors are re-raised rather than swallowed, as Indy expects, so a client that disconnects mid-request still ends the connection instead of producing a log entry and a write to a dead socket. The fallback also carries the `Access-Control-Allow-Origin` header, which the listener adds to every response it builds itself: without it a browser hides the `500` behind a CORS error instead of showing the body
- **A `condition` and a `direction` in a filter payload are emitted from the allowlist, not from the request.** Both were validated against the allowlist and then written into the SQL verbatim, and the check was `String.Compare(..., True)`, a linguistic compare-equal: case variants and ignorable code points such as `U+00AD` passed. Both allow-lists ask `TTIdentifier.Same` since the locale sweep in this same section, so those code points do not pass any more either and reached the statement unchanged. Nothing exploitable could get through - what passes cannot form SQL syntax - but the invariant a reader is entitled to assume was "identical", and it was only "compare-equal". The matched constant is now what the query carries
- **A JWT whose segments are not canonical base64url is refused.** The check is now canonicity, not just the alphabet: `IsValid` re-encodes what it decodes and requires the same string back. `TNetEncoding.Base64` silently drops characters outside the alphabet, so `header.payload.signature` with any junk appended to the signature segment decoded to the same bytes and verified. Infinitely many distinct token strings therefore authenticated as the same token, and any denylist, anti-replay or de-duplication keyed on the token string could be walked around by adding a character. The alphabet alone was not enough: the last character of a segment carries bits the payload does not use, so four different signature strings decode to the same 32 bytes on HS256, sixteen on RS256, and swapping that one character still walks around a denylist. `LoadFromToken` now requires all three segments to be canonical - decoded and re-encoded, they must come back identical - and returns `False` otherwise, which the Bearer handler turns into the usual `403`; `TTHttpJWTEncoding.Decode` is unchanged, so nothing that calls it directly breaks. `TTHttpJWTEncoding.IsValid` is `public` and has changed meaning with it: a host calling it as an alphabet check now gets `False` for any string that is not the canonical encoding of its own bytes - padding, trailing whitespace and a segment whose length cannot be padded included. An empty segment is refused too: `IsBase64Url` never entered its loop on one, and `Encode(Decode(''))` matches, so `IsValid('')` answered `True`. It was not reachable as a bypass - an empty header dies on the JSon parse and an empty signature on the length check, with no `alg: none` shortcut anywhere - but the refusal came from those accidents rather than from the rule, and `IsValid` is the canonicity gate a host is told to call.
- **A malformed token cannot answer `500` to an anonymous caller.** `IsValid` is `public`, and it now decodes to decide: `Decode` pads a segment whose length is congruent to 1 modulo 4 with three `=`, which is not a valid base64 quad. The RTL decoder skips what it cannot read rather than raising, so nothing escapes today, but that is a property of `TNetEncoding` and this release ships three sets of packages across five Delphi versions. `IsCanonical` now answers `False` instead of letting an exception out, and the unit pins `{$BOOLEVAL OFF}` so the alphabet check still short-circuits in a host that compiles with `$B+`
- **A header claim that is not a string cannot answer `500` either.** `LoadHeader` read `alg` and `kid` with `TJSONValue.GetValue<String>(name, default)`, whose default covers a claim that is absent or `null` but not one that is present with the wrong type: on Delphi 11 that overload goes through `AsType<T>`, and `TJSONObject` does not override `AsTValue`, so `{"alg":{}}` - a perfectly canonical header, which the canonicity check above has no reason to refuse - raised `EJSONException` out of `Check` and reached the caller as a `500`, plus a logged error per request, from someone with no credentials. Delphi 13 returns the default instead. Both claims are now read through a guard that answers an empty string, which fails the `alg` comparison and gives the `403` the caller should have had
- **`TTHttpLanguage` clears the resolver it lends to `TTLanguage`.** `AfterConstruction` installs itself as `TTLanguage.Instance.Resolver`, a borrowed reference that `TTLanguage` neither owns nor frees, and the class destructor freed the instance without taking it back. `Trysil.Consts` is a leaf unit, so it finalizes last: from that point every `Translate` - that is, every framework exception message - dereferenced freed memory. Unreachable in a normal executable shutdown, reachable by unloading the `Trysil.Http` package with `Trysil` still loaded, which is how the BPLs on GetIt are meant to be used. The destructor now clears the slot, and only when it still holds this instance, so a resolver the host installed afterwards is left alone
- **`TTHttpAuthenticationDigest<C>` is deprecated, and no longer answers `500` to a malformed header.** **A deprecation is not counted as a break here**, because the symbol still compiles and still works; a project built with `{$WARN SYMBOL_DEPRECATED ERROR}` is the one case where it stops the build, and that is the project's own setting.** The parser fed the `Authorization` parts into a dictionary with `Add`, so a repeated key - `Digest username="a", username="b"`, which anyone can send without credentials - raised `EListError` and came back as `500`. It now uses `AddOrSetValue`. The scheme itself stays at RFC 2069, the 1997 form: no `qop`, no `nc`, no `cnonce`, a captured response replayable for as long as `IsValidNonce` accepts its nonce, and a response comparison that is not constant time. It is not being brought up to RFC 7616, so the class carries a `deprecated` directive; use Bearer with JWT. The directive is visible at build time: a descendant of `TTHttpAuthenticationDigest<C>` now raises `W1000 Symbol is deprecated`, and a project compiled with `{$WARN SYMBOL_DEPRECATED ERROR}` stops
- **Breaking (compilation): `TTHttpLogRequest.Create` and `TTHttpLogResponse.Create` take one more argument**, the redaction hook. They are public constructors on public records: a host that only receives those records in its log writer is unaffected, but one that builds an item by hand needs the extra argument. As with `TTHttpListener<C>.Create` before it, the signature changed rather than gaining an overload, so it is noted here rather than assumed harmless
- **`AllowAnonymous`** on `TTHttpServer`: the one-line opt-out from the start-up check above, for a server that really does serve every route without authentication
- **Breaking, and the compiler does not catch it: a route carrying `[TArea]` with no authentication class registered refuses to start**, `AllowAnonymous` or not. `CheckAreas` was entirely inside `if Assigned(FRttiAuthentication)`, so with no authentication class the areas were not permissive, they were not looked at, and there was no signal: whoever wrote `[TArea('admin')]` believed a door was shut that was open. Two ways in, both silent - setting `AllowAnonymous`, which waives the start-up check on authentication and so let a server with no authentication class start, or having every route on `[TAuthorizationType.None]`, since that check only counts routes that require authentication and none did. `AllowAnonymous` itself never reached the listener and never switched areas off: what switched them off was the missing authentication class. An area without a user is a contradiction, so `Start` now says so instead of running
- **Breaking, and the compiler does not catch it: `[TArea]` on a route marked `[TAuthorizationType(None)]` refuses to start too.** Authentication does not run on a free route, so `Request.User` stays the empty one built with the request, its area list is empty, and the listener's area check denies every caller: a route permanently answering `403`, with nothing anywhere saying why. It is the mirror image of the entry above - that one served what it should have refused, this one refuses what it should have served - and both were silent. `Start` now names the offending route
- **Breaking, and the compiler does not catch it: `[TArea]` no longer spreads between overloads of the same name.** Areas are collected by walking the methods that share a name, which is what carries an ancestor's `[TArea]` onto an `override` - the pattern the REST example documents. It also unioned overloads: a public `Get` next to a `Get(const AID: Integer)` marked `[TArea('admin')]` ended up restricted too, answering `403` in silence to every caller without that area, and once `Start` began refusing an area on an anonymous route it refused this one, naming a route whose source carries no `[TArea]` at all. The walk now matches on the parameter list as well as the name, so an override still inherits and an overload does not. **What changes for an application**: an overload with no `[TArea]` of its own, which was restricted by its sibling's, now answers every authenticated caller - put `[TArea]` on each overload that must stay restricted
- **Breaking, and the compiler does not catch it: the area check no longer depends on there being an authentication class.** `CheckAreas` ran entirely inside `if Assigned(FRttiAuthentication)`, so the two start-up refusals above only cover a host that goes through `TTHttpServer`. `TTHttpListener<C>.Create` and `SetRttiAuthentication` are both `public`, and a host that builds a listener by hand and never calls the setter had the original defect intact: `[TArea('admin')]` served to an anonymous caller, silently. The guard is gone, so the loop always runs: with no authentication the user carries no area and the route answers `403` instead of opening. **What changes for an application:** a listener built by hand with no authentication class used to serve its `[TArea]` routes and now refuses them. To exercise those routes without issuing tokens, register an authentication class whose `Check` fills `Request.User.Areas` and returns
- **Breaking, and the compiler does not catch it: an exception raised inside a `[TValidator]` is no longer turned into a validation error.** `TTResolverValidator` invoked custom validators under a `try..except` that put `E.Message` into the error list under an empty column name, so a failure became an outcome. The framework hands the context to a validator precisely so it can query the database, which means the swallowed exception was routinely a `EFDDBEngineException` carrying a constraint name, a schema-qualified table and often the statement - and since the entry below started publishing the validation message, that text was on its way to the client. A validator that raises now lets the exception through: it reaches the caller, and over HTTP it is a `500` with the fixed body and a logged error, which is what a fault is. A validator that wants to reject a value still calls `AErrors.Add`
- **Breaking for a client of the server, not counted: an `ETConcurrentUpdateException` answers `409` and an `ETValidationException` answers `422`.** Neither descends from `ETHttpException`, so both reached the client through the generic branch of `HandleRequest` as a `500` with no detail: a status that tells a client to retry the same request, when the right answer was to reload the row or to fix the body. The soft-delete guard added in this release made the first one ordinary - a `PUT` on a deleted row now touches no row at all, and the resolver raises exactly that. `ETHttpUnprocessableContent` and `TTHttpStatusCodeTypes.UnprocessableContent` are new; `ETDataIntegrityException` is deliberately left alone, since only the application knows whether a broken foreign key is the caller's doing. **What changes for an application:** a controller that already wrapped those two in a `try..except` keeps its own status; one that did not stops answering `500`
- **Breaking, and the compiler does not catch it: `TTHttpContext.Delete<T>(AID, AVersionID)` answers `404` when the row is not there.** The overload loads the row before deleting it, and raised `ETConcurrentUpdateException` when the load came back empty - which the entry above then turned into a `409`. But `409` tells the client to reload and retry, and reloading will never produce that row: `Get<T>` returns nil both for an id that never existed and for one that is soft deleted, and in either case the resource is gone now. It raises `ETHttpNotFound` instead, with the id. A real version conflict is untouched: there the row loads, the `UPDATE` matches nothing, and the resolver raises the concurrency exception further down, where `409` is right
- **Breaking, and the compiler does not catch it: registration and log hooks are refused once the server is running.** `RegisterController`, `RegisterAuthentication`, `RegisterLogWriter` (all three overloads), `AllowAnonymous`, `OnCanLog` and `OnRedactContent` now raise if `Started`, like `Port` and `BaseUri` already did. Registering a controller after `Start` used to slip past the new start-up check and, worse, mutated the routing tables while request threads were reading them
- **The log thread writes what is still queued when it is stopped, once it has run and holds a writer.** `Execute` left the `while not Terminated` loop without a final `ProcessQueue`, so everything queued at the moment of `Stop` was lost - the last requests served, which are exactly the ones anybody goes looking for. It now drains the queue before releasing the writer. The writer is not tried once more on the way out: if the last attempt to create it failed, the thread holds none when it stops, and what is queued is lost with it. `TTLoggerThread`, the other log thread in the library, already did this: the two behaved differently for the same problem
- **An error row is never discarded because the queue is full.** `Enqueue` for an error went through the same capacity check as requests and responses, so under load - which is when errors happen - the `500`s were thrown away together with the traffic that caused them, while `docs/http/server.md` states that an error row is always worth writing. Errors now go in regardless. The cap still applies to requests and responses, and the discard counter still reports what it dropped
- **A log writer that cannot be created no longer kills the log thread.** `TTHttpLogThread.Execute` created the writer as its first statement, outside any guard: an exception from its constructor - a directory that does not exist, a file locked by another process, a database that is down - left `Execute`, the RTL parked it in `FatalException` and the thread ended, while `TTRoundRobin` kept handing that dead thread out. Every entry was enqueued into a queue nobody drained, filling to capacity and then counting discards nobody would ever write: the server ran, logged nothing and reported nothing. The same silence covered a `CreateLogWriter` that returns `nil`, which reached every `Write` call as an access violation inside the handler that swallows it. The writer is now created inside a guard, on first use, and retried on the next cycle, so a transient cause - the file unlocked, the database back - resumes logging by itself. In the normal case its lifetime is unchanged: one writer for the life of the thread
- **Breaking, and the compiler does not catch it: `RegisterLogWriter` now constructs the writer once, at registration.** It checked the shape of the class through RTTI and never ran it, so a writer whose constructor always raises registered without complaint, the server started, served requests and wrote no log. The registration now creates one writer and frees it immediately, letting the writer's own exception reach the caller at start-up, on the caller's thread, next to the `Start` checks above. Note what this refuses: an application whose log destination is not available at start-up - a log-to-database writer that opens its connection in the constructor, against a database that comes up later - now fails to start where it used to start and log nothing. A writer that can tolerate that must not open the destination in its constructor
- **A failing `OnCanLog` or `OnRedactContent` can no longer break the request.** `LogRequest` and `LogResponse` are now wrapped like `LogError`, which already carried the rule that logging must not break the operation being logged. Without it an exception from the host's own closure escaped into Indy, which answers `500` with the exception message in the body, bypassing the error contract entirely
- **A body that does not parse costs the body, not the whole request record.** `TTHttpLogRequest.SetContent` read the content through `ARequest.JSonContent`, and from this release that property raises on a malformed body. `TTHttpLog.LogRequest` builds the record inside a mute `try..except`, on the principle that logging must not break the operation being logged - so the exception went nowhere, and the record was simply never queued. With `MaxContentLength` raised above its default, which is the documented way to capture bodies, a malformed request lost its uri, its caller IP, its headers and its counts, not only its body. The response record survived, but the caller is named in the request one only. The read is now guarded: the body is dropped and marked omitted, and the line is written. Read it together with the `GET` carrying a query string, which the last clause of the entry on an empty body covers: until both were closed, a request that was answered `400` could leave no trace at all in the request log.
- **The redaction list covers the parameters too, and an application can add to it.** `RedactedNames` was a `const` in a `strict private` section holding five header names, and the same list was applied to the query parameters - where a secret is not called `Authorization`, it is called `token`, `access_token` or `key`. The shape that makes it concrete is a link a browser opens: a printable invoice behind an `<a href>` cannot set a header, so the token travels in the url, and from then on every log line carries it in clear. The list is now `TTHttpLogRedactedNames.Instance`, it ships with those parameter names beside the header ones, and `Add` takes whatever an application calls its own secret - `TTHttpLogRedactedNames.Instance.Add('X-Tenant-Key')` before `Start`. Before `Start` is not advice: `Add` raises while a server is running, because the list is read on every header and every parameter of every request and adding to it under those readers is a race. That refusal is what lets the read path carry no lock, and it lifts again when the server stops. It only ever bit with body logging on, because the parameters are omitted whenever the content is, which is to say it bit exactly the application that turned logging on deliberately.
- **The redaction of a header name does not follow the language of the machine.** `IsRedacted` compared the name it was given against the list with `String.Compare(..., True)`, which is a linguistic compare: on a machine set to Turkish or Azeri a client sending `AUTHORIZATION` did not meet `Authorization`, the header was not recognised as one to hide, and the bearer token went into the log in clear. It is the only member of the locale family that fails **open**, which is why it is here rather than with the others.
- **A byte order mark in front of the body is not part of the body.** `GetContentText` decodes with the charset the request declares, and `TEncoding.UTF8.GetString` keeps the mark: `String.Trim` does not remove it, because `U+FEFF` is not below a space, and the parser of the RTL skips space, tab, CR and LF only. So `{"where":[]}` sent with a leading `EF BB BF` came back `nil` from `ParseJSONValue` and was answered `400`. Before this release it read as `{}`, which meant the whole table - refusing was the right direction, but it made every request from a client that writes the mark, which .NET and PowerShell do by default, fail. A leading mark is now dropped, and only where a body is read from the stream: `FormParams` and the query string never carry one.
- **The HTTP filter accepts the name the client sees.** `columnName` was looked up only among the column names of the metadata - `Alias_Column` for a joined column - while every response and `MetadataToJSon<T>` show the client the member's JSON name. It is now looked up as a column name first, as before, then as the JSON name, which the new `TTColumnMetadata.JSonName` exposes and the new `TTIdentifier.PublishedName` computes with the rule the serializer uses. A column name that worked still reaches the column it reached, unless that column is hidden from the responses, which the entry below on columns no response returns refuses; a filter written against the names in the payload now works too, except in the collisions described next, and on a joined column it survives the alias being shortened. The column name is tried first, and the column it finds is the answer: if it is hidden from the responses or not filterable, the filter is refused, even when the JSON name of another member is spelled like it, compared without regard to case. Passing the name on to that member would move a filter written for one column onto another, with a `200` and nothing said - and in 1.0.0, which checked only that the column existed, that name filtered on the hidden column. The price is narrow: in that collision the published JSON name answers `400`. The same rule has a second face, and it answers `200`: when the column the name finds is visible and filterable, the filter reaches that column, even though the payload published the same name for another member - the rows 1.0.0 returned, not the member the client meant. Keep the JSON names of the members apart from the column names. A refusal repeats the name the client sent, not the database name behind it, which the payload stopped publishing in this release
- **Breaking for a client of the server, not counted: a date without a time zone in a filter is the date it says, not that date in UTC.** A filter value reaches its typed parameter through `TTDateTimeParameter.TryValueFromString`, which read it with `TryISO8601ToDate(value, result, True)` and moved the result to local time. That overload of the RTL takes a text without a time zone as UTC, so `2026-03-05` became one in the morning on a server at UTC+1 - two in summer - and `Data = :p0` on a `DATE` column found nothing, while `>=` skipped a day. 1.0.0 put the value into the statement as text, and the database read it as the date it was; the typed parameters brought the defect, and the public master already has it. A value with a zone - `Z`, `+hh:mm` or `-hh:mm` after the time - is still moved from UTC to local time; a value without one is taken as written, as local time. How the RTL treats a text without a zone was read in the sources of Delphi 13, where the overload with a `Boolean` never passes `ioNoTZIsLocal`. The body of an entity is not on this path: a `TDateTime` sent there without a zone is still read as UTC, as in 1.0.0, and what the serializer writes always carries the `Z`
- **Breaking for a client of the server, not counted: a filter body that parses to something other than an object is refused, where it used to mean no filter.** `TTHttpFilterValues.GetArray` reaches for `where` with `FindValue`, and `FindValue` on a root that is not a `TJSonObject` returns `nil` at once, which reads as `Missing`, which reads as no condition. So `POST /customers/select` with a body of `0`, `true`, `"x"` or `[]` answered `200` with the whole table up to `MaxLimit`, and no `400`, because the body did parse. `TTHttpFilter<T>` now refuses a root that is not an object, which is the same principle the rest of the filter follows: it is refused whole rather than applied in part, because the part that gets dropped is a restriction. An absent body still means no filter - `nil` is not a malformed body, and turning it into a `400` would be a different break.
- **Breaking for a client of the server, not counted: a body that parses to something other than an object is refused on the way in, too.** The overloads of `EntityFromJSonObject<T>` take a `TJSonValue`, in spite of the name, and read every column with `GetValue<TJSonValue>(name, nil)` - which answers `nil` for every column when the root is an array or a string, and writes nothing. So a `POST` with a body of `[]`, which is what a front end sends when a `JSON.stringify` gets an array where an object was meant, built an entity with every field at its default and inserted it, answering `200`. On the update path it is worse: no field is written, no error is raised, and the caller believes it has saved. The two overloads that take a string checked the root already; the two that take a value do now. It is the same principle as the filter above - a body that cannot be read is refused, not ignored.
- **Every route parameter is decoded, not only the first.** With Sqids on, `GetIntegerParam` decoded the placeholder in position zero and read all the others with `Integer.TryParse`: on `/orders/?/rows/?` a valid sqid in second position matched nothing, so the route was never found and the request came back `404` with no explanation. The index is gone from the whole chain - it existed only to express that restriction - and `TryDecode` already falls back to `Integer.TryParse` when Sqids is off, so nothing changes for an application that does not use it
- **A failed URI match no longer leaves parameters behind.** `TTHttpUriParts.Equals` cleared the list on entry and added a parameter for each placeholder it accepted, but on a segment that did not match it returned `False` **keeping what it had already added**. The next candidate cleared it again, so the damage showed only when no candidate matched at all: the request fell through to a `'*'` route, which takes no parameters, and was invoked with one - `EInvocationError`, answered as `500`. Since the candidates come from a dictionary, whether it happened depended on iteration order, which is why it looked intermittent. The list is now cleared on the way out too
- **Breaking for a client of the server, not counted: a filter field of the wrong kind is a 400 on every Delphi version.** `where`, `orderBy`, `start`, `limit`, `condition`, `value` and `columnName` were all read with the RTL's `GetValue<T>(path, default)`: up to Delphi 11 a value of the wrong shape raised and came back as a `500`, and from Delphi 12 the same payload silently took the default. The dangerous one was `{"where": {}}`, which left no filter at all and answered with the whole table. The filter is now refused whole, naming the field, rather than applied in part - a dropped piece of a filter is a dropped restriction

- **A malformed Basic credential is refused, where it used to be a `500`.** `TTHttpAuthenticationBasic<C>.Check` handed the header straight to `TNetEncoding.Base64.Decode`, which decodes to bytes and then reads them as UTF-8 - and raises `EEncodingError` when they are not. That exception is not an `ETHttpException`, so it walked out of the authentication chain and was answered as an internal server error. Any client, with no credential of any kind, could force a `500` on every route behind Basic by sending `Authorization: Basic //8=`, and the same for anything outside the base64 alphabet. The decode is now guarded and a credential that cannot be read is answered `403`, next to the one that carries no colon. Found by the new authentication tests, which is the point of having them

- **Breaking (compilation): the request language is a thread variable, so `TTHttpLanguage.SetThreadLanguage` and `RemoveThreadLanguage` no longer take a thread id.** They kept a `TDictionary<TThreadID, TArray<String>>` behind a process-wide read-write lock, and the server wrote to it twice per request - once to record `Accept-Language`, once to drop it - taking the **exclusive** side of that lock each time, which shuts out readers too. Every request therefore had two points where every other request on every other Indy thread waited, and it happened whether or not the application had registered a single translation. The language of a thread is thread-local by definition, so it now lives in a `threadvar`: the two writes take no lock at all, and reading it during a translation takes none either. The signatures lose the thread id because with a thread variable you can only set your own - keeping the parameter would have been a lie. Nothing in this repository outside the server and one test called them, and they are named in no page of the documentation. **Note for anyone maintaining this**: a `threadvar` of a managed type is not finalized when the thread ends, so `RemoveThreadLanguage` has to keep being called in a `finally`, which is what the server does; the two new tests in `Trysil.Tests.Http.Language` check that one thread never sees the language of another, and that a thread nobody set a language on falls back to the key rather than inheriting one
- **The comparer behind the translation table hashes what it is given.** `TTLanguageValueEqualityComparer.GetHashCode` returned `Language.Length + Key.Length`, so every pair whose two lengths added up to the same number landed in one bucket and the dictionary degraded to a linear scan. It is now `THashBobJenkins` over the pair, as `TTIdentifier.JoinAliasName` already does
- **The logger stops building what it then throws away.** `TTLogger.Log` tested `Enabled` **after** its argument had been constructed, so with logging off every call still built a `TTLoggerItem` - a `TTLoggerItemID` plus a copy of the value array - and, worse, every call site in `Trysil.Data.Parameters` had already converted the parameter to a string to pass it: `ToString`, `DateTimeToStr`, `CurrToStr`, once per parameter per row. An insert of 200 rows over 20 columns paid four thousand conversions and four thousand items for nothing. The seven entry points now check first, and so do the twenty call sites
- **The constructor of an entity is looked up once per query, not once per row.** `TTRttiEntity<T>` scanned `GetMethods` on every `CreateEntity` - twice, when the entity has no constructor taking the context - and `TTProvider.Select` and `RawSelect` built a fresh `TTRttiEntity<T>` inside the row loop. The lookup is now memoized on the instance, keyed by the context it was resolved against, and the instance is created once per query and passed down. Nothing about the entity contract changes: an entity with a context constructor still gets it, and one without still falls back
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): the filter answers the same thing for a column that does not exist and one that must not be filtered.** `FindColumn` raised two different `400`s, `SColumnNotFound` and `SColumnNotFilterable`, both naming the column. A caller with nothing but read access could therefore enumerate the `[TNotFilterable]` columns of an entity by asking one at a time - the columns the host marked precisely because they must not be probed. It is not a leak of data, it is the map of where they are, and it is the same reason `MetadataToJSon<T>` stopped publishing them. There is one message now, and it names both possibilities without saying which: *it is not a column of this entity, or it is marked as not filterable*
- **Breaking for a client of the server, not counted: a column no response ever returns cannot be filtered either.** The metadata told a client, in the same object: this field is not readable, and yes, you may filter on it. `[TJSonIgnoreSerialize]` on a `Password` or a `Costo` left `filterable` untouched, because that flag answers `[TNotFilterable]` and nothing else, and the gate in front of the server-side filter asked only that flag. So `LIKE '$2a$10$a%'` was accepted and the row count in the answer is the oracle: one character at a time, a value the API would never return comes back. The documented mitigation was to put `[TNotFilterable]` on it as well, which is a rule somebody forgets. The gate now asks both questions. It is the same gate the `orderBy` goes through, so a column no response returns cannot be sorted on either, and it answers for `[TJSonIgnore]` as much as for `[TJSonIgnoreSerialize]` - if you sort an administrative list by an internal column and that column is hidden from the payload, that `orderBy` is refused now and was not before. The payload reports `filterable: false` for the columns it does describe, so the two agree - a client that builds its filter UI from the metadata hides them instead of discovering them through a `400`. `TTColumnMetadata` carries the names of the attributes its column declares, which is what lets the HTTP layer ask a question the core has no business knowing the answer to; it carries them as names, not as a reference back into the mapping, so the metadata stay a snapshot.

- **`TTHttpServer<C>.Free` no longer raises when `Stop` fails.** The destructor called `Stop` bare; it now wraps it in `try..except` and writes the message to the log instead. Destroying an object must not raise, and a server whose `Shutdown` throws used to take the exception out through `Free` - where an application has no sensible place to catch it. The behaviour change is real though: if you relied on `Free` telling you the port did not close, it does not any more; ask `Stop` yourself first

- **Breaking, and the compiler does not catch it: the text of `SForbidden` changed, which only a translation table keyed on the English text notices.** It read `Acess forbidden : %s.` - a typo - and reads `Access forbidden: %s.` now. The warning written above about `SRecordChanged` applies word for word: that resourcestring is the key `TTLanguage.Add` looks up, so a translation table keyed on the old **English text** loses the entry and falls back to English without a sound. A table written the way `Demos/Languages/README.md` teaches, naming the constant, recompiles unharmed. These two are the only resourcestring texts that changed against 1.0.0: every unit with a `resourcestring` section was compared with `v1.0.0`, and besides the two texts there are two constants removed, `SForbiddenArea` and the `SColumnNotFound` of `Trysil.Http.Consts`, both declared above. Against the public master there is a third, `SColumnNotFilterable`, whose text now names both reasons a column can be refused: it is counted and described above

- **Sqids are a no-op below Delphi 12, and now it is written down.** `TTJSonSqids` is built on `TSqidsEncoding`, which is an RTL 12 type, so the whole implementation lives under `{$IF CompilerVersion >= 36}`. On 10.3, 10.4 and 11 the `{$ELSE}` branch compiles and does nothing: `UseSqids := True` is accepted and `UseSqids` reads back `False`, and the keys go out as plain integers. That is degradation, not a break, and it has always been so - but an application that switches Sqids on to obfuscate its ids on one of those three compilers gets ids in clear while believing otherwise

### Declared limits

These are not defects and none of them is being fixed here. They are the places where this release made a choice, or leans on something it does not own, and where saying so is worth more than a silent assumption.

- **An entity belongs to the context that built it, and nothing checks it.** An entity read or created by one context and written by another on the same connection is not supported: each context keeps its own rewind of the shared transaction, and `FreeEntity<T>` tells only its own. Read it through one context, save it through another, free it through the first, and a rollback makes the second write into freed memory; with the identity map on, destroying the first context before the transaction ends does the same. Write and free an entity through the context that read or created it, and give each context its own connection when you want them independent. The same holds for a lazy member: with the identity map on it keeps the instance it is given, so hand it only an entity the map of its own context holds. Refusing a foreign entity at the write would take a register of the entities a context builds, and it would also refuse an entity built with `TPerson.Create` and handed to `Insert`, which works today, so it is left to a later release. With the identity map on, `FreeEntity<T>` through either context frees nothing, and the fault comes instead when the context whose map holds the entity is destroyed before the transaction ends

- **`FreeEntity<T>` decides on the type, so with the identity map on it does not free a clone.** It asks whether the identity map would hold an entity of that type, and with the map on the answer is yes for every keyed entity without joins. That is right for what the context read or created, which the map holds, and a leak for everything else of the same type: a clone from `CloneEntity` or `OldEntity`, a row of a `RawSelect<T>`, an object the host built. A clone and a raw select row kept in a `TTList<T>` that owns nothing are freed with `FreeClone<T>`, which frees in both modes. A lazy member handed one of them with the map on keeps it as it is: nobody frees it, and if the host frees it the member is left on freed memory - as it is, with nothing the host does, when the entity is a clone the session holds in `Entities` or the `OldEntity` of an event and that is destroyed. The same holds for `TTSession<T>` with the map on: an entity of such a type handed to `Insert` that the map does not hold is freed by nobody but the host, with `FreeClone<T>` after the session. Deciding on the object instead - asking whether the map holds this very pointer - is the right answer, but `TTLazy<T>.SetEntity`, `TTSession<T>` and `CreateEntityList<T>` decide on the type too, and each of them keeps or frees on that answer: changing one without the others turns the leak into a double free. All of them move together, with a register of the entities a context builds, in a later release. Who frees what, case by case and in each mode, is the table in `docs/guide/context.md`

- **`[TDetailColumn]` goes on a `TTLazyList<T>`, and nothing checks it.** The documentation has always said so, and the mapper accepts any owning list all the same. The detail loader clears the list before it reloads it, on every `Refresh` of the master and, with the identity map on, on every read that finds the master again: a `TTLazyList<T>` tells the context about each row it frees, any other list frees them silently, so a detail row written inside a transaction that rolls back makes the rollback write into freed memory. The clear was already there in 1.0.0; the rewind is what made it matter. The lazy members of the rows it frees stay registered on addresses nobody holds, as with a raw select collected into an owning list. Refusing another list in the mapper would turn a shape that happens to work into an exception, so it is declared, not refused

- **This release was compiled on Delphi 11 and 13, and its tests were run on Delphi 13.** The package sets for 10.3, 10.4 and 12 are kept aligned with the other two - the same units, the same `requires`, the same dependencies - and no API this release adds is known to be missing on 10.3, but they were not compiled for it: those three compilers were not available. A compilation error on one of them is a defect to report, not a surprise to work around

- **The ORM logger queue has no ceiling; the HTTP log queue got one in this release.** `TTHttpLogQueue` gained a capacity and a discarded counter here. `TTLoggerQueue` did not: under a server every transaction, every statement and every parameter of every request thread goes into an unbounded `TQueue<TTLoggerItem>`, drained by a **single** thread, since `RegisterLogger<T>()` without a size makes one. The synchronisation is correct; what is missing is back-pressure, and the two queues look alike from outside while only one of them has it. If your logger writes slower than your server serves, the queue is where the memory goes

- **A second `RegisterLogger` adds to the pool; it does not replace the logger.** `TTRoundRobin<T>.CreateItems` is additive, by design and under a test, and `RegisterLogger<T>` builds on it, so `RegisterLogger<A>(2)` followed by `RegisterLogger<B>(3)` leaves five threads of two classes, and the log lines divide themselves between two destinations. That is what 1.0.0 did, and this release keeps it. Replacing the pool was written and withdrawn before release: a thread taken out of the round robin can still be in the hands of a caller that picked it a moment before, and freeing it waits for its queue to drain while your logging code, which may log in turn, runs. Raising on the second call was considered and rejected, because it would break at runtime a host that registers in every test setup. Register once, at startup, with the class and the size you mean

- **Nothing orders the finalization of `Trysil.Logger` against the other singletons.** Its interface `uses` names neither `Trysil.Consts` nor `Trysil.Mapping`, so where it finalizes in the link order is an accident. It matters because tearing the logger down drains what is left in the queue, which runs **your** logging code during process finalization: if that code reaches `TTLanguage` or `TTMapper` and they have gone first, it dereferences nil while nobody is watching - on the logger's own thread, or, for whatever is still queued once that thread has stopped, on the thread that frees the logger, which during finalization is the main thread. Nothing inside Trysil does that, so the chain is not reachable from here - it is reachable from a logger you write. There is no call that stops the logger early: it lives until `Trysil.Logger` finalizes. What **is** ordered is worse for a logger that keeps state of its own: the unit declaring your logger uses `Trysil.Logger`, so it always finalizes **first**, and a writer or a lock shared by the threads of the pool, held in a class variable and freed in that unit's finalization or class destructor, is gone when the drain reaches it. Keep what the logger writes through inside the thread instance, built in its constructor and freed in its destructor. And stop the threads of your own that log before the process ends: a line logged while the logger is being torn down reaches a pool that is being freed

- **`TTJSonSerializers` and `TTJSonDeserializers` have no guard against being written while a server serves.** `TTHttpLogRedactedNames` got `BeginServing`/`EndServing` in this release precisely so that a late `Add` raises instead of rehashing a dictionary under concurrent readers. The two serializer registries are the same shape - a process-wide dictionary, `Register<T>` public, read from every request thread with no lock - and did not get the same guard. The rule is documented instead: register everything before `Server.Start`, from the main thread

- **`TTColumnMetadata.HasAttribute` answers `False` for two different questions.** It says `False` when the attribute is absent, and it says `False` when there is nothing to ask - a column the database returned that the entity does not map, or a column map with no member. For the two callers inside the library the two cases coincide; for a host calling it on a column of its own choosing they do not, and there is no way to tell them apart from the result

### Fixes

- **A re-entrant `EntityToJSon` starts with a clean visiting set.** The serializer keeps three pieces of state across a serialization - the config, the depth and the set of entities currently being written - and `EntityToJSon` saved and restored the first two and not the third. The only way in is a `DoAfterSerialized` that calls back into the `TTJSonContext` the serialization started from, and the inner run then inherited the outer set: a field that would have been written was read as a cycle and left out, silently. The visiting set is now saved, cleared and restored like the other two. In the same procedure, the depth was incremented and the key pushed **outside** the `try` that undoes them, so a failing push left the depth raised for the life of the serializer; the pop is now a truncation back to the count taken on entry, which is correct whether the push happened or not
- **Two objects that were built and then dropped on the floor.** `TTHttpRttiLogWriter.CreateLogWriter`, `CreateAuthentication` and `CreateController` construct through RTTI and, when the result is not of the expected type, returned `nil` while leaving the instance alive - the JSON twin, `TTJSonEventFactory.CreateEvent`, frees it. Registration already refuses a wrong type, so the branch is not reachable from the public API, but it now frees what it built. And `TTHttpServer<C>.Destroy` opened with `if FHttpServer.Active`, which is a read through `nil` when the constructor failed before allocating it: Delphi calls the destructor anyway, and every other line of it was already nil-safe
- **Breaking for a client of the server, not counted: the `Server` header names Trysil, and can be changed.** `TTHttpResponse.ServerHeader` is a class property, default `API REST made simple by Trysil Delphi ORM` plus the repository URL, written into every response. In 1.0.0 the same header carried `Indy/10.6.x`, because Indy assigns it before the request handler runs. Neither value is a secret and both name a stack, so if you would rather not declare yours, assign `TTHttpResponse.ServerHeader` at startup - an empty string leaves the header out. It is mentioned here because a knob nobody knows about is not a knob
- **Breaking (compilation): `TTJSonLazyList.CreateList` is now `PrepareList`, and `TTJSon` no longer carries its `FRttiContext` field.** It also declares no constructor or destructor of its own any more, which breaks nothing: `TTJSon.Create` is `TObject.Create`. Both are in `Trysil.JSon.Rtti.pas` and both matter only to a host that had subclassed `TTJSon`, which nothing in this repository or its demos does. Note for anyone reading that unit: the matching `TTLazyList<T>.PrepareList` looks unreferenced and is not - it is reached by name through RTTI, which is why the type carries an explicit `{$RTTI EXPLICIT METHODS}` directive
- **Breaking (compilation): a connection keeps a list of transaction observers, so the `TransactionObserver` property is gone.** It is replaced by `AddTransactionObserver` / `RemoveTransactionObserver` and a read-only `TransactionObserverCount`. The single slot was the wrong shape: it is one per connection, but what it holds - the new-entity cache - is one per context. A second context built on the same connection silently displaced the first one's cache, and from that moment the first context was never told about a commit or a rollback, so an entity it inserted in a transaction that then rolled back stayed marked as written and the next `Save` updated a row that was not there. Two contexts on one connection share the physical transaction, so both caches now hear about it, which is what sharing a transaction means. Nothing outside the library set the property: it existed for `TTContext` to claim the slot
- **Breaking, and the compiler does not catch it: `TTContext` no longer leaves a dangling observer on its connection, and must now be freed before it.** `AfterConstruction` registers the new-entity cache as an observer on the connection - a single slot at the time, a list since the entry above - and nothing ever removed it, so destroying a context left the connection pointing at freed memory; the next `StartTransaction` wrote into it. A `BeforeDestruction` now calls `RemoveTransactionObserver` with the context's own cache. The consequence is a new ordering constraint: until now **nothing** in the context's destruction reached the connection, so freeing the connection first was harmless. It now reads and writes memory that is already gone. Destroy in the reverse order of creation - context, then connection - as `docs/guide/context.md` now states
- **An entity with no updatable column now raises instead of generating invalid SQL.** With `[TCreatedAt]`/`[TCreatedBy]` out of the `SET` list, an entity with no `[TVersionColumn]` whose only non-key columns are creation or, since this release, deletion tracking would have produced `UPDATE T SET  WHERE ...` - with a version column the `SET` list is never empty, because the version is emitted as `V = V + 1`. `TTUpdateSyntax` raises `ETException` with the table name instead
- **`TTJSonSerializer` no longer frees a detail array twice.** The inner handler around a detail collection freed the result without clearing it and re-raised, and the outer handler freed it again. Deterministic heap corruption whenever a detail item carried a field type with no registered serializer
- **`[TWhereClauseParameter]` values are now bound.** The attribute never worked end to end: the metadata probe inherits the entity's `WHERE` clause from `TTSelectSyntax` and accumulated the parameters on the syntax filter, but `GetMetadata` passed `TTFilter.Empty` to `CreateDataSet` and threw them away, while `InternalCreateDataSet` skipped binding altogether for a filter whose `Where` and paging were empty. Both are fixed
- **Breaking, and the compiler does not catch it: a limit with no offset now pages instead of being ignored.** `TTFilterPaging` dropped the whole paging when either bound was missing, and the builder starts from `-1`, so `LBuilder.Limit(10).Build` returned every row with no error - the plainest use of the API. A limit with no start now means start at the first row, normalised where the paging is built, so it covers the fluent builder, a hand-built `TTFilter` and the HTTP filter alike. The generated SQL is the `LIMIT n OFFSET 0` form every dialect already emits. An offset with no limit raises, see below
- **Breaking, and the compiler does not catch it: an offset with no limit now raises instead of being ignored.** The other half of the same defect: `LBuilder.Offset(50).Build` skipped nothing and returned every row. Trysil cannot express "skip 50 and return the rest" portably - three of the seven dialects need a fabricated upper bound - so it says so instead of pretending. `TTFilterPaging` raises `ETException`, and the HTTP filter answers `400` rather than letting it become a `500`. Only a **positive** start counts as an offset: `TTFilter.Create(where, 0, 0, orderBy)` still means "order, no paging", exactly as before, and so does a zero `start` over HTTP. This is reachable from HTTP only on an endpoint configured with a negative `MaxLimit`, since otherwise the ceiling supplies the missing limit; the `start` parameter now defaults to absent rather than `0`, so omitting both still means no paging
- **Breaking, and the compiler does not catch it (on the public master, not in 1.0.0): pool parameters registered for a connection that already exists now raise.** `RegisterConfig(AName, ...)` writes into the per-connection pool table, but pooling is baked into the FireDAC connection definition by `RegisterConnection`, so parameters supplied for a name already registered were stored and never used. They now raise `ETException` naming the connection; supplying the parameters the name already carries stays a no-op, so a call that runs more than once is still harmless. The global `Config` is unchanged and keeps applying to every registration that follows it, which is what a multi-tenant host relies on when `TTTenantConnection` registers a tenant on first use
- **Breaking, and the compiler does not catch it: SQL Server no longer sends `Encrypt=No`.** It was hardcoded on every connection with no way to override it, so traffic between application server and database was in clear with no opt-out - and it was not merely a missing encryption, it actively cancelled the `Encrypt=Yes` that ODBC Driver 18 applies on its own. Trysil now says nothing unless asked, leaving each driver generation its own default. `TTSqlServerParams.Instance.Encrypt` takes a `TTSqlServerEncrypt` - `DriverDefault`, `Yes`, `No` - read when a connection is registered, so it belongs at start-up, before the first registration; it is one setting for the process. **What changes for an application:** one that connects through Driver 18 to a server with a self-signed certificate used to work, because Trysil turned encryption off underneath it, and now fails validation. Set `TTSqlServerEncrypt.No` to keep the old behaviour explicitly, or set `TTSqlServerConnection.Driver.ODBCAdvanced := 'TrustServerCertificate=yes'` to keep validating nothing
- **`TTSqlServerParams.Instance.TrustServerCertificate`**, a tri-state next to `Encrypt`, emitted where FireDAC will actually read it. `TrustServerCertificate` is not an ODBC keyword FireDAC knows: the connection string is built from a closed list per driver (`TFDDefinition.BuildString`), the MSSQL list has `Encrypt` but not this, and the string occurs nowhere in the FireDAC sources - a parameter outside the list is dropped with no error. Both earlier attempts in this release wrote it as a plain parameter and therefore did nothing, while the API said the certificate was not being validated. It now travels through `ODBCAdvanced`, which FireDAC appends to the connection string verbatim, outside the filter, and which is read at every open rather than once at driver load - so a multi-tenant host, whose tenants register on a request thread long after start-up, reaches it too. It is the one setting here that appends rather than yielding: `ODBCAdvanced` carries many settings in one string, so a value already in the list is joined with a `;` instead of being left alone, and a registration that runs twice still does not append it twice. Verified against a live SQL Server with a self-signed certificate: the same connection is refused without it and opens with it

### Demo and documentation

- **The session's two unwritten rules are written down.** That `TTSession<T>.Insert` **adopts** the entity handed to it is the break described under ORM, and `docs/guide/sessions.md` never said so - while its complete example created an entity and did not free it, so a reader applying the general rule would have added a `Free` and got a double free. Second, `ApplyChanges` writes the **clones**: the objects in the list passed to `CreateSession<T>` keep the state they had when the session started - no new key, no incremented version, no change tracking stamp - and what the session does about it is set `IsValid := False` on the source list when it is a `TTObjectList<T>`. Both are now warnings in the page, and the example says which object belongs to whom. The page also said that the session detects changes by comparing the clones with the originals, and its first example modified the clones without calling `Update`: the session has never compared anything, not in 1.0.0 either, and a clone is written only when it is marked, with `Update` or `Delete`. The example calls it now. The page also said that `ApplyChanges` inserts first, then updates, then deletes, and it never did, not in 1.0.0 either: it writes the clones of the source list in the order of that list, updated or deleted as marked, and then the inserted entities in the order they were inserted. An update pointing at an entity inserted in the same session runs before that insert, and the page now says so
- **What runs before authentication is now written down.** The per-request context is built before the route is resolved and before authentication, so `C.Create` runs for a URI that does not exist and for a caller carrying no token. The order is deliberate - authentication is the host's code, it is handed the context because deciding who the caller is usually means asking the database, and the `401` on an unknown route has to be decided before the `404` - and the consequence for secrets was documented while the consequence for resources was not. In the documented context shape `C.Create` opens a database connection, which is one pooled connection per anonymous request. `docs/http/server.md` now says so and shows the way out: build the connection on first use rather than in the constructor, which costs nothing when the authentication is a signature check. `docs/http/multi-tenant.md` says the same for resolving a tenant, which is the heavier case
- **The server states that it does not terminate TLS, and why.** `docs/http/authentication.md` recommended Basic "over TLS" without saying where the TLS was meant to come from, and the `TIdHttpServer` is `strict private` with no accessor, so it could not come from here. That is deliberate: TLS is a standing obligation - cipher suites, protocol versions, certificate renewal, OCSP stapling, HTTP/2 - that a reverse proxy discharges better and without a rebuild, and owning it would mean owning the OpenSSL version the Indy SSL handler wants inside a process that already has a database driver's opinion about its libraries. `docs/http/server.md` now has a **TLS** section saying so, with the deployment the server is actually written for: terminate at IIS, Apache or nginx, bind the server to loopback, and read the caller from `ClientIP`, which resolves the last `X-Forwarded-For` entry only when the peer is loopback
- **The entry pages no longer teach a double free.** `Readme.md`, `docs/getting-started/quick-start.md` and `docs/guide/cookbook.md` called `LPerson.Free` on an entity from `CreateEntity<T>`, but a context built with `TTContext.Create(AConnection)` keeps an identity map, and the map owns what it holds: the second free arrived when the context went down. Every example now uses `FreeEntity<T>`, which frees the entity when the caller owns it and does nothing when the map does, and the same form is used in the JSON and HTTP pages, where a context refuses the identity map and the caller always owns - so there is one rule to remember rather than two
- **`TTList<T>` no longer described as owning its entities.** It extends `TList<T>` and owns nothing; the owning list is `TTObjectList<T>`, and `CreateEntityList<T>` picks the ownership that matches the context. Seven pages built entity lists with `TTList<T>.Create` and two of them said in words that the list frees what it holds - `docs/examples/simple-crud.md` twice. The `SelectAll` example in `docs/http/controllers.md` was the one that mattered: a JSON context has no identity map, so that list freed nothing, once per request
- **The event method attributes are named correctly.** The classes are `TBeforeInsertEventAttribute` and its five siblings, so the attribute is `[TBeforeInsertEvent]`; `docs/guide/events.md`, `docs/guide/validation.md` and `docs/api-reference/attributes.md` wrote `[TBeforeInsert]`, which under the `{$WARN UNKNOWN_CUSTOM_ATTRIBUTE ERROR}` those same pages prescribe is a compilation error. The examples also declared the methods `strict private`, where the default RTTI does not emit them: the resolver never sees the attribute, nothing is registered and nothing raises, so the method is simply never called. They are `public` now, with the rule written next to them


- **`docs/http/multi-tenant.md` no longer suggests a tenant setup that is not safe.** It offered "header, subdomain, or JWT claim" as equivalent ways to resolve the tenant. The claim is not one of them: the listener builds the per-request context and only then authenticates, so at the moment the tenant is chosen no token has been verified. With the single shared signing secret the examples imply, a user of one tenant could send their own valid token with the header of another and be served that customer's database. The page now says the tenant name is unverified client input, and gives the fix that needs no comparison and no ordering: one secret per tenant, derived from a base secret and the tenant name, so a token signed for another tenant simply fails verification. The "full tenant isolation" line is qualified as isolation of state, not of authorization
- **The `APIRest` demo reads its JWT signing secret from configuration.** It was a hardcoded constant in a file the documentation points at as a model, so anyone copying the demo inherited a signing key published in the repository. `GetSecret` now reads `TAPIConfig.Instance.Authentication.Secret` and raises when it is missing or shorter than 32 characters, instead of falling back to a default. The previous secret is in the repository history and must be considered compromised
- **The `APIRest` demo refreshes an entity after updating it.** With the creation audit no longer written by `Update<T>`, a `PUT` that answered with the entity it had just deserialized reported `createdAt` and `createdBy` empty: the row on the database was right, the response was not. `Context.Refresh<T>` before serializing costs one SELECT and makes the response match the row. Any application following the same shape needs the same change
- `docs/http/authentication.md` warns against hardcoding the secret next to the placeholder in the example
- **The REST demo mints and checks its token expiry in UTC, using the standard `exp` claim.** It formatted local time as `yyyymmddhhnnss` into a private `expireTime` claim and compared it against another local timestamp, so every daylight-saving transition moved the expiry: a thirty-minute token could last ninety, or be born expired. It is now `exp` in Unix seconds with a small clock-skew allowance. **Renaming the claim invalidates tokens already in circulation**: a token carrying the old `expireTime` reads back as `exp = 0` and is refused, so anyone who copied the demo logs every active session out at deploy. In an application that matters, keep the claim name and change only local time to UTC on both sides, which costs nobody their session The framework itself is unchanged and still checks the **signature only**: `TTHttpJWTAbstractPayload` imposes no claim set, so an application whose `IsValid` does not look at the clock issues tokens that never expire. `docs/http/authentication.md` now says so where the example is
- **The REST demo enabled connection pooling too late to have any effect.** `TAPIContext.Create` runs per request, long after `TAPIHttp.AfterConstruction` registered the connection, so the demo advertised pooling while running unpooled, and wrote to a global singleton from every request thread. The line moved to the server start-up, before `RegisterConnection`. The same mistake was in `docs/examples/rest-api.md` and `docs/http/server.md`, and `docs/database-drivers/index.md` now states when `Config` is read

- **The IDE build order of the package group is right in all five sets.** The `Build` target has always called the projects in dependency order - core, drivers, JSon, Http - but the `BuildGroupProject` item group, the one the IDE uses for *Build* over every configuration, was in an order of its own in every single set: `260` opened with `Trysil.Http260` and had the core in third place, and `270`, `280`, `290` and `370` all put `Trysil.Http` second while `Trysil.JSon`, which it requires, came eighth to tenth. A first build from the IDE therefore failed, on any of the five. The item groups now follow the same order as the `Build` target, which is read from the target itself rather than written by hand
- **Linux64 is no longer half-declared.** The platform was enabled in twenty of the fifty package projects and had a build group of its own in the 290 and 370 group projects, while the `.bat` files pass `"Win32 Win64"` and no page mentions it: nobody had ever compiled it, and the first proof of that was two linker artefacts from a Linux64 build - a link response file full of absolute paths, and an ELF version script - that had ended up tracked because `.gitignore` covered `Win32/` and `Win64/` but not `Lib/`. The platform is now disabled in every project, exactly as Android, iOS and OSX already were, the build groups are gone, and `Lib/` and `Linux64/` are ignored. Nothing that was building stops building: the supported platforms are the two the `.bat` files have always passed
- **Version metadata says 2.0.0.** All fifty package projects and the five Expert projects carried `FileVersion=1.0.0.0` and `ProductVersion=1.0.0.0` in every one of their `VerInfo_Keys`, so every binary of this release would have declared itself 1.0.0.0 to anyone reading its version resource. Those keys are only the **strings**, though: the numeric part of a Windows version resource comes from `VerInfo_MajorVer` / `MinorVer` / `Release` / `Build`, and not one of the sixty-two projects in the repository defined them at all, so the compiler used its own default - 1.0.0.0 - for the numbers whatever the strings said. All fifty-five product projects now carry both, `2.0.0.0` and `2/0/0/0`, and `boss.json` says `"version": "2.0.0"`
- **`docs/Setup.md` is gone, and what it had that was right moved into the installation page.** It was the only one of the 44 pages outside the `nav`, so it was never published, and it was linked from the Readme and from five demo readmes: everyone following those links read a page the documentation site did not have. It also duplicated `installation.md` and contradicted it, and the contradiction was resolved against the machine's own registry: the expert lives under `Experts` (plural, which `Setup.md` got wrong as `Expert`), its project is in `Trysil.Expert/` and not under `Packages/` (which `installation.md` got wrong), it has to be built for Win32 because the IDE is a 32-bit process, and Delphi 13 Florence's registry version is `37.0` (which `installation.md` left as a dash). The installation page now carries all of it, with the value name and the full path spelled out, and every link points there
- **The PDF manuals are gone from the repository and from the Readme.** They predate the whole HTTP module, so they described a library that no longer matched, while being linked from the front page as *the* manual. The documentation site and the blog stay in the table
## Hardening - Error Contract, Filter Ceilings & Lifetime Fixes

**Breaking.** Two kinds, both called out inline below.

*Compilation* - `NestedException: Exception` is gone from `ETException`, replaced by three read-only string properties; the `TExceptionHelper` class helper on `Exception` is removed; and `TTHttpListener<C>.Create` takes a fourth argument. Code that inspects the exception chain, calls `E.ToJSon`, or builds a listener by hand needs the one-line change described below.

*Behaviour* - the 500 response body, the `includeDeleted` filter key, the default `limit`, and the `TaskID` format.

### Exceptions

- **`ETException` no longer takes ownership of the exception in flight.** It used to call `AcquireExceptionObject` in the base constructor, which detaches the current exception from its raise frame, and then free it in its own destructor. Any `ETException` built inside an `except` block - `ETHttpBadRequest` included, since every `ETHttp*` descends from `ETException` - stole the outer exception and freed it, leaving a later `raise;` working on a zeroed frame and a dead object. The constructor now records the **class name and message as strings**, read through `ExceptObject`, which is non-destructive
- **`NestedException: Exception` is replaced** by `HasNestedException: Boolean`, `NestedExceptionClassName: String` and `NestedExceptionMessage: String`. The chain is diagnostic text, not a live object graph
- **`ETHttpConflict` (409)** and `TTHttpStatusCodeTypes.Conflict`: a convenience subclass for a version conflict or an integrity violation, so the status code has a name. The framework never raises it: mapping `ETConcurrentUpdateException` and `ETDataIntegrityException` to HTTP stays with the application, deliberately

### HTTP error contract

- **Every 5xx goes through the same path**, including an `ETHttpException` whose status code is 500 or above. Routing it by class instead of by status would have left `raise ETHttpInternalServerError.Create(E.Message)` - a natural thing for a host to write - reporting the message to the client and reopening the hole this change closes. `TTHttpErrorResponse.ToJSon` gained an overload that keeps the caller's status code, so a 503 stays a 503
- **Breaking: the 500 body no longer carries the exception.** `TExceptionHelper`, the class helper that serialized `Self.Message` verbatim and recursed over the exception chain, is **removed**. Anything that is not an `ETHttpException` now returns `TTHttpErrorResponse.ToJSon(ATaskID)` - `{"status":500,"message":"Internal server error.","taskId":"..."}` and nothing else. That path was reachable without a token in a multi-tenant app that resolves the tenant in the controller constructor, and it leaked database engine, host, database and account names straight to the caller
- **`TTHttpLogAbstractWriter.WriteError(ALogError: TTHttpLogError)`**: the detail that no longer reaches the client now reaches the log. The record carries task id, host, uri, exception class and message, and the recorded nested class and message. Virtual and not abstract, like `WriteDiscarded`, so existing writers still compile, and the default forwards to `WriteAction`. The exception is rendered to strings **synchronously on the request thread** - the object does not survive the handler, so only the strings are queued. It is not gated by `OnCanLog`
- **Breaking: `TTHttpTaskID` is now a 32 character opaque identifier** derived from a GUID. It was a millisecond timestamp plus the thread id, which two requests served by the same thread in the same millisecond could share - and correlation by task id is only worth anything if the id is unique. `ToString` no longer appends the thread id; the `ThreadID` property stays on the record for in-process use

### Server-side filter

- **`[TNotFilterable]`** (`Trysil.Attributes`): marks a column as not reachable from the JSON filter. `where` and `orderBy` on it answer `400` with `SColumnNotFilterable`, which until now was declared and never used. The flag travels with the entity mapping, so it is resolved once per entity and costs nothing per request, and it applies to the filter built from the payload rather than to what the entity can express through `TTFilterBuilder`

```delphi
[TColumn('Password')]
[TNotFilterable]
FPassword: String;
```

- **`MetadataToJSon<T>` reports `"filterable": false`** for a column carrying `[TNotFilterable]`. The pair is emitted only when the column is excluded, so existing payloads do not change and absence keeps meaning filterable. Without it a client that builds its filter UI from the metadata would keep offering a column that answers `400`
- **`TTHttpFilterParameters`**: ceilings for the JSON filter, carrying `MaxLimit`, `MaxWhereConditions`, `MaxOrderByColumns` and `IncludeDeleted`. `TTHttpFilter<T>.Create` with two arguments applies `Defaults` - 1000 / 32 / 8 / False; the three-argument overload takes them from the host application. A negative ceiling means unlimited, and **a zero ceiling means the default**, so a record left at its zero state - `Default(TTHttpFilterParameters)`, or a field of a class, which the RTL zeroes - behaves as the defaults instead of removing the pagination clause altogether. A local variable is not that: the record has no managed fields, so nothing zeroes it on the stack, and a garbage `IncludeDeleted` reads as `True`. Assign `Default(TTHttpFilterParameters)` or a constructor, and do not rely on the declaration. This governs the filter built from the payload: an endpoint that builds its own `TTFilter` is unaffected
- **Breaking: an omitted `limit` no longer means the whole table.** `TTFilterPaging.IsEmpty` is true for `limit <= 0`, so the pagination clause was simply not emitted. `limit` is now clamped: absent, zero or negative means `MaxLimit`, above the ceiling is capped to it, and a negative `start` is normalized to `0`
- **Breaking: `includeDeleted` is no longer read from the payload.** Bypassing the soft-delete filter was a visibility switch in the client's hands. It is now `TTHttpFilterParameters.IncludeDeleted`, decided server-side
- **A non-object item inside `orderBy` is a 400**, as it already was inside `where`. It used to leave the array slot at the zero record, whose `ToString` produced `' '` - not empty, so it passed the `OrderBy.IsEmpty` guard and produced `... ORDER BY  `, a syntax error surfacing as a driver message on the 500 path
- **Column names are canonicalized**: the name that reaches the SQL text comes from the metadata, not from the client string that matched it case-insensitively
- **More `where` conditions or `orderBy` columns than the maximum is a 400**, not a slow query

### Logging

- **The discarded-entry counters are bounded.** The host is sanitized and truncated to 64 characters before it becomes a dictionary key or reaches the report, distinct hosts are capped at 64 with the remainder accumulating under `<other>`, and an absent host no longer produces an empty key. The counters are now flushed **on a timer as well as when the queue empties** - under sustained load the queue never empties, so they were never flushed and the dictionary grew with every new `Host` header

### Multi-tenant

- **`TTMultiTenant.Remove` detaches without destroying.** `FOwner` is an owning list, so `Remove` freed the tenant immediately while other threads could still hold a reference handed out by `TryGet` or `GetOrAdd`. The instance now lives until the registry is destroyed, and `GetAll` iterates the dictionary so it stops listing removed tenants
- **Registering the same connection twice is a no-op, registering a different one under the same name still raises.** `Remove` never deregistered the connection, so a `GetOrAdd` on the same name afterwards hit a duplicate key and burned the name - and with the cooldown in place that transient failure stuck to it for the whole window. `RegisterConnection` now compares against a signature of the parameters Trysil itself passed, rather than reading them back from FireDAC: an identical registration - the parameter lines sorted and matched on exact text, parameter names included - is left exactly as it is, a conflicting one raises. Reading them back would have called a shorter list identical to a longer one - which is what happens when pooling is turned off for a name, since the `POOL_*` lines simply stop being emitted - and would have compared values case-insensitively, so a changed password or a `Database` differing only in case would have passed as unchanged. Replacing the definition instead would have been worse than the disease - `DeleteConnectionDef` does not touch the physical layer, so the old `TFDPhysConnectionHost`, its pool and **its cleanup thread** would survive for the life of the process, and for a while the host's `POOL_MaximumItems` would be doubled. Not deleting anything also means the name never stops resolving, which a delete-then-add sequence cannot promise to a request thread running in between. The signature is taken from `DriverID` plus the caller's parameters and **before** the `POOL_*` lines are appended: those are derived from `TTFireDACConnectionPool.Instance.Config`, which an application can change at any point, so folding them in would have made an identical re-registration start raising the moment anyone touched the global pool configuration - the burned name again, by another route. The whole comparison happens under the pool's write lock, as does the deregistration. A conflict raises `ETException` with `SConnectionAlreadyRegistered`: it used to be an `EListError` from the connection dictionary, or FireDAC's own duplicate-definition error, so an `except` that discriminates by class needs updating
- **`UnregisterConnection` is a hard teardown**, not the inverse of a cache miss. It calls `CloseConnectionDef` before `DeleteConnectionDef`, so it closes every open connection on the definition and destroys the physical connection host and its pool instead of leaving them alive for the life of the process. That is what makes it the way to *replace* a definition, since registration refuses to overwrite one - but it also means a `TTConnection` another thread resolved an instant earlier keeps its object and loses the FireDAC connection underneath it, raising on the next statement. Quiesce the name before calling it
- **Failed tenant creation is rate limited.** A failed `GetOrAdd` records the name with a cooldown - `FailureCooldown`, 5000 ms by default, `0` disables it - and repeats inside the window fail without touching the disk. Failures are still not memoized permanently, so onboarding a tenant by dropping a folder keeps working. The table is capped at 128 names; when it is full the entry closest to expiry is evicted, rather than the new name going unrecorded, which would have removed the protection precisely under the load that creates it
- **Breaking: `GetOrAdd` now always raises `ETTenantUnavailable` when it cannot build the tenant**, carrying `TenantName` and `OriginalClassName` and keeping the original message. It used to propagate whatever the host's `TTTenantConfig` raised, and with the cooldown in place the class would have depended on how recently someone else had tried the same name - a host discriminating by type would have taken different branches for the same cause. Wrapping every failure makes it deterministic. The original exception cannot simply be re-raised: Delphi constructors are not virtual, so rebuilding one from a class reference calls `Exception.Create` and would produce, for instance, an `ETHttpNotFound` with a status code of zero.

    One consequence to plan for: `ETTenantUnavailable` descends from `ETException`, not from `ETHttpException`, so on the HTTP path an unresolvable tenant now answers **500 with the fixed body**, where before the exception the host's `TTTenantConfig` raised decided the status. If you turned an unknown host into a 404 that way, catch `ETTenantUnavailable` where you resolve the tenant and re-raise the `ETHttp*` you want

### ORM

- **`[TWhereClause]` parameters are bound again.** `TTAbstractSelectSyntax.AddWhereClause` added them to the syntax object's own copy of the `TTFilter` record while the binding ran on the caller's copy. `TTAbstractSelectSyntax` now exposes `Filter`, and `TTGenericConnection.SelectCount` and `TTGenericReader.GetDataset` read `SQL` into a local first and then bind `LSyntax.Filter`
- **`Guid` and `Currency` columns are honoured on the filter path.** `TTColumnMetadata` carries `IsGuid` and `IsCurrency`, populated by `TTGenericConnection.GetMetadata`, and `TTFilterParameter` carries them to `SetParameter`. A `Currency` column mapped onto `ftBCD` was converted and bound as `Double`. `FindColumnMap` matches on `LookupName` rather than `Name`, so this and `[TNotFilterable]` resolve on entities with `[TJoin]` too, where the metadata columns carry the join alias
- **`TTLazy.SetEntity`**: `FEntity` is cleared right after the `Free`, so a failing clone no longer leaves a dangling reference for the destructor to free twice, and `SetEntity(nil)` clears the relation instead of reaching `CloneEntity(nil)` and an access violation
- **`TTFireDACConnectionPool.Instance`**: the singleton is still created lazily, but under a lock instead of a plain test-and-assign. The test-and-assign was not atomic, and two instances would mean two open `TFDManager`s with connection definitions registered on only one of them. Creation stays lazy on purpose: `AfterConstruction` calls `FDManager.Open`, which cannot run during unit initialization
- **`TTParameter.Create` with two arguments** passed the uninitialized `FConnectionID` instead of `AConnectionID`
- **`SetContentStream`** freed `AResponseInfo.ContentStream`, which is still nil on the only reachable error path, losing the stream it had just built

### Logging: what the cap actually covered

- **`MaxContentLength` did not keep the body out of the log.** With `Content-Type: application/x-www-form-urlencoded` Indy reads the whole body into `FormParams`, glues it to the query string and decodes it into `Params`, so the parameters *are* the body while only `Content` was gated. `Params` is now omitted whenever `Content` is, and `ParamsOmitted` declares it the way `ContentOmitted` does
- **Breaking: the log caps have finite defaults.** `RegisterLogWriter<W>()` and `RegisterLogWriter<W>(AThreadPoolSize)` used to leave content, parameters and headers unlimited, so the two forms an application reaches for first were the two that capped nothing. They now apply 64 KB of content and 128 items. Pass a `TTHttpLogParameters` explicitly, with a negative value, to go back to unlimited
- **Sensitive headers are redacted, not omitted.** `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie` and `X-Api-Key` reach the writer with their name intact and `<redacted>` in place of the value. With `TTHttpAuthenticationBasic` the previous behaviour put the credentials in the log in clear text after base64, on every request. `OnCanLog` was not a remedy: it is per request and all-or-nothing, so keeping the token out meant giving up the endpoint's log entirely
- **`MaxItemCount`**: a fourth `TTHttpLogParameters` field, because a cap in bytes does not bound a count - tens of thousands of short distinct parameter names fit in a body of about a megabyte. Above the cap `Params` and `Headers` are not captured, while `ParamsCount` and `HeadersCount` are always written. Negative means unlimited, and the existing constructors keep the previous behaviour
- **The demo's log writer is aligned with the contract.** `TLogRequest` gains `ParamsCount`, `ParamsOmitted`, `HeadersCount` and `HeadersOmitted`, `TLogResponse` gains `Uri`, and a `log.Errors` table with a `WriteError` override joins the other three. Without the override the default forwards the whole error payload into a `TTHttpLogAction`, and the demo's `[Action]` column is `nvarchar(255)`: the row was silently truncated away by the database and the exception swallowed by the log thread, so a 5xx left no trace exactly where the documentation promised one. `Demos/APIRest/SQL/Log.SqlServer.sql` gains the columns and the table. It is the code hosts copy, so a `Params` column left empty with nothing in the row to say why is a defect in the example, not only in the example's documentation
- **Breaking: `TTHttpListener<C>.Create` takes the log**, so the listener can hand `WriteError` the detail it no longer sends to the client. The constructor signature changed rather than gaining an overload: the listener is built by `TTHttpServer<C>` and there is no reason for a host to construct one, but the type is in the package, so this is noted rather than assumed harmless
- **`TTMultiTenant<T>.GetAll` no longer returns registration order.** It iterates the dictionary now, which is what makes it stop listing removed tenants; the order is unspecified and differs between runs. Sort the result if you display it
- **`TTHttpLogResponse.Uri`**: the request record carried the uri and the response record did not, so a writer could not decide anything by route on the way out - redaction had to scan every payload for sensitive keys instead of matching the endpoint. `LogResponse` already receives both records, so the value was there all along

### Authorization

- **Breaking: `[TAuthorizationType]` is now read on the method as well as on the class**, the method taking precedence. Areas were already read on both. The asymmetry cut both ways, and both directions change on upgrade:

    - a method added to a controller declared `[TAuthorizationType(None)]` - which is what an authentication controller is, so that it can expose the login - silently became an anonymous endpoint, inheriting the file's convention along with its authorization level. That case is now closed;
    - conversely, `[TAuthorizationType(None)]` written **on a method** of an authenticated controller used to be ignored, leaving the endpoint protected. It is now applied, and that endpoint becomes anonymous.

    Nothing reports the second case: it compiles, runs, and answers without a token. Before upgrading, grep for the attribute on methods and confirm each occurrence still says what you mean

### HTTP headers

- **Header lookup is case insensitive.** `TTHttpHeaders` now builds its dictionary with an ordinal case-insensitive comparer, so `Headers.Value['Authorization']` matches whatever case the client sent. It also affects enumeration: two headers differing only in case now collapse into one entry, so `Headers.Count` and the log's `HeadersCount` can be one lower than before. The comparer is resolved once in a class constructor rather than per request, because the RTL's own `TIStringComparer.Ordinal` is a lazily created singleton with an unsynchronized test-and-assign. HTTP header names are case insensitive by specification and **HTTP/2 mandates lower case**: the previous exact-match lookup would have failed to authenticate the first conforming client or proxy, closed - a 401, not a bypass - and with "the right credentials do not work" as the only symptom. `TTHttpParameters` deliberately keeps exact-match semantics, as query parameter names are case sensitive

### Build

- **Every package is set to explicit rebuild** (`{$IMPLICITBUILD OFF}`, 50 `.dpk` files across the five Delphi versions). Building a project group that includes Trysil no longer rebuilds the packages implicitly, which is both faster and predictable; the trade-off is that after changing Trysil's own sources you have to build the packages yourself before the change reaches a dependent project

### Tests

- Twenty-three new cases, suite at 360 green: the nested exception is captured as strings and a `raise;` after a swallowed `ETException` still finds the original alive; the 500 body carries no chain; `ETHttpConflict` is 409; the task id is unique across a thousand calls on one thread and carries no clock; the filter uses canonical column names in both `where` and `orderBy`, rejects a non-object `orderBy` item and refuses too many conditions or columns; the limit ceiling clamps and a negative ceiling stays unlimited; the log queue carries error entries and never keys a discard on an empty host; the item cap is unlimited unless asked for and rejects counts above it; header lookup ignores case while parameter lookup does not

## Transactions - Explicit Mode & RunInTransaction

- **`TTContext.RunInTransaction(AProc)`**: runs a procedure inside a transaction. It commits on clean exit, rolls back and re-raises on an exception, and **joins the active transaction** when one is already open, so a domain method that wraps itself in it is atomic both when called on its own and when called from inside a larger unit of work
- **`TTTransactionMode`** (`Trysil.Transaction.pas`, scoped enum): `CommitOnDestroy` or `RollbackOnDestroy`, passed to `CreateTransaction`, decides what destruction means when neither `Commit` nor `Rollback` was called. `RollbackOnDestroy` makes the ordinary `try..finally LTransaction.Free` correct, because any path that does not reach `Commit` rolls back. **Breaking (compilation) for anyone calling the constructor directly**: `TTTransaction.Create` takes the mode as a second argument and has no one-argument overload. The documented way in is `TTContext.CreateTransaction`, which does have one and means `CommitOnDestroy`, so most code is untouched
- **`TTTransaction.Commit` is now public**, and clears the local flag so that destruction never repeats work already done. A failed `Commit` attempts a rollback and re-raises, instead of leaving the transaction open on the connection
- **`CreateTransaction()` with no arguments is deprecated** and maps to `CommitOnDestroy`. Existing behaviour is unchanged, so nothing breaks: `try..finally LTransaction.Free` still commits on the way out of an exception, which is exactly why the deprecation is there
- **A nested `RollbackOnDestroy` raises**: Trysil does not use savepoints, so an inner transaction cannot roll back independently of the outer one. Declaring that intention now fails immediately instead of silently doing nothing
- **Destruction is silent by design**: whatever happens in `BeforeDestruction` is swallowed, because an exception escaping a destructor would replace the error that caused the unwind and would stop the instance from being freed
- **`TTTransaction.Run(AConnection, AProc)`**: the shared implementation, at the connection layer. `TTContext.RunInTransaction`, `TTContext.InternalApplyAll`, `TTSession<T>.ApplyChanges` and `TTGenericCommand.ExecuteCommand` all route through it, so `TTTransaction` is now constructed in exactly two places
- **`ExecuteCommand` no longer builds a transaction object per command** when the connection is already in one
- **Tests**: six new cases in `Trysil.Tests.Abstract.Transaction.pas` - `RollbackOnDestroy` with and without an explicit `Commit`, a nested `RollbackOnDestroy` raising, and `RunInTransaction` committing, rolling back and joining an outer transaction

## Currency - First-Class Decimal Type

- **`Currency` entity fields**: `Currency` and `TTNullable<Currency>` are now mapped end to end without going through `Double`. `TTColumnMap.IsCurrency` drives the choice, exactly like `IsGuid` / `IsInteger` / `IsInt64`, so a `Currency` member is read through `TTCurrencyColumn` (`TField.AsCurrency`) and written through `TTCurrencyParameter` (`TTParam.AsCurrency`), and its four decimals stay exact
- **`TTParam.AsCurrency`**: new writer on the parameter contract, implemented by `TTFDParam`, the only implementation **in this repository** - a driver written outside it brings its own `TTParam` descendant and does have to change, see the entry on `TTParam` in the 2.0.0 section
- **Filter values**: a `Currency` value bound to a filter parameter is now written as `Currency` instead of being converted to `Double`
- **JSON**: `TTJSonCurrencySerializer` / `TTJSonCurrencyDeserializer` emit and parse the exact decimal representation with invariant formatting, replacing the previous aliasing on the `Double` serializer
- **`TTDataset<T>`**: a `Currency` column is published as an `ftCurrency` field definition, and the record buffer is converted for both plain and nullable members. Previously a `TTNullable<Currency>` member was filled with the raw bit pattern of a `TTNullable<Double>`. **`TTDataset<T>` is still in development and is not shipped**: it is in no package, so it is not in the compiled output. This entry describes work in progress, not something you can use yet
- **Trysil Expert**: new `Currency` column type, generating `DECIMAL(19,4)` (`NUMBER(19,4)` on Oracle, the same type). Firebird and InterBase get `DECIMAL(18,4)`, since they reject a precision above 18
- **Tests**: `TTestAllTypes` gains a `Currency` and a `TTNullable<Currency>` column on all seven engines, with a round-trip test that accumulates 0.07 ten times and expects exactly 0.70

## JWT - Signing Algorithms & Key Rotation

- **Payload split into algorithm units**: `TTHttpJWTAbstractPayload` (`Trysil.Http.JWT.Payload.pas`) now declares only the signing contract (`Algorithm`, `Sign`, `Verify`, `ToJSon`, `FromJSon`); the actual cryptography lives in `TTHttpJWTHS256Payload` (`Trysil.Http.JWT.Payload.HS256.pas`) and `TTHttpJWTRS256Payload` (`Trysil.Http.JWT.Payload.RS256.pas`)
- **BREAKING CHANGE**: application payloads must now inherit from `TTHttpJWTHS256Payload` (previous behavior: HMAC-SHA256 with the secret returned by `GetSecret`) or from `TTHttpJWTRS256Payload`, no longer from `TTHttpJWTAbstractPayload`
- **RS256 (RSA-SHA256)**: asymmetric signing built on OpenSSL `libcrypto`, so the issuer holds the private key and every resource server only needs the public one
- **Key objects, parsed once** (`Trysil.Http.JWT.RSAKey.pas`): `TTHttpJWTRSAPrivateKey` (`Sign` + `Verify`) and `TTHttpJWTRSAPublicKey` (`Verify` only) parse their PEM in the constructor and own the OpenSSL `EVP_PKEY` for their whole lifetime. The application creates them once at startup and the payload borrows them through `GetSigningKey` / `GetVerificationKey`, so **no request ever parses a PEM**. A verify-only server is expressed by the type: give it a public key and `Sign` does not exist
- **Verification key resolved per token**: `GetVerificationKey(AKeyID)` is called at verify time with the `kid` of the incoming token, so it can pick the matching key or the current tenant's. An unresolved key fails closed (`Verify` returns `False`, no exception), while signing without a private key raises `ETHttpJWTException`
- **`SigningKeyID` derives from the key**: the RS256 payload emits the `kid` of the key it signs with, so a key ID is declared in one place
- **`libcrypto` resolved dynamically at first use**: the key unit compiles on every platform and only fails (with `ETHttpJWTException`) when a key is actually loaded without OpenSSL present. Candidate library names cover Windows (`libcrypto-4/3/1_1[-x64].dll`), Linux, macOS (including the Homebrew paths) and Android; resolution is guarded by a critical section and the library is intentionally left loaded. HS256 has no external dependency
- **Keys are warmed up on construction**: loading a key runs one signature operation while still single-threaded, so OpenSSL's lazily populated internals are in place before several threads share the key. One key instance can then sign and verify concurrently
- **Tests**: first RS256 test fixture (`Trysil.Tests.Http.JWT.RS256.pas`): round-trip, wrong public key, missing signing key, unresolved verification key, `kid` in the header, and eight threads sharing one key pair
- **`kid` header for key rotation**: `TTHttpJWTAbstractPayload.SigningKeyID` (override `GetSigningKeyID` to emit a `kid` when a token is generated). On the way in, the `kid` is an **argument, not payload state**: `LoadFromToken` extracts it from the header and passes it to `Verify`, which hands it to `GetSecretFor` (HS256) or `GetVerificationKey` (RS256). `GetSecretFor` defaults to `GetSecret`, so applications that do not rotate keys are unaffected
- **Header is parsed, not compared byte-for-byte**: `LoadFromToken` reads the header JSON and matches `alg` case-insensitively against the payload's own algorithm; a token signed with a different algorithm is rejected, and additional header members such as `kid` no longer invalidate the token
- **Breaking (compilation): `TTHttpJWTEncoding` works on bytes**: `Encode(TBytes): String` / `Decode(String): TBytes` produce and consume base64url without padding directly, replacing the previous double base64 string round-trip. The `TTHttpJWTHeader` class is gone: the header is built by `TTHttpJWT<P>`
- **Constant-time HS256 signature comparison**: `TTHttpJWTHS256Payload` compares signatures without early exit, removing the timing side channel of a plain string equality test

## HTTP - Client IP Behind a Proxy

- **`TTHttpRequest.ClientIP`**: returns `RemoteIP` for direct connections. When the connection comes from loopback (`127.*`, `::1`, `0:0:0:0:0:0:0:1`, including `::ffff:`-mapped forms), it takes the **last** `X-Forwarded-For` entry, which is the one written by the trusted local reverse proxy, strips any port, and unwraps bracketed IPv6 literals. Client-supplied entries earlier in the chain are ignored, so the header cannot be spoofed from outside
- **`TTHttpLogRequest.ClientIP`**: exposed next to `RemoteIP` and emitted in the request log JSON, so logs behind a proxy show the real caller

## Fixes

- **`TTContext.ApplyAll<T>` inside an open transaction**: it no longer opens a second transaction when the write connection already has one. It joins the caller's transaction, and rollback/commit stay with whoever started it
- **Breaking, and the compiler does not catch it: `TTLazy<T>` double free**: assigning an entity to a lazy relation with the identity map disabled now stores a **clone** of that entity. Previously the caller and the lazy field owned the same instance and both freed it, so the code that worked was the one that handed the instance over and stopped freeing it: that instance is lost now. Free what you assign
- **A failing log writer no longer breaks the server**: `TTHttpServer<C>.Log` swallows exceptions raised by a log writer, so logging cannot abort the operation being logged
- **`Host` in `TTHttpLogResponse`**: the response log record is now built from the request and carries `Host` alongside the user
- **Sqids round-trip on a lazy relation foreign key**: JSON deserialization decodes the raw string value of the FK instead of its quoted JSON representation
- **MariaDB driver ID**: the FireDAC driver link registered by `TTMariaDBDriver` is now named `MariaDB` instead of `Trysil_MariaDB` (the other drivers keep the `Trysil_<engine>` form derived from their base driver ID). Only relevant to code that referenced the driver ID directly

## Algebraic Filter Expressions

- **Expression filter API** (`Trysil.Filter.Expression.pas`): `TTProperty` and `TTExpression` records add operator-overloaded WHERE building to `TTFilterBuilder<T>`. Combine comparisons with `and` / `or` / `not` to produce correctly **parenthesized** groups - e.g. `((City = 'Roma') or (City = 'Milano')) and (Age >= 18)` - which the flat fluent chain cannot express
- **`TTProperty` operators & methods**: `=`, `<>`, `>`, `>=`, `<`, `<=`, plus `Like`, `NotLike`, `IsNull`, `IsNotNull`, `Between`, `InValues`
- **Builder overloads**: `Where` / `AndWhere` / `OrWhere` accept a `TTExpression`; `OrderByAsc` / `OrderByDesc` accept a `TTProperty`. Both forms share one parameter counter, so they mix freely in a single builder
- **Join entity filtering**: the two-argument `TTProperty.Create(Alias, Column)` qualifies the WHERE reference as `Alias.Column` and validates against the joined column's output alias `Alias_Column` - the first filter form that resolves join aliases
- **Trysil Expert - companion record generation**: the "Generate entity model" dialog can emit a `T<Entity>Properties` companion record next to each entity (one `TTProperty` per column, primary key included, version column excluded), so column names are checked by the compiler at the call site. ## Undelete & Lazy Loading

- **`Undelete<T>` / `UndeleteAll<T>`** (`TTContext`): reverse a soft delete - clears the `[TDeletedAt]` / `[TDeletedBy]` columns and issues an `UPDATE`. Raises `ETException` (`SUndeleteNotSupported`) when the entity has no `[TDeletedAt]` column
- **`IncludeDeleted` overloads on `Get<T>` / `TryGet<T>`**: `Get<T>(AID, AIncludeDeleted)` and `TryGet<T>(AID, out AEntity, AIncludeDeleted)` load an entity by primary key even when it is soft-deleted (existing single-argument overloads default to `False`). That is the shape this window introduced and the one the public master carries; the release above reorders the arguments of `TryGet<T>`, and says so
- **`TTLazy<T>` resolves soft-deleted entities**: lazy single-entity references now load through `Get<T>(ID, True)`, so a soft-deleted parent still resolves through its foreign key

## JOIN Queries & Raw Select

- **`[TJoin]` attribute**: declarative JOIN support with three overloads - simple (`TJoin(Kind, Table, SourceCol, TargetCol)`), with alias for self-joins (`TJoin(Kind, Table, Alias, SourceCol, TargetCol)`), and chained (`TJoin(Kind, Table, Alias, SourceTableOrAlias, SourceCol, TargetCol)`)

- **`TJoinKind`**: scoped enum - `Inner`, `Left`, `Right`

- **Identity map skip**: join entities bypass the identity map (same PK can appear in multiple rows)
